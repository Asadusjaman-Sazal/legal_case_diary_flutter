## Label / Localization Convention (added during implementation, 2026-09-17)

Every user-facing label on the Settings surface (and the rest of the app) lives in `lib/core/l10n/app_en.arb` and `lib/core/l10n/app_bn.arb` — those two files are the only place a label text is written. Code reads them through `AppLocalizations.of(context)`; `flutter gen-l10n` (wired by `l10n.yaml` + `flutter: generate: true`) regenerates `lib/core/l10n/generated/*`.

- **Key naming:** one prefix per screen, in camelCase of the screen: `settingsScreen_*` (main list) `settingsAccountProfile_*` `settingsProfile_*` `settingsManageAccount_*` `settingsOnlineSync_*` `settingsBackupRestore_*` `settingsEditCourtSteps_*` `settingsEditCourtNames_*` `settingsCourtNamesSteps_*` / `settingsEditItems_*` `settingsItemList_*` `settingsCourtList_*` `settingsCourtFlow_*` / `settingsLowerCourtCategories_*`; shared chrome uses `sharedActions_*`, `sharedDialogs_*`, `sharedMessages_*`; the app shell uses `appShell_*` and `databaseRecovery_*`; case screens use `<screen>_*` / `casesContact_*`.
- **Files are grouped by screen:** an `"@@_section_<id>": "<TITLE>  |  <source file>"` row precedes each screen's keys. `flutter gen-l10n` ignores `@`-prefixed keys (verified), and the repo's `generate_l10n.py` / `tool/generate_l10n_dart*.py` skip them as well, so the markers are documentation only. Keep new keys inside their screen's section and in the same relative order in both files — `test/l10n/arb_keys_test.dart` fails if the two files diverge.
- **Both languages are mandatory:** add a Bengali value with the same key in `app_bn.arb`. The guard test also fails if a translation drops a `{placeholder}`.
- Never hard-code a label in a Settings screen, and never pass a literal to `SettingsSubPageModal(title:)`, a dialog title/body, a button label, a tooltip, or an empty/error state. Section headings are stored in sentence case and upper-cased by the widget.

## Shared Sub-Menu Sizing Contract (added during implementation)

- `lib/features/settings/presentation/settings_menu_card.dart` (new file; logged in `docs/version_history.md` 0.0.171) is the single source for sub-menu card/button sizing:
  - `SettingsMenuCard` — the shared tappable card (Card, radius 12, 16 px padding, body-lg title / body-sm subtitle, 28 px icon, chevron). Used by the Account & Profile menu (the size reference), the Edit Court/Steps menu, Edit Court Names & Categories, Lower Courts divisions, and Districts.
  - `settingsMenuCardRowHeight` (44 px) — the content-row floor. Rows that keep their own mockup layout (Manage Account items, the Delete Account card, Online Sync's Cases/Notes/References rows) use it so they render at the same height.
  - `settingsPrimaryButtonHeight` (56 px) — every sub-menu primary button: Sync Now, the three Backup & Restore actions, and Profile's Save Profile.
  - `SettingsActionCard` (0.0.411) — the full-width account action card (16 px padding, 40 px icon circle, the 44 px row floor) in two colour tones: **neutral** for Manage Account's **Logout** and **destructive** for its **Delete Account**. One widget for both, because the user asked for the Logout button to be the same size as the Delete Account button — so their size is a property of the code rather than two layouts that must be kept equal by hand.
- **Size override, user-approved 2026-09-16:** every sub-menu card renders **76 px** and every sub-menu primary button **56 px** (both measured with a throwaway widget test). This deliberately supersedes the per-mockup sizes — e.g. `settings_backupRestore`'s `h-12` (48 px) buttons are now 56 px, and its `ListTile`-style rows are now the Account & Profile menu card — so those bodies match their mockups in everything except card/button size. Change a size only through the constants above, never with per-screen literals.
- Outside the contract (unchanged): non-tappable content cards (Backup status, profile data card, Quick Tip note, Online Sync status), the Backup schedule's 56 px radio rows, the `settings_courtNamesSteps` card's 44 px action buttons (the card itself uses `settingsMenuCardRadius` and the 44 px row floor), the dense court/item edit rows, and Language's plain `ListTile`s.
- **The Settings list's section card is a shaped `Material`, not a decorated `Container` (0.0.407).** A `ListTile` paints its background and ink splashes on its nearest `Material` ancestor, so the white `Container` with top/bottom hairlines that each section used to be hid every row's ripple — and Flutter asserts about exactly that, once per row per layout, which is what filled the app's error log with 179 bare `FlutterError` entries and fed the 0.0.403 ANR loop. `Material(color: AppColors.surface, shape: Border(top: …, bottom: …))` paints the same white card and the same two hairlines per `settings_main`, with the rows' ink now landing on it. The rule for any future tile list on this surface: the card wrapping `ListTile`s must itself be a `Material` (as `backup_restore_screen`'s schedule card already is), never a colour-bearing `DecoratedBox`. `settings_drawer_share_test.dart`'s `drainFrameworkNoise` helper, which swallowed the assert as noise, is deleted — its tests now fail if any framework error returns.

## Lower Court Categories (added during implementation, 2026-09-16)

The Edit Court/Steps menu carries a third card, **Lower Court Categories**, alongside "Edit Case Types, Step etc" and "Edit Court Names & Categories":

- Flow: **Divisions → Districts → Court Categories** (the category list is the last screen). The Divisions and Districts pickers are the existing `court_category_screen.dart` / `district_list_screen.dart`, routed with `?flow=lower_court_categories` (`AppRoutes.lowerCourtCategoryFlow`); the category list is `edit_court_steps/lower_court_category_list_screen.dart` (`AppRoutes.settingsLowerCourtCategoryList`).

- The add button is the Add Case button (black FAB, white `+`, size 28, default bottom-right), because the mockup's FAB is that same control.
- **Mockup note:** there is no mockup for the category list itself; it reuses the court-row layout from `courtCategory_lowerCourts-Districts_listOfCourts\code.html` (drag handle, title, edit, delete) per the Critical Rules above, rather than introducing a new card design.

## View Settings (added during implementation, 2026-09-17)

This screen has no mockup of its own. These are the decisions taken while implementing §10.1's five values (all five are stored in the one per-user preference row — see Phase 4 Implementation Notes):

- **One labelled section per setting**, the label above the control in the Notifications screen's pattern (`SettingsSectionLabel`), values in Title Case ("7 Days", "4 Screens Selected", "8 of 8 Sections Shown"). **Default Landing Page sits in a card of its own**, below the Navigation card.
- **The two list settings are check-mark dropdowns, not inline switches** (0.0.180): the shared dark picker header over one option row per candidate; ticking toggles without closing the picker, and the Bottom Navigation list is reorderable by drag & drop inside it. The at-least-one-tab rule (with its snack bar) is enforced there.
- **The rows are one serial per list, and choosing a screen never moves a row** (0.0.189). Both lists offer `bottomNavTabDefs`' eight screens in a serial order; ticking only toggles the check mark, and a drag is the only thing that rearranges the rows.
- **The Bottom Navigation serial is the user's, and it is saved** (0.0.200). The rows open in the order the user left them — the new per-user `bottom_nav_order` key holds the whole serial, ticked rows and unticked ones alike — instead of the canonical order being re-seeded on every open, which made a drag look as if it had been forgotten (the drag already rewrote `bottom_nav_tabs`, so the bar changed while the dropdown did not). An empty or partial serial falls back to the canonical order for every screen it does not name, so an older install and a screen added by a later release both stay correct. `bottom_nav_tabs` remains the bar's own order: a drag writes both, so the two can never disagree. Side Navigation Options still shows the canonical order, since only the bottom bar has an order to reorder.
- **Settings cannot be hidden from Side Navigation** (0.0.181): the drawer's Settings item is `removable: false`, so a stale `side_nav_options` value written by an older build can never hide the way back, and the screen writes only the eight toggleable keys.
- **The landing page takes effect at launch:** the router provider awaits the settings row and uses `AppRoutes.landingPageRoute(defaultLandingPage)` as the initial location, keeping Daily Cause List if settings cannot be read. The bar itself renders every stored tab and scrolls horizontally above four.
- **The app ignores the phone's own font-size setting** (user-requested). The Font Size stepper (`font_size_step`, −2..+6) is the only control that changes the app's text: `FontSizeScope` at the app root replaces the inherited `TextScaler` with `TextScaler.noScaling` before adding the step, so a device set to an extreme scale can no longer clip labels or break layouts. Recorded here because the Font Size section itself is not in the plan.
