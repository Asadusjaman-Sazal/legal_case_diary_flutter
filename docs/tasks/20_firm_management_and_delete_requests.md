# Task 20 — Firm Management & Delete-Request Workflow

> **Plan references:** Sync Plan §1 (Account Mode Detection, Associate Deletion Policy, Online-Only Firm Administration), Database Schema (`firms`, `firm_members`, `firm_invites`, `delete_requests` + notes), Folder & File Structure (`manage_associates_screen.dart` [Design-deferred]) in `docs/implementation_plan.md`.
> **Goal:** The Manage Associates experience (firm creation, invites, permission toggles), permission freshness/rollback behavior, and the full offline-capable delete-request workflow with hardened review.
> **Rules:** Follow the Universal Working Rules in `00_INDEX.md`. Ask, don't guess. Firm administration is **online-only**; case-data operations (including delete requests) remain offline-capable.
> **Firm failures are the firm domain's own (error-log follow-up).** A firm RPC fails for reasons a sign-in never can, so this task no longer borrows `AuthFailure`: `FirmFailureKind`/`FirmFailure`/`mapFirmFailure` in `firm_repository.dart` classify what a call threw — network, server, unauthorized, too many attempts, unavailable, invalid invite code, already a member, owner offline, premium required, unknown — and `firmErrorText`/`failureText` in `auth_widgets.dart` are the one place a screen asks for the sentence. The three kinds the auth wording would misdescribe (server, unauthorized, unavailable) have firm sentences of their own; no connection, too many attempts, the premium gate and the owner being offline stay shared. Every failure the screen catches is recorded (`firm.action`, `firm.members`, `firm.invites`) and a firm failure is logged as `FirmFailure(server)`, never under an auth failure's name. The roster read is recorded in the provider, not in the screen's build, and an unchanged repeat collapses into one line — Riverpod retries a failed provider, and a report wants the fault rather than the retry count.

## Phase 1 — Individual → Firm Transition & Manage Associates Screen

1. **Firm creation trigger:** the moment the main user adds their first associate via `Settings > Accounts & Profile > Manage Associates`, the system creates a `firms` record, sets the main user's `role` to `'owner'`, links both profiles to the new `firm_id`, and transitions the account to Firm mode. **What creation shares (user ruling, 0.0.520):** every ledger row the owner authored while firm-less becomes the chamber's — cases, case histories, notes, case references, the customised reference rows and pending delete requests, **tombstones included** — stamped with the new `firm_id`, with `version` bumped and `server_updated_at` refreshed so each device converges by pulling. Implement this as an online-only server operation (RPC or guarded multi-statement call — ask the user if they prefer an RPC; RLS-privileged multi-row writes suggest one).
2. **Premium gate:** Firm mode requires an **active premium subscription** (Resolved Clarifications). Block adding the first associate on a free entitlement and route to the Paywall (Task 21). **As built (0.0.384):** the *entry* is gated, not only the action — the Accounts & Profile menu offers Manage Associates to a **premium individual** and to a firm owner **whatever their plan** (a lapsed owner keeps the firm and the server still lets them manage its roster; only *creating* a firm is refused), and to nobody else. **(Firm-mode ruling: creation needs the Firm tier or above)** — Pro's seat cap is 0, so the entry follows the stored tier rather than a bare premium check, `ensure_firm`'s gate is re-pointed from `is_premium()` at the tier, and a Pro owner is told to upgrade; a lapsed owner who already holds a firm still keeps the entry and its roster. The screen itself keeps its free-account Paywall state for a deep link.
3. Build `manage_associates_screen.dart` — marked **[Design-deferred]** in the plan, so there is no mockup: propose a layout following the Justice Ledger design system and **confirm with the user before building**. Required contents: associate list (name, role), per-associate permission toggles, invite generation entry point, and remove-associate action.
4. **Offline state:** all firm-admin screens show "Connect to the internet to manage your firm" when offline.

**Phase 1 completion:** Run `flutter analyze`, fix all errors. Update `docs/version_history.md` (new version entry + `## Current Version`).

## Phase 2 — Invites & Permission Management

1. Wire the invite primitives from Task 17 Phase 5 into Manage Associates: generate a code (plaintext shown once, copy-to-clipboard/share), list outstanding unused invites, and revoke unused invites.
2. **Permission toggles:** owner edits `can_add`, `can_edit`, `can_delete` (and role `associate`/`viewer`) per member — online-only writes to `firm_members` under owner-only RLS.
3. **Permission freshness (client side):** refresh `firm_members` on launch, resume, reconnect, and before every online permission-sensitive action; store `permissions_synced_at`. The local cache is advisory — `push_changes` is always authoritative.
4. **Provisional offline actions & rollback:** offline, authorized-looking case operations proceed **provisionally** (queue entries retain the `pre_mutation_payload` snapshot — Task 05/18 plumbing). If the server rejects because permissions changed: restore the authoritative server row (or the pre-mutation snapshot until the pull completes), resolve/remove the rejected queue entry, refresh permissions, and show *"Your firm permissions changed; this pending action was not applied."* Destructive provisional actions must be **visibly marked pending** in the UI.
5. **Removing an associate:** an owner-only online server operation immediately revokes membership, sessions, Realtime topic access, and future app access. Preserve authored records and immutable audit attribution without reassignment. Reject and never merge that member's queued mutations; on the removed device's next connectivity, discard/roll back pending local mutations, force logout, and securely erase all app data. Broadcast membership revocation so connected devices enforce removal immediately.

**Phase 2 completion:** `flutter analyze` clean. Update `docs/version_history.md`.

## Phase 3 — Delete Requests: Creation (Associate Side, Offline-Capable)

1. When an associate **without `can_delete`** attempts to delete a case, note, or reference, create a `delete_requests` row instead of deleting: `entity_type`, `entity_id`, `entity_snapshot` (JSON snapshot at request time), `target_base_version` (target version observed), `requested_by`, `status = 'pending'`.
2. Queue it through `sync_queue` with `entity_type = 'delete_request'` — fully **offline-capable**. Show the toast: *"Deletion request sent to Admin/Owner."*
3. The requester can edit/cancel their **own pending** request (RLS permits requester updates while pending).
4. Localized strings in `app_translations.dart`.

**Phase 3 completion:** `flutter analyze` clean. Update `docs/version_history.md`.

## Phase 4 — Delete Requests: Review (Approver Side)

1. **Notification surface:** pending delete requests appear as a notification/badge in the Settings dashboard (and optionally Manage Associates — confirm placement with the user) for all firm members with `can_delete = true`.
2. Review screen: tapping shows the `entity_snapshot` of the item plus requester and date; actions are **Approve** and **Reject** (with optional `review_note`, e.g., rejection reason). Reviewers may stage decisions offline; the server remains authoritative.
3. **Hardened approval semantics** (server side — extend `push_changes`/a dedicated RPC per the `delete_requests` schema note):
   - Approval submits both the request `base_version` and `target_base_version`, locks request and target, and proceeds only when the request is still pending **and the target is unchanged**.
   - If the target changed: return `target_conflict` with the current snapshot/version, set/show `status = 'stale_review_required'`, and require the reviewer to inspect and **reconfirm** — an old snapshot never authorizes deletion of materially changed data.
   - If the target is already soft-deleted: return `already_resolved` with tombstone metadata and retain the request as audit history.
   - Successful approval **atomically** tombstones the target (with server-side cascade for case children), resolves the request, records reviewer + server time, and produces idempotent receipts.
4. **Reject** keeps the record, sets `status = 'rejected'`, and notifies the requester (badge/toast on their next sync).
5. `delete_requests` rows are never hard-deleted (audit trail; RLS has no DELETE policy).
6. The client never resolves later queue entries merely because a review completed.

**Phase 4 completion:** `flutter analyze` clean; delete-review tests pass (changed target → `target_conflict`/`stale_review_required`; reconfirmed current version deletes atomically; duplicate approvals return the same terminal receipt). Update `docs/version_history.md`.

## Firm mode membership rulings (user-ruled, plan record — nothing built)

> **Where this comes from.** The user's firm-mode rulings, recorded in `docs/implementation_plan.md` → *Resolved Design Clarifications* and written out in full, with the reasoning and the edge cases, in `docs/firm_mode_blueprint.md`.

- **Phase 2 item 2's permission defaults change.** A newly joined associate starts with `can_add = true` and `can_edit = true`, so the chamber's cases, notes and references are theirs to work on from the first day. **`can_delete` stays false**, because deletion runs through this task's delete-request flow — any member may raise a request, and the owner approves or rejects it. The owner may still narrow add or edit per member. This supersedes the shipped `join_firm` default of `can_edit = false` (`20260929102300_phase3_join_firm.sql`).
- **The shared chamber config is member-editable (user ruling — reversed).** Edit Court/Steps, case types and on-behalfs offer a member Add, Edit and Reorder exactly as they do the owner, because `AGENTS.md` rule 10 keeps those tables firm-shared and most owners do not touch cases themselves — their associates do, so an owner-only config queues the chamber's work behind its busiest person. The owner-only reading of the earlier draft is **withdrawn**. Three limits hold it: the built-in baseline (`is_custom = false`) is immutable for members and owner alike; a reference row a live case still names cannot be deleted (already refused on the device, and the server guard is owed); and a member's own `can_edit = false` switches their reference edits off with everything else. Member edits are attributed (`last_modified_by`) and a simultaneous edit of the same court is an ordinary conflict on the shared banner and rebase flow.
- **Phase 2 item 5's removal gains its ordering, its second half and its owner warning (user ruling).** The device erases itself, **without asking and without waiting for a tap**: on the next launch or connectivity it runs the **complete wipe scope** (`BackupRepository.wipeToFreshInstall`, the same scope a logout uses) **before any sync, pull or write runs**, discards its queued mutations instead of pushing them, cancels its scheduled case notifications, and force-signs out. There is **no confirmation step** — the earlier notice carrying an *Erase & sign out* button is withdrawn, because the erase is the chamber's decision rather than the phone-holder's — and what the member sees instead is an informational *your access ended* screen reporting what has been removed. Authored rows stay the firm's, with attribution preserved and never reassigned; afterwards the account holds no link to the firm and, its diary being empty, may join another chamber. **The honest limit, stated to the owner in the removal confirmation:** a device that never comes online again can only be erased the first time it is opened, so the confirmation says the associate's phone keeps a copy until it is next opened and is erased then on its own, advises having the associate **open the app once while the two of them are still together and connected**, says that a phone which will never be opened again can only be cleared by a factory reset or the platform's remote wipe, and reassures that the chamber's rows on the server are untouched and attributed. One more rule is stated rather than implied (audit): a removal deletes no `device_tokens` row (`remove_firm_member` touches none), so **a removal takes that device's push registration with it** as soon as the device is reachable again — and by ruling (0.0.520) the RPC does it itself: `remove_firm_member` deletes the member's `device_tokens` rows in the same transaction as the revocation, so no firm notification can be routed to a removed device even before its own erase runs. **It ships no earlier than the seat-empty refusal:** a self-erasing device is only safe once a new seat is guaranteed empty, and Task 17 holds that half.
- **The removal is not complete until the read policies are scoped, and a dissolve writes a scope owner (server change owed).** `cases_select_scoped`, `case_history_select_scoped`, `notes_select_scoped` and `case_references_select_scoped` read `user_id = auth.uid() or firm_id = current_firm_id()`, the six reference tables add the same author clause beside `is_custom = false`, and `conflict_log_select_own` has no membership condition. Because attribution is immutable, `user_id = auth.uid()` **alone** still selects every row a removed member wrote in the chamber they left, and the pull carries no firm filter of its own — so after the removal wipe, a fresh local database starting at the initial cursor sentinel pulls that chamber's rows back down the moment the account is premium again. `20260930210000_sync_can_write_firm_membership.sql` and `20260930220000_rls_firm_membership.sql` closed this for **writes** only, on the stated belief that "a caller with no firm already reads nothing from a firm row", which is true of the `firm_id` half and false of the `user_id` half standing beside it. Each of the **eleven ledger tables** (`cases`, `case_history`, `notes`, `case_references`, the six reference tables and `delete_requests`) must read `(user_id = auth.uid() and firm_id is null and scope_owner_id is null) or firm_id = current_firm_id() or scope_owner_id = auth.uid()` — `is_custom = false` kept for the reference tables' seeded rows, the condition copied with `requested_by` in `delete_requests`, and `conflict_log` given the **membership condition only** (`user_id = auth.uid() and (firm_id is null or firm_id is not distinct from current_firm_id())`) with **no** scope owner, because its rows are a device's own merge diagnostics rather than ledger rows. Consequence to hold: **dissolving** a chamber must null its rows' `firm_id` **and write the owner as their scope owner**, not merely clear `profiles.firm_id` — a bare null would hand every member-authored row back to its author and hide it from the owner, and `scope_owner_id` is a scope key rather than attribution, so `user_id`, `created_by` and `last_modified_by` are not rewritten.
- **Permissions are a real boundary now, not an interface rule (user ruling).** `cases`, `case_history`, `notes`, `case_references` and the six reference tables all allowed UPDATE to any firm member through `can_edit_firm()`, so `can_edit` and owner-only config were interface rules and a modified client could name its own permissions. The ruling is the delete-transition trigger's own shape: **one `BEFORE` trigger per table, `can_add` on INSERT and `can_edit` on UPDATE**, read from the caller's `firm_members` row for the caller and the row's firm. **Both halves are new work** (audit correction: an earlier draft of this entry called the INSERT half already enforced) — there is no `can_add_firm` helper beside `can_edit_firm` / `can_delete_firm`, and no INSERT path reads the flag today. With the shared config now member-editable, no owner-only guard over the six reference tables is needed, and per-member toggles are the only control: there is no firm-wide read-only switch.
- **Dissolution: the owner empties the roster first, then dissolves (user ruling).** The order is deliberate — every leaving member goes through the one removal path that already exists, so each device erases itself, each revocation is broadcast, and nothing of the chamber is left on a phone nobody agreed to abandon. The owner must remove every member, associates and viewers alike, until only his own seat is left; the dissolve action is unavailable while the roster holds anyone else and says how many are left rather than only refusing. Open invites are **retired** (`revoked = true`), so a code issued before the dissolve can never create a seat in a chamber that no longer exists, and the invite rows themselves leave with the `firms` row by cascade. The chamber's rows are **unscoped and given the owner as their scope owner** — every row carrying that `firm_id` has it set to null **and** `scope_owner_id` set to the owner's id — so he keeps a complete, ordinary, offline diary instead of losing the rows his members wrote; attribution is untouched and nothing is deleted, because he built the ledger. `conflict_log` is the one exception: a colleague's merge diagnostics are neither handed to him nor taken from their author. The `firms` row and the owner's `firm_members` row are removed, `profiles.role` returns to `individual` and `firm_id` is nulled, so the account is individual again and `delete_my_account()` is no longer refused; and the owner's **plan is untouched** — dissolving is not a cancellation, the subscription runs to its own expiry and now covers the individual diary. Dissolution is **not reversible by the app**: re-creating a chamber makes a new chamber with a new `firm_id`, and the rows must be shared into it the way any existing diary is at creation.
- **A member is offered no backup on the way out** — see Task 15's entry.
