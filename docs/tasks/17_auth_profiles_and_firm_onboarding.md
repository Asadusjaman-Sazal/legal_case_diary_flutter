## Phase 4 — Offline Session Handling

1. **Never gate local data on JWT validity:** Supabase access tokens expire in ~1 hour and refresh requires network. An offline lawyer must always reach their diary — local DB reads/writes work regardless of token state.
2. If a token refresh **ultimately fails while online** (revoked session, changed password): require re-login, but **never wipe local data while `sync_queue` has pending rows**. Route the re-login path through the branched logout flow (implemented fully in Task 19) so unsynced work is synced, exported, or explicitly discarded — never silently lost.
3. Distinguish "offline, token stale" (fully usable, sync paused) from "online, session invalid" (re-login required) in the auth state machine, with clear localized messaging. **"Session invalid" has two causes, not one (follow-up):** a rejected refresh token (`SignOutReason.sessionExpired`) *and* a persisted session that cannot be parsed back into one at all (`SignOutReason.sessionMissing` — corruption, not rejection, raised before any request is made). Reading only the rejection left the second cause falling through to "offline, token stale", which by design shows nothing, so the diary opened as usual, the sync stayed dead for good, and the user had no prompt and no reason to ever sign in again. `authSessionNeedsSignIn` decides both; a deliberate sign-out is deliberately excluded.
4. Add tests: offline app open with expired token still reaches case data; online refresh failure triggers the re-login state without touching the local DB.

**Phase 4 completion:** `flutter analyze` clean; offline auth manual test (login → airplane mode → restart → data accessible). Update `docs/version_history.md`.

## Firm mode onboarding rulings (user-ruled, plan record — nothing built)

> **Where this comes from.** The user's firm-mode rulings, recorded in `docs/implementation_plan.md` → *Resolved Design Clarifications* (the bullets *A Chamber Holds One Ledger* through *The Order Of Work For Firm Mode*) and written out in full, with the reasoning and the edge cases, in `docs/firm_mode_blueprint.md`. Nothing here is code: no screen, RPC or migration has been changed for it.

- **Phase 2 item 2's "Join Existing Firm" gains a refusal.** An account that already holds its own diary cannot take a chamber seat. *Its own diary* means non-deleted rows the account authored while it had no chamber — `firm_id IS NULL` **and no scope owner**, which is what stops a dissolved chamber's rows ever counting as anybody's own diary — cases, notes, case references, or a court category, case category, court, step, case type or on-behalf it added or edited. The refusal reads **"This account already has its own diary (N cases). An associate's diary must be empty — sign up again using a different account with Join Existing Firm, or export your diary and delete this account."** — the English source string, localized in both ARBs like every other refusal, and never silent: a refused join changes nothing and says why. *(A numbering note: this is **Task 17's own** Phase 2 item 2, not the blueprint's firm-mode phase of the same number — the refusal was built as the blueprint's firm-mode **Phase 3** (0.0.523), `supabase/migrations/20261015120000_firm_mode_join_gate.sql`. The three numbering schemes in play, and which one each citation means, are listed in `docs/tasks/20_firm_management_and_delete_requests.md` under *Firm mode membership rulings*.)*
- **Rows authored inside a chamber never block a later join.** They are the chamber's, not the account's own diary, even though they keep the author's `user_id`. So the account of a removed member — whose diary is empty by then — may join another chamber with the same account (Task 20's removal item).
- **Joining a lapsed chamber is deliberately allowed.** Phase 5's invite redemption carries no entitlement gate today and keeps none: if the owner's plan has lapsed past the 48-hour grace window the join still succeeds, because there is nothing to merge (the seat is empty) and the member simply works local-only until the owner renews, under the plan's existing associate banner. Creation is the gate, not joining: **a chamber needs the Firm tier or above** (user ruling), so `ensure_firm`'s gate reads the stored tier rather than the derived premium answer it reads today (`is_premium()` in `20260930180000_ensure_firm_premium_gate.sql`, so the replacement is owed) and a Pro caller is refused with the reason, instead of being allowed to build a chamber whose seat cap of 0 makes every invitation fail.
- **The seat cap binds new joins (user ruling).** `join_firm` reads the chamber's stored tier (`firms.tier` — Pro 0, Firm 5, Firm Plus 20) and refuses a join that would exceed the cap, naming the cap and how many seats are in use; the shipped `join_firm` inserts a membership with **no seat check of any kind**. Nobody is ever auto-removed by a billing change: the cap binds new joins only and the owner is told to trim the roster.
- **The invite-code fumble is fixed (ruled).** `join_firm` consumes the code when the redeemer is already a member of that firm; the migration calls that deliberate (*"a retry by someone already in the firm still consumes the code rather than leaving it redeemable for a stranger"*), and the cost is that a member who fumbles their own redemption burns the owner's code. The rule becomes: the redemption still returns `already_member`, so the member is told the truth rather than an error; the code is **retired as revoked** (never as `used_by`), so it is dead for a stranger while the owner's list reads *retired* rather than *used by [member]* and the owner is not misled into thinking a colleague joined; and the **client never offers the invite field to an account that already has a firm** — the Join Existing Firm path is not shown to a signed-in member, which is the cheap half of the fix and the one that stops most of these fumbles before they happen. Recorded in full in `docs/firm_mode_blueprint.md` §2.5.
- **A dependency to hold.** The `firm_id IS NULL` definition above is only sound once a member can no longer **read** rows they authored in a chamber they have left — which is not true on the server today. See Task 16's read-scoping entry and `docs/firm_mode_blueprint.md` §4.3.

## The Email Box's Clear Cross And Domain Window (0.0.608, user request)

Both auth cards' address boxes — Login's **Email** and Sign Up's **Email Address** — became one shared `AuthEmailField` in `auth_widgets.dart`, built on `AuthTextField` so their label, placeholder, fill, validation and helper are untouched. Two things sit on top of it.

**The clear cross.** An `Icons.close` in the box's trailing slot, shown only while the box holds text (a cross over an empty box is a button with nothing to do), which empties the controller and **unfocuses** the field, so the keyboard closes with it. Its accessible name is the new ARB key **`auth_clearEmail`** ("Clear Email" / "ইমেইল মুছুন") in both languages.

**The domain window.** `@gmail.com`, `@yahoo.com`, `@hotmail.com`, `@outlook.com`, `@protonmail.com`, `@proton.me` — `emailDomainSuggestions`, in that order — offered under the box once the box is focused and holds **at least one letter**. Before an `@` the whole list is offered; after one it narrows to the domains still starting with what was typed, so **`@g` leaves `@gmail.com`**; a domain typed whole offers nothing, which is also what closes the window after a choice. A tapped domain is put on the address as *the typed name + the domain*, with **no space**, and whatever was typed after the `@` is **replaced**, so `john@g` + `@gmail.com` is `john@gmail.com` and one address cannot collect two domains. The field keeps the focus and the keyboard, because a domain is a step in typing rather than the end of it.

**How it behaves.** It stays up while the user works in the box and closes on an **outside tap**, on an **emptied box**, and once a whole domain is in place; typing again — or coming back to the box — brings it back, so a dismissal is a pause, not a setting. **(0.0.609, user request)** An outside **tap** is decided on the finger lifting without travelling past the touch slop: a press that becomes a scroll of the page (or a long hold that scrolls) keeps the window up, and because the window is anchored to the box it stays with it as the page moves. It is drawn in an **`OverlayPortal`**, not pushed as a route: a route would take the focus and the keyboard with it, and the window has to be tappable while the keyboard is up. The box and the window share one **tap-region group** (the field's `groupId` is forwarded by `AuthTextField` along with an optional `focusNode`), so a tap on a domain is not a tap outside the field and the keyboard stays. **(0.0.610, user request)** The window does not scroll itself: a vertical drag that starts anywhere on it is passed to the enclosing page through `ScrollPosition.pointerScroll`, so holding the window and moving the finger scrolls the screen, and the window keeps following the box; a drag end re-measures it so it cannot keep a height that now reaches under the keyboard.

**Its shape follows the app's pop-overs.** The same rounded window the account popover draws — `AppColors.surfaceContainerLowest`, 16 px corners, elevation 8 and the `AppColors.outlineVariant` hairline — hung **4 px under the field at the field's own width**. **(0.0.609, user request)** It now **always hangs below** the box: when the keyboard leaves less room below than the list needs, the enclosing page is scrolled up by the shortfall (clamped to what the page can scroll) instead of flipping the list above the field, so the window is never above the box and never pushed under the keyboard; if the page still cannot give enough room, the window scrolls internally. The window measures the floor from the raw view (`MediaQueryData.fromView`), because the Scaffold body has the keyboard inset removed from its own `MediaQuery` while the overlay does not. Each row reads as the **whole address the tap would produce** — `john@gmail.com`, not `@gmail.com` — using what is typed before the `@`. The overlay lays its children out at the screen's size, so the follower is wrapped in an `Align` to be sized to the window itself, and `AuthTextField`'s column now takes its own height (`MainAxisSize.min`) rather than the page's, which is the height the window is measured against.

**Proof.** New `test/features/auth_email_field_test.dart` (10 cases): the cross appears with text and empties the box and the keyboard; one letter offers the six domains in the written order; a number alone offers nothing; `@g` and `@p` narrow the list; a chosen domain is attached with no space and closes the list; a half-typed domain is replaced rather than doubled; an outside tap closes it and a keystroke brings it back; a tap inside the window is not an outside tap; emptying the box by hand closes it; and it hangs under the box at the box's width in the pop-over's own shape. `auth_login_test.dart` and `auth_signup_test.dart` each gained one assertion that their address box is this widget. No mockup change: both drawings show the resting form — an empty box, no keyboard — so neither the cross nor the window is a state they can draw.
