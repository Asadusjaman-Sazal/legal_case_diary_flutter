## Phase 1 — All Cases Screen

1. Body designed from `allCases\code.html`; shell from `cases_screen_modal.dart`.
2. Primary data source of the app: every case added via the FAB from any case page lands here.
3. **Sorting:** first-come-first-served serial order (first case = serial 1, next = 2, …).
4. **KPI summary:** total Active and Disposed counts at top (per mockup).
5. **Filters:** by Court Name (cases of a selected court category/specific court) and Chronology (newest/oldest first).
6. **Case card lines (exact):**
   - L1: left `case_type` & `case_number` | right On Behalf label
   - L2: `petitioner` Vs `respondent`, using the full available Case Card content width while preserving the existing left inset; the L1 On Behalf label must not consume L2's horizontal space
   - L3: Name of the Court, followed by the `honorable_judges` value (Name of Honorable Judges') when the case is filed in an Appellate or High Court Division court
   - L4: left Next Date (`DD/MM/YYYY`, with Today/Tomorrow rule) | right `last_step` (for lower-court cases) or `result` (for AD/HCD cases, which have no `last_step`)
   - L5: Phone, Message, Update buttons (Update opens the Task 07 Phase 3 pop-up)
7. Card tap → Case Detail screen (Task 10).

## Phase 5 — Disposed Cases Screen

1. Body from `disposedCases\code.html`. **No Add Case FAB on this screen** (a disposed case is not created here). The mockup's bottom-right FAB is a **Help FAB** (`help_outline` icon) — see item 5.
2. **Source of truth:** a sorted-out subset of the All Cases dataset.
3. Filter: `last_step` in the disposed-step set from `pre_seeded_data.dart` **or** an AD/HCD `result` containing a configured disposal term (Plan §6 — AD/HCD cases have no `last_step`, so Result is the only disposal signal for them). Sorted by `next_date` descending (latest disposed on top). Do **not** build the mockup's `All Disposed | Settled | Dismissed | Disposed` filter-chip row (explicitly out of scope).
4. **Card layout — match `disposedCases\code.html` exactly (this card is structurally different from the other list cards; do not reuse the standard list card):**
   - **Outcome chip:** a small rounded, tinted status chip above the case number showing the disposal outcome (mockup examples: `SETTLED` green-tinted, `DISMISSED` red/error-tinted). Derived from `last_step` (or AD/HCD `result`); tint by outcome family.
   - **Top-right block:** a `Disposed:` label with the `next_date` (the date the case was disposed) directly beneath it.
   - **Case number:** `case_type` & `case_number` in the case-number style, beneath the chip.
   - **Parties:** `petitioner` vs `respondent` in title style.
   - **Final result / Note box:** `notes_results` shown inside the mockup's styled quote box — italic text with a left accent border (`border-l-4`), rounded, on a subtle container fill.
   - **Case History timeline:** an uppercase `Case History` header, then the **last two** `case_history` entries rendered as a vertical timeline (left rail with ring dots; the latest/top entry emphasized in the secondary color and bold; each entry shows its date and description).
   - **No Phone/Message/Update action row** on this card (unlike All/Active/Upcoming/Overdue).
5. **Help FAB + Guidelines modal (per mockup):** a bottom-right `help_outline` FAB opens a "How to set a case as disposed?" modal explaining that choosing a disposal step while updating a case's date moves it here, that the case remains in the All Cases list, and listing the **Disposed Keywords** as chips (আপোষ মিমাংসা, প্রত্যাহার, খারিজ, নিষ্পত্তি, ২৪৮ ধারায় প্রত্যাহার, সাজা, রিমান্ডে প্রেরণ (R), নথিজাত, অব্যহতি, পদক্ষেপ নেওয়ার প্রয়োজন নেই, খালাস), with a "Got it" dismiss button. No `BackdropFilter` — use a plain scrim per the plan's performance rule.

## Phase 6 — Case List Extended View (0.0.203; header-and-column table in 0.0.204; per-screen choice and column refinements in 0.0.205; per-screen columns and the folded date cell in 0.0.206; Step/Result column and pinned court headings in 0.0.207; Overdue Dates' Step/Result column restored and foldable court headings in 0.0.208, user-requested)

The header's compact ↔ expanded toggle existed in `cases_screen_modal.dart` but was never wired, and `case_list_display_mode` was stored without a consumer. Both now exist, for the six case-list screens only (**not** Notes or Case Reference, which share the shell but have no case list — the toggle renders only when a host wires it).

1. **A per-screen choice with a global default (0.0.205, user-requested).** Each screen stores its own mode as an entry in `case_list_display_modes` (screen id → `compact` / `expanded`) inside `view_settings_json`, keyed by the screen's bottom-navigation key (`CaseListScreenId` in `case_list_view_mode.dart`); the header toggle writes only that screen's entry, so All Cases can show the table while Daily Cause List stays a card list, and the choice survives a restart. The existing global `case_list_display_mode` inside `user_preferences` is kept as the default for every screen the user has not switched — Settings → View Settings → Case List Display still reads and writes it — and an explicit per-screen entry overrides it. No new column, no ARB change (both toggle tooltips already existed).
2. **Reads vs writes.** Screens read it through `core/providers/settings_providers.dart` (`userSettingsStreamProvider`, the live Drift row) and write through `setCaseListViewMode` in `features/cases/presentation/case_list_view_mode.dart`, which reads the whole row before saving (so no other preference can be lost while the ViewModel state is loading) and then invalidates `settingsViewModelProvider` — View Settings renders that ViewModel, and without the invalidation it would keep showing the mode the app started with. Renders must come from the stream; the ViewModel reports `loading` between a write and its refresh, and a nullable state would flash the compact list mid-toggle.
3. **The table — `shared/widgets/case_table_row.dart` (0.0.204; column and content refinements in 0.0.205 and 0.0.206).** The extended view is a spreadsheet: **one header row** naming every column once (`CaseTableHeader`, its labels **middle-aligned**), then one row per case whose cells are values only — no per-cell labels. The full column order, left to right, is **Serial → Update → Date → Name of Court → Case Type → Case Number → Petitioner → Respondent → On Behalf → Step → Note** (0.0.205 moved the date column to just before Name of Court), but the list is **per screen** since 0.0.206: `CaseTableView`, `CaseTableHeader` and `CaseTableRow` take a `columns` list built through `caseTableColumns(exclude: ...)`, so the three grouped screens (Overdue Dates, Daily Cause List, Upcoming Cases) **omit Name of Court** — the group heading already names the court — while every screen keeps its own Step/Result column — Overdue Dates folded it away in 0.0.206 and 0.0.208 restored it (item 8). The date column is named per screen for itself: "Next Date" on All Cases / Active / Upcoming / Daily Cause List, "Previous Date" on Overdue Dates, "Disposed" on Disposed Cases. The **Step column is labelled "Step/Result"** since 0.0.207 (composed from the existing `caseCard_lastStep` and `addEditCaseSheet_result` strings) and it **carries an AD/HCD case's free-text Result**: higher courts have no step dropdown, so the result is the only value in that slot, and it renders in the step's place — or stacked beneath the step, through the same `subText` slot, when a case somehow holds both. The header label composition means no ARB key was added. Every cell is a single line (`maxLines: 1`, `softWrap: false`, ellipsis) — a value too long for its column ellipsises and the user widens the column to read it — and the one two-line cell follows the same rule line by line. Every data cell uses the Name of Court font and size (`AppTypography.bodyMd`) so the row reads as one grid; only the colour carries meaning (muted serial, red overdue date). The **Case Type column shows the case type only** — the free-text title/section is no longer appended (0.0.205) — and the **case number is plain black** (`onSurface`), not the compact card's link blue. The row keeps the card's chrome (white surface, `cardBorder` outline, right-rounded `cardRadius` corners, red 4 px strip on overdue rows) and drops the compact card's phone and message actions, which stay on the card and the case detail screen (user-approved). Where the court column is present, the judges' name is appended to it, joined with `·`.
4. **`enum CaseTableColumn` is the column contract.** Each value's `name` is its stable id in the stored width map, so the enum may be reordered but never renamed without a data migration; `caseTableColumnOrder`, `_defaultWidths`, `_minWidths` (48–96 px floors), `caseTableMaxColumnWidth` (640 px) and `resolveCaseTableWidths` (ignores unknown ids, clamps every value) live beside it.
5. **`CaseTableView` owns the sizes and the scroll — `features/cases/presentation/case_table_view.dart`.** It renders the header, wraps header + body in one horizontal `SingleChildScrollView`, and lays both out at `caseTableMinimumWidth(columns, widths)` (the columns the screen shows + inter-column rules + the fixed chrome: 2 px border, 4 px strip lane, 12 px gutter either side, 16 px screen margin) so a narrow phone scrolls the table sideways instead of squeezing columns. It reads the stored widths once when the screen opens, updates them live as a header rule is dragged, and stores them when the drag ends — `case_table_column_widths` in `view_settings_json` (no schema change), written through `setCaseTableColumnWidths` in `case_list_view_mode.dart` with the same read-modify-write and View Settings invalidation as the mode. The 4 px strip lane is reserved by the header and **every** row — only overdue rows paint it — which is what keeps the header's cells exactly over the data cells; a test asserts that column by column.
6. **Serial numbers.** Every screen numbers its rows, because the header row gives all of them a Serial column. The number is the screen's own running order over what it is showing — `index + 1` on the flat lists (All Cases, Active, Disposed; a filter or Newest-First renumbers from 1), and a serial map built in the same order the groups render on the grouped screens (Daily Cause List, Upcoming Cases, Overdue Dates). It is rendered with `AppDateUtils.formatDigits(serial, l.localeName)` so বাংলা shows ১. Grouped screens keep their date/court sub-headings, shown *below* the header row, and since 0.0.206 that heading replaces the court column entirely; both modes keep the overdue red strip on Overdue Dates.
7. **Empty states, search, sync, pull-to-refresh and the FABs are untouched** in either mode, and each screen's card and row are built in the same file (`_buildCaseCard` next to `_buildCaseRow`) so the two views cannot drift apart unnoticed.
8. **Overdue Dates' date column (0.0.206; folded cell removed in 0.0.208).** 0.0.206 dropped this screen's Step column and folded the step into a two-line "Previous Date & Step" cell; 0.0.208 undid that at the user's request, so the Step/Result column is back on this screen — directly before Note, as on every other screen — and the date cell is the red previous date alone. `CaseTableRow.dateShowsStep`, the `subStyle` hook it needed and the composed header label went with it, so the step is never shown twice, the date column is named from the existing `caseCard_previousDate` string, and an overdue AD/HCD case shows its result in its own Step/Result cell exactly like every other screen.

9. **Pinned court headings on the grouped screens (0.0.207).** Overdue Dates, Daily Cause List and Upcoming Cases build their extended body as a `CustomScrollView` of `CaseTableGroup`s (in `case_table_view.dart`) instead of one `ListView` item per group. Each group is one `SliverMainAxisGroup` holding a **pinned** `SliverPersistentHeader` for the court heading plus the court's rows, so the heading **holds the top of the list for as long as that court's cases are on screen** and is pushed out as the next court's heading arrives — a court with several cases keeps its name visible the whole time. The grouping is load-bearing, not decoration: plain consecutive pinned headers in one scroll view accumulate at the top of the viewport (each is laid out at the pinned extent of the ones before it) and would all stay on screen at once. The pinned band paints the screen background across the table's full width so the rows slide underneath it, its heading is inset to the same gutter the rows use, and `caseTableGroupHeaderHeight` sizes it from the heading's own line height, scaled with the user's text size. Upcoming Cases keeps its date heading above each day's groups as an ordinary (non-pinned) row. The compact card list on all three screens drew plain headings until 0.0.210, when it was given the same pinned, foldable groups (item 11).

10. **The court headings fold (0.0.208, user-requested).** Tapping a heading hides that court's rows and tapping it again brings them back, and the band carries a chevron that points **down** while the court's cases are hidden and up while they are showing — the down arrow is the indication that something is hidden under the heading. A court **opens expanded** (flipped in 0.0.209), so its cases are there to read on arrival and the down chevron is the only thing that says a court has been folded away. The band is the whole tap target (not just the arrow), and the fold state lives in `_CaseTableGroupState`: it is per group, so folding one court leaves the others as they were, and a folded group contributes its heading sliver alone, which lets the next court's heading come straight up behind it. The heading stays pinned while its cases are open; nothing is pinned under a folded court because there is nothing below it to pin over.

11. **The compact card list gets the same headings (0.0.210, user-requested).** Overdue Dates, Daily Cause List and Upcoming Cases now build their **compact** body as a `CustomScrollView` of the same `CaseTableGroup`s, with the screen's `CaseCard`s as the group's cases (the group takes plain widgets, so the table hands it rows and the card list hands it cards — there is no second implementation of the pinning or the fold). The heading therefore pins and folds identically in both views: the band is the tap target, a folded court is the only one showing the down chevron, and every court opens expanded. The fold choice needs no new setting — both views read and write the same per-screen `case_table_collapsed_courts` entry, through a per-screen `toggleCourt` helper each of the three screens now shares between its two bodies — so a court folded in the card list opens folded in the table and survives a restart. The list keeps the gutters and spacing the old `ListView` had (the group's cases sliver insets and spaces by `AppSpacing.md`, and the list is topped and tailed by it), Overdue Dates and Upcoming Cases keep their `RefreshIndicator`, Daily Cause List's card list keeps the no-pull-to-refresh body it has always had, and Upcoming's date heading stays an ordinary row above each day's groups, now built by one `dateHeadingSliver` helper both of that screen's bodies share. **That Daily Cause List exception ended at 0.0.605 (user request):** its compact card list now carries the same `RefreshIndicator` as the other lists, and both of its views use `AlwaysScrollableScrollPhysics` so a day with a single hearing can still be pulled. The header sync button and the empty-state pull-to-sync are unchanged.

12. **Every case list's pull now runs the header's action (0.0.606, user request).** The pull on All, Active, Disposed, Upcoming, Overdue and Daily Cause List was reloading the local list only; each now calls `pullCaseListToSync(ref, _loadCases)`, the same forced sync plus reload the header button runs, and every compact `ListView` uses `AlwaysScrollableScrollPhysics` so a short list can still be pulled. Case Detail's pull does the same through `_load`. Notes and Case Reference keep their own `_onRefresh` (`retryNow` + provider invalidate) and now take the shared clamped pull configuration, so a short library is pullable without the cards moving under the finger.

### Empty-state messages (0.0.430, user request)

The five list screens no longer use their own heading as the empty state — a heading names the screen, not the state the user is in. Each screen passes its own message to the shared `CaseListEmptyState` (`case_search.dart`), one new ARB key per screen, English and Bengali in the same edit with `flutter gen-l10n` re-run:

1. **All Cases** — `allCasesScreen_empty` → *No case added yet. Tap + to add one.*
2. **Active Cases** — `activeCasesScreen_empty` → *No active case to show. Tap + to add one.*
3. **Overdue Dates** — `overdueDatesScreen_empty` → *No overdue case*
4. **Upcoming Cases** — `upcomingCasesScreen_empty` → *No upcoming case*
5. **Disposed Cases** — `disposedCasesScreen_empty` → *No disposed case*

**The titles are untouched.** The messages are new keys rather than renamed `*_title` values, because those titles are also each screen's header and its print title — renaming them was the defect an earlier working-tree edit introduced, when *No Active Case* and *No Cases in Upcoming Dates* became two screens' headings. **Daily Cause List is unchanged** — the request named the five others, and that screen already showed a real message (*No hearings scheduled for this date.*, `dailyCauseListScreen_noHearings`), which is the pattern the five now follow. A scoped search that hides every row still reads *No results found.* on all of them (`sharedDialogs_noResults`) — the empty message exists for the case where nothing is being filtered out. No mockup draws an empty list, so none was changed (rule 9). `test/features/case_list_search_test.dart` gained one case over all five screens (pumping each with no cases seeded and asserting its own message), which fails if any screen goes back to its title.

## Alignment Addendum (Implementation Plan Revision 2.4)

- Every list search is constrained to that screen's existing dataset/filter before applying the text query.
- Active count/listing excludes disposed-step cases; free-tier counts are not sourced from this active count.
- Overdue Last Updated: Part A shows a clear local/offline state. Part B shows latest successful server update for firm data plus explicit pending/error states; never invent a local associate-sync timestamp.
- Phone/message actions resolve the explicitly stored petitioner/respondent phone appropriate to the action target.
- Quick Update history is repository-owned and date-change-only.
- **Serial numbers (0.0.203; extended 0.0.204):** the extended view's serial is the screen's own visible running order, not a stable per-case ordinal — plan line 138's "first, second, third" describes the unfiltered list, and a filtered or Newest-First list is expected to renumber (user-approved). Since 0.0.204 the header row gives every screen a Serial column, so the grouped screens number their rows too, in render order.
