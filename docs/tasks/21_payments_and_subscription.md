## Phase 2 — Submission, Local Draft & Rate Limiting

1. **Local draft:** save the checkout form input to `SharedPreferences` on every keystroke. If submission fails or the user closes and reopens, pre-fill the form from the saved draft. Clear the draft only after a confirmed successful submission.
2. Submit to `payment_submissions` (status starts `pending`; `submitted_at` is server-assigned — the client never supplies it). On network failure show *"Submission failed. Tap Retry."* — the draft remains saved.
3. **Rate limiting UX:** perform a best-effort local check (3 submissions per 24h) purely as UX; the authoritative gate is the server `BEFORE INSERT` trigger (Task 16). Surface the trigger's rejection as *"You've reached today's submission limit. Please try again tomorrow."*
4. Show the user's submission history/status (pending/approved/rejected with `admin_notes`) — own rows only under RLS. Confirm placement (Checkout screen vs Manage Account) with the user.
5. Implement `payment_viewmodel.dart` controlling submission state + draft, per the folder structure.

**Phase 2 completion:** `flutter analyze` clean. Update `docs/version_history.md`.

## Phase 3 — Derived Premium Entitlement (Client)

1. Replace the Task 15 `SettingsRepository` entitlement stub with the real derivation: **`subscription_expiry + 48h grace > now()`** — computed, never read from `subscription_status` (display/analytics only).
2. **Firm inheritance:** for firm members, entitlement derives from `firms.subscription_expiry` (mirrored from the owner by the Task 16 trigger). When the owner lapses past grace, the derived check fails for every member on their next sync attempt.
3. Feed this single derivation to: the sync worker gate (Task 18), Firm-mode gating (Task 20 Phase 1), and the 50-case Add Case gate (Task 15 Phase 5 — call sites must not change).
4. **Clock caution:** the local check uses device time and is UX-only; RLS/RPC checks with database `now()` remain the security boundary. Apply the recorded clock-skew offset (Task 18 Phase 3) to reduce false banners.
5. **Lapsed-premium users keep everything:** expired premium never hides, blocks, or deletes existing cases; only *adding beyond 50* is gated on a free entitlement.

**Phase 3 completion:** `flutter analyze` clean; entitlement derivation unit tests pass (active, in-grace, lapsed, firm-inherited). Update `docs/version_history.md`.

## Phase 4 — Grace Period, Expiry Banners & Activation Detection

1. **48-hour grace period:** when `subscription_expiry` passes, sync stays fully active for 48h with a persistent, non-intrusive banner: *"Your subscription expired. Renew to avoid losing sync access."* If an admin approves a payment within the window, expiry extends seamlessly and the banner disappears.
2. **After grace ends:** sync is disabled immediately; the app falls back to local-only mode; no data is deleted. Banners:
   - Firm Owner: *"Your premium subscription has ended. Renew your subscription to restore sync."*
   - Associate: *"Your firm's premium subscription has ended. Contact your firm owner to renew."*
3. **Activation detection:** the app detects an approved payment via a Broadcast ping or a profile refresh on next launch/resume; on activation, trigger the **Initial Backlog Push** (Task 18 Phase 4) for first-time upgrades.
4. Reflect subscription state (plan, expiry date in `DD/MM/YYYY`, status) in `manage_account_screen.dart`.

**Phase 4 completion:** `flutter analyze` clean; payment submission & approval test per the Verification Plan passes end-to-end. Update `docs/version_history.md`.

## Firm-mode payment rulings (user-ruled, plan record — the ladder is applied and live)

> **Where this comes from.** The user's firm-mode rulings, recorded in `docs/implementation_plan.md` → *Resolved Design Clarifications* ("Pricing", "The Tier Ladder Is Settled, And The Tier Is Stored", "A Member May Not Buy A Personal Plan", "How A Subscription Is Sold") and written out in full in `docs/firm_mode_blueprint.md` §5.1, §5.3, §5.4 and §5.6.

- **The ladder is ten plans at flat prices, and the percentage-discount story is withdrawn.** **Pro** sells **1, 3, 6 and 12 months at ৳100 / ৳285 / ৳540 / ৳1,000** — its annual moves from the shipped ৳960 to **৳1,000**, a `plan_type` constant change and a migration rather than a code change — and **Firm** and **Firm Plus** sell **3, 6 and 12 months** (a chamber does not buy a month) at **৳855 / ৳1,620 / ৳3,000** and **৳1,710 / ৳3,240 / ৳6,000**. Each price is simply its price: **no struck-through full price, no saving badge and no discount percentage**, so `SubscriptionPlan.undiscountedAmount` / `discountPercent` and the badge they drive have no place in the rebuilt paywall. The tiers are Free (৳0 · 50 cases · strictly individual), Pro (1,000 cases · one account), Firm (2,500 cases · up to 5 associates), Firm Plus (6,000 cases · up to 20 associates) and Unlimited (by quotation). This supersedes the four-plan set and the ৳550/৳960 constants recorded above, and **there is no `payment_plans` table**: the ladder lives as `plan_type` keys plus the constants inside `approve_payment`, so one new plan touches four server places and is a migration.
- **The tier and its seats are stored, so this task's screens have a source.** `profiles.tier` / `firms.tier` are written by `approve_payment` at approval and **never cleared by expiry** (the column is the record of the last tier held), with `tier_pending` / `tier_pending_from` beside them for a mid-term downgrade, and the firm's copy moves only because `mirror_owner_subscription_to_firm()` is widened to cover the tier. **A downgrade waits for the period it was bought for** — the tier in force is never overwritten mid-term, and every reader takes the effective tier — while **a lapse falls back to the allowance of the tier last held** (Pro 100, Firm 500, Firm Plus 1,000) rather than to Free (Task 15's entry).
- **A member may not buy a personal plan, and their own expiry does not count while they hold a firm.** The app does not offer Subscription Plans to an account that holds a firm — **including the side menu's Current Plan row**, which also expands into the plans — and **the server refuses the submission itself**: `payment_submissions_insert_own` is `with check (user_id = auth.uid())` today, so refusing it is a **policy change** and not a client check. This matters because the state is reachable today: `profiles.subscription_expiry` is not cleared when someone joins, so an account that bought Pro and then joined with an empty diary keeps a live expiry, and the gate is currently *my own expiry **or** the firm's* — while the owner was lapsed, that member kept pushing. **While the account holds a firm, only the firm's expiry counts**, and paid time is preserved rather than destroyed: it is ignored in a chamber and applies again once they are individual. **Built (0.0.534)** in `20261017100000_firm_mode_member_no_plan.sql`, applied to the live project on 2026-10-17: `has_sync_entitlement` counts the chamber's expiry alone once `profiles.firm_id` is set, and `payment_submissions_insert_own` adds “no firm, or a firm the caller owns” to its check, so a member's insert is refused by the policy. **The owner is exempt** (user ruling 2026-10-17) — his purchase *is* the chamber's renewal, and the two entries this phase removes from a member are his only routes to it. On the client, `firmMemberProvider` is the one place "member, not owner" is decided: the Subscription screen and the side-menu plan row drop the plans entry, the paywall answers a member with a chamber notice instead of an offer, and Current Plan reads *Premium* rather than a plan bought before joining. Proven by `supabase/tests/firm_mode_member_no_plan_test.sql` (rolled back against the project) and the client widget tests.
- **Creating a chamber needs the Firm tier or above.** Pro's seat cap is 0, so `ensure_firm`'s gate moves from `is_premium()` to the stored tier and a Pro caller is refused with the reason rather than allowed to build a chamber nobody can be invited into. See Task 17's and Task 20's entries.
- **A seat cap binds new joins only.** Nobody is auto-removed by a billing change; the owner is told to trim the roster and the extra members keep working read-write until he acts.
- **Distribution is direct, not Google Play, for now.** The project's own APK, delivered by the in-app updater that already reads its own GitHub releases, stays the only channel until the product has been tested and feedback gathered, and Play is a later decision rather than a rejected one. Play requires **Play Billing** for an in-app digital subscription and forbids steering a user to another payment method, and Bangladesh is in no alternative-billing programme; a Play-distributed app also **may not update itself outside Google Play's update mechanism**. The two mechanisms this task is built around — the manual MFS flow and the self-updater — are therefore compliant only while the app is not on Play, and direct distribution keeps 100 % of the revenue instead of 85 %. That makes the updater's release naming, size verification, `FileProvider` grant and **release authenticity** critical infrastructure, and if Play is adopted later it becomes a **build flavour** that switches to Play Billing and drops the self-updater rather than a code change. **Built (0.0.541), the authenticity half and the install docs.** The mechanism is the plan's first option, **a signed release verified by the app**: inside the install handler, before the `FileProvider` lookup or any intent, `MainActivity.kt` reads the downloaded archive's signing certificate (`GET_SIGNING_CERTIFICATES` on API ≥ 28, the pre-28 `GET_SIGNATURES` below it — minSdk is 24), hashes it with SHA-256 and compares it with the certificate of **the app already installed**, which is the identity Android itself enforces at install; a mismatch, an unreadable archive or a missing certificate answers `error("unverified_signature")` and dispatches nothing at all. The anchor is the running app's own signature rather than a fingerprint pinned in the app, so no value is transcribed by hand and no future release can be broken by a keystore change no code would see; and the check sits in Kotlin because reading a certificate is a platform API and the check must be the same step that dispatches the intent, so an APK cannot change between being verified and being handed over. The handoff now returns a three-way `ApkInstallOutcome` (`handedOff` / `unsupported` / `unverified`) instead of a bool, because "this device cannot install an update" would be an untrue explanation of a release that failed its check; the flow maps the refusal to `UpdateFlowError.unverifiedRelease`, which reads one new ARB sentence in both languages (*This update could not be verified, so it was not installed.*), and a refusal leaves the stored offer standing instead of reporting the refused release as the version in hand. The docs half is `README.md`'s **Installing The App (Android)**: the download page (the project's GitHub releases page — the readme is the download page until a site exists, per the user's ruling), the publisher named as the repository's owner, the asset name **as GitHub actually stores it** (`Legal.Case.Diary.v<version>-ARM64.apk`, dots rather than the workflow's spaces), and the install steps that survive Android's unknown-sources prompt including the *Install unknown apps* permission and the older *Unknown sources* spelling, in **English and Bengali**. No migration and no SQL: this phase is client and docs only. Pinned by eight new cases in `test/features/update_install_test.dart` and `test/features/update_section_test.dart` (the channel's refusal, the flow's refusal state and retained offer, the sentence on the real Update screen, and the Kotlin halves read from source, including that the refusal precedes the URI and the intent).
