## Phase 1 — Versioned JSON Backup Format & Export Engine

1. Define the canonical backup envelope in a dedicated module (e.g., `core/utils/backup_format.dart`):
   - A top-level **`schema_version`** field (integer) in the JSON envelope — mandatory for forward compatibility.
   - App version, export timestamp (epoch ms), and a payload **checksum**.
   - Full data payload: a restorable snapshot of every portable app-state class: all domain rows and tombstones (`cases`, `case_history`, `notes`, `case_references`, `court_categories`, `courts`, `steps`, `case_types`, `on_behalfs`, `delete_requests`, `conflict_log`) including sync columns; all pending/blocked/conflicted `sync_queue` rows; per-user preferences and case-notification settings; pull-only profile/firm/member caches; composite cursors; seed migration ledger; sync/recovery metadata; and required local configuration. Include all custom and user-modified seed rows plus enough canonical seed/version information to reproduce the exact state.
2. Implement the export engine as a repository-level service so the **same code path** serves: manual "Backup to Local Storage", logout auto-export (Part B, Task 19), and the extended-offline safety archive (Part B, Task 19). This single-format rule comes straight from Sync Plan §5.
3. Record archive path, checksum, and completion state after every export.

## Phase 2 — Authenticated Encrypted Export

> Per §12.3.1 (revised): encryption is opt-in and off by default — a backup is sealed only when the user turns it on. Never place a *sealed* export in shared storage against the user's wish.

1. Seal a backup with an **authenticated format** (versioned header, KDF parameters, nonce, ciphertext, authentication tag, checksum) when encryption is on. See *Encryption is opt-in, off by default* below for the revised behaviour.
2. The encryption key derives from a **user recovery secret** (passphrase) or a platform-protected key — ask the user which UX they prefer for the manual backup flow (passphrase prompt vs. silent device-key) before implementing; the plan requires one of the two.
3. Never log or persist the recovery secret; redact all key material from any diagnostics.
4. Add security tests: round-trip an encrypted backup, verify decryption with the correct secret, and verify tampering with ciphertext/tag/checksum **fails closed** (per Verification Plan).

## Phase 3 — Restore / Import with Validation

1. Implement restore from a user-selected backup file:
   - Decrypt and authenticate first; on any tag/checksum failure, abort with a clear error and **never partially import**.
   - Validate the `schema_version` and run per-version upgrade adapters so **future schema changes never break old backups**. Unknown/newer versions are rejected with a clear message.
   - Import inside a single Drift transaction; on failure, roll back completely.
2. Define collision behavior: restoring into a non-empty database must ask the user (replace all vs. cancel). Do **not** silently merge — ask the user for the desired policy if the mockup doesn't define it.
3. Restored rows keep their original IDs and sync columns so a later premium upgrade (Part B) can push the restored data unchanged.
4. Add tests: full export → wipe → import round-trip preserving row counts, IDs, sync columns, and queue contents.

**Phase 3 completion:** `flutter analyze` clean; round-trip tests pass. Update `docs/version_history.md`.

## Excel Backup & Restore — deliberate deviation (0.0.263, user-requested)

> **This deviates from two things stated above and must be carried into Part B.** The plan's backup format is the versioned **JSON** envelope, and §12.3.1 as it stood then required every export to be authenticated-encrypted. A workbook the user opens in Excel cannot carry the app's AEAD container, so this feature is **plaintext by design**: an exception the user asked for and approved, not an oversight. The encrypted `.lcbak` JSON remains the canonical, complete backup.

- **Scope is four tables, not all twenty.** The workbook carries `cases`, `case_history`, `notes` and `case_references`, plus an `Info` sheet holding the format marker, `schema_version`, app version and export time. Courts, steps, case types, on-behalfs, court/case categories, preferences, caches, cursors, the queue and metadata are **not** in it, so a workbook is not a complete backup and is restored into a diary that already holds that reference data. The screen's Excel-format section says both of these plainly.
- **Restore is scoped to the file's own tables.** `BackupRepository.restoreSnapshot` now runs its collision check and its delete-all over **the tables the file carries**, in reverse FK order, instead of every portable table. A JSON backup carries all twenty, so its behaviour is unchanged and the plan's Replace-or-Cancel rule still holds; a workbook replaces only its four tables and leaves everything else untouched — which is what keeps a partial file from emptying a working diary's reference data. The same scoping runs the pre-replace question (`hasDataInTables`), so a workbook never asks about data it would not touch.
- **No spreadsheet package could be used.** `excel` pins `xml <7` and `pdf ^3.13.0` (Task 14) requires `xml ^7.0.1`, so the two can never coexist. The container is therefore hand-built OOXML on `archive` + `xml`, both of which were already resolved transitively through `pdf` and are now direct dependencies. Writing is string-built; reading also understands shared strings, so a workbook the user re-saved in Excel still restores.
- **The column list is derived, not written down.** Sheet headers come from the live Drift schema (`$columns` / `requiredDuringInsert`) via `BackupRepository.excelColumnSpecsFor`, so the export, the downloadable template and the reader cannot drift from the tables: adding a column to a table adds it to all three.
- **Sheet names are fixed English identifiers** (`Cases`, `Case History`, `Notes`, `Case References`, `Info`), deliberately **not localized**, so one workbook restores in either app language; the ARB explains the names in the user's own language instead.
- **Row rules.** A blank `id` is given a fresh UUID, which is what makes a hand-added row importable; any other blank in a NOT NULL column without a default is refused **naming the sheet and the spreadsheet row**, before any SQL runs. Rows import verbatim otherwise, keeping ids and all five sync columns, so a restored row can be pushed unchanged after a Part B upgrade.
- **Part B must mirror this.** The four tables are the synced domain tables, and the workbook carries their sync columns — so nothing about the workbook needs server-side change, but the plaintext-export exception must be recorded wherever server/backup policy is written, and `schema_version` in the `Info` sheet must be upgraded through the same `backupPayloadAdapters` chain as the JSON payload (it already is).

## Restore ownership gate — restore only your own backup (0.0.472, user-requested)

> **Requested by the user, Backup & Restore only.** Another account's backup could be restored into this device and then refused to sync (the rows it brought named somebody else); and the id check was to be relaxed **only** for a fresh Excel file that carries nobody's id — the downloaded sample the user typed their own cases into.

- **The envelope names no owner, so the rows do.** A backup carries `schema_version`, the app version and the export time and nothing about who made it, so ownership is read from the payload's own rows. New pure module `lib/core/backup/backup_ownership.dart` (no Flutter, no Drift, no file system): `BackupOwnerColumns` (a table's `user_id`/`requested_by`, its `firm_id`, and its attribution columns), `BackupOwnership {mine, ownerless, anotherAccount}`, `classifyBackupOwnership`, `stampRowOwnership` and `isOwnerIdValue`.
- **The columns come from the live schema, not a list.** `BackupRepository.backupOwnerColumns()` derives them per portable table from `$columns`, so a renamed or added column cannot leave the check blind; a table with neither `user_id` nor `requested_by` is **never consulted**, which is what keeps the pull-only caches (`firms.owner_id`, `profiles.id`, `firm_members`) out of the decision — they name accounts without holding authored data.
- **Three answers.** `mine` — every owned row names this device's identity (its bound account, or its pre-account placeholder) or a firm it belongs to; `ownerless` — **no row names an id at all**; `anotherAccount` — at least one row names an id that is neither, which is enough, because one unpushable row is what the user met as a sync failure.
- **Only a UUID can be an id.** `isOwnerIdValue` accepts a UUID shape and nothing else, so a blank cell, the template's `user_id`/`example-court-id` placeholders or a name typed by hand all count as "names nobody" — that, and not a table name or a file kind, is what makes the relaxation narrow rather than a hole. Every real identity is a UUID on both sides (a `Uuid().v4()` placeholder or an `auth.uid()`), so no id can be mistaken for text.
- **Where the gate runs.** `BackupRepository.checkRestorable(backup, ownerId:, firmId:)` is callable the moment a file is opened, and `restoreSnapshot` calls it **first — before the collision check and before the transaction**, so a refused file writes nothing and does not even hold a write lock. `restoreSnapshot` gained `ownerId` (required) and `firmId` (optional), and its result gained `ownership` and `stampedRows`. Rows are copied before they are stamped, so the payload the caller still holds is never mutated.
- **The screen.** `backup_restore_screen.dart` reads the identity and the firm **before its first await** (`localIdentityServiceProvider.getId()` and `accountProfileProvider.value?.firmId` — Riverpod 3 refuses a widget ref on the way out), calls `checkRestorable` immediately after opening the file and **before** the replace question, and maps `anotherAccount` to a new ARB key in both languages.
- **Stamping.** For an `ownerless` file, `stampRowOwnership` writes this device's identity into each row whose owner cell is not id-shaped, fills its `firm_id` only when this device has a firm, and follows the owner into the attribution columns (`last_modified_by`, `created_by`, `reviewed_by`) where those name nothing either. A row that already names somebody is left exactly as it was — its author, its firm scope and its attribution are not this device's to rewrite, and identity adoption (which runs at **sign-in**) is the flow that exists for the pre-account case.
- **Two deliberate limits, recorded rather than discovered.** Adopting a **firm colleague's** rows in a firm this device belongs to is accepted and keeps its authors, because a firm's rows are shared; and another device's **pre-account** backup is refused, because its placeholder is a different person as far as the server is concerned. The second is stricter than the old behaviour and is the price of never importing a row the server will not accept from this account.
- **Tests (new).** `test/core/backup_ownership_test.dart` — the pure classifier and stamper: mine / another account / ownerless, one foreign row out of many, a colleague inside the firm against a colleague of another firm, placeholder text and blanks, an unconsulted table, and stamping (ownerless row filled, individual device writes no firm, a colleague's row untouched). `test/features/backup_restore_repository_test.dart` — a run of **`restoring whose file it is`**: another account's real export refused with nothing written and nothing replaced, the same file accepted as its own author, a file naming nobody restored **and stamped** (`stampedRows`, and the note's `user_id` now this device's), the sample template accepted while a real export of the same diary is `mine`, and a colleague's firm rows accepted with their author intact. `test/features/backup_restore_screen_test.dart` — the refusal sentence with no replace question and the existing row untouched, and an ownerless file restored with both `user_id` and `last_modified_by` left as this device's identity.
- **Teeth (two, both proven and reverted).** With the `anotherAccount` throw disabled, the repository's refusal case and the screen's refusal case fail (0 widgets with the refusal sentence); with `stampRowOwnership` short-circuited to `false`, four cases fail (both stamping unit cases, the repository stamping case and the screen stamping case). Both source files were restored byte-for-byte (md5 verified).
- **No mockup change (rule 9).** No screen body moved; only a new failure message exists behind an existing control, so no mockup is owed.
- **Part B note.** The gate mirrors what the server enforces anyway (a row must name the pushing account or its firm), so a Part B pull that finds foreign rows remains a separate, server-side concern; this phase only stops the client from importing what it could not push.

## Restore guard for synced subscribed accounts (0.0.475, user-requested)

> **Requested by the user, Backup & Restore only.** A premium user who has synced at least one item to the cloud must not restore an offline save over the diary — it would contaminate the cloud copy. Tapping **Restore from Backup** in that state opens a pop-over with the restriction sentence and two centred buttons: **Cancel**, and **Delete Local & Cloud Data**, which runs exactly the Manage Account flow (its tick list, its type-`delete my data` screen, its toasts) and then continues the restore on the emptied diary. **(0.0.476)** The two buttons are stacked one after another — Delete first, Cancel beneath — full-width, equal-sized (48 px) and middle aligned, rather than side by side.

- **Three decisions taken with the user first (rule 1).** (1) "Synced" is the durable last-successful-sync stamp (`syncLastSuccessProvider`'s source), not a new pushed-item counter — no sync-engine change. (2) A completed wipe **auto-continues** into the restore; a refusal, cancellation or failure restores nothing. (3) The fence opens only while the diary holds the user's own data (`BackupRepository.hasUserAuthoredData`) — an empty diary restores straight through, so the prescribed wipe can never dead-end.
- **Where the gate runs.** At the top of `_restoreFromBackup`, before the folder scan or picker: premium comes from `resolvePremiumAccess(db, identity)` — the derivation every gate uses, called directly because `premiumAccessProvider` answers through the auth session chain this screen otherwise only peeks at — plus the sync stamp and the authored-data check, all read before the first dialog await. Everyone else (free, never synced, nothing authored) restores exactly as before.
- **Shared flow, not a second one.** The tick-list/typed-screen/service/toast sequence is extracted to `runDataDeletionFlow` (`features/accounts_and_profile/presentation/data_deletion_flow.dart`), and Manage Account's `_deleteData` now delegates to it — same refusals, same strings, same outcomes, proved by its untouched 27-case suites. - **Tests (4 new).** `backup_restore_screen_test.dart` — fenced off before the picker (warning, centred Cancel + red destructive action, picker never opened, row untouched), the wipe deleting first (tombstone before the replace question) then the restore completing on it, a never-synced premium diary and an empty synced one both restoring straight through. - **The automatic backup is replaced, not accumulated (0.0.494, user-requested).** The daily job wrote a fresh file every run, so `Download/LegalCaseDiary` grew without limit. It now writes `AutomaticBackup_<dd-mm-yy_hh-mm-ssam/pm>.lcbak` — the stamp kept, so the file still says when it was made — and then deletes the previous automatic files in that folder, leaving exactly one. ## Firm mode backup rulings (user-ruled, plan record — nothing built)

> **Where this comes from.** The user's firm-mode rulings, recorded in `docs/implementation_plan.md` → *Resolved Design Clarifications* and written out in full in `docs/firm_mode_blueprint.md` §6.

- **Restore is barred whenever firm mode is on, the owner included.** A backup file is a photograph of the ledger at one moment, and putting it back over a chamber re-introduces rows other members may have changed or deleted since. This is a **stricter fence than the 0.0.475 synced-subscribed-account guard** and sits on top of it: firm mode does not offer the Delete Local & Cloud Data route as a way through to a restore.
- **The one exception is a completely empty device** — a fresh install, or the state a wipe leaves. There is nothing to overwrite, and the full pull a fresh install performs brings the chamber's rows and every tombstone the server still holds over the restored ones, so a deletion from within the last 365 days corrects a stale restored row. A server row already purged past that window cannot, which is the accepted ceiling of the exception.
- **What the restore exception may write (ruled).** `profiles`, `firms` and `firm_members` are **never restored**: they are pull-only caches (rule 4), they belong to the server, and a restored `firm_id` standing beside a restored membership row is the removal check's own condition, so a restore could erase the diary it had just written. A restored **row's** scope is settled rather than inherited — every row is stamped with the current chamber's `firm_id` and has its `scope_owner_id` cleared — and a file whose rows name **another firm** is refused outright, because such a row can neither be pushed (`sync_can_write` refuses a firm that is not the caller's) nor read back from the server. `user_id`, `created_by` and `last_modified_by` are **not** stamped: attribution is not the restorer's to rewrite, and the restoring account is written in only where an owner column names nobody at all, which is a hand-filled workbook.
- **A member is offered no backup at all** when removed, signing out, or switching account: no *Backup Data to Local Storage* window and no passphrase prompt, just a plain warning naming what is being discarded and, when there is a connection, that the sync should be allowed to finish first. This supersedes the safety-copy offer in Sync Plan §5 **for firm accounts only** — an individual account's logout flow keeps it.
- **The owner keeps both**, because an export is still how a chamber gets a copy off the phone; it is the restore that is barred.
- **The 50-case limit is the free individual's wall and nothing else; a lapse is capped by the tier's own allowance instead.** There is no chamber exemption to write: a free account has no online sync at all, firm mode is premium-only, and a chamber account is premium-derived by definition. A lapsed account — chamber or individual — is not re-gated at 50 and loses nothing it can read, but it may only **write** up to the **allowance of the tier it last held**: Pro 100, Firm 500, Firm Plus 1,000 cases, notes and case references, read from the stored tier (`profiles.tier`, or a chamber's `firms.tier`), with the **most recently updated** rows writable and the rest readable, searchable, printable and exportable but read-only until renewal. Deleting a writable row frees a slot, a note or reference on a read-only case is read-only too, and seed customisation stays unlimited. **Where the allowance has to be enforced, so it is not a rule without a site (audit):** the shipped gate is `freeTierCaseLimit` (50) in the Add Case save path, applied whenever the account is not premium, so a lapsed Pro or Firm account would stop at **50** until that check is replaced by the allowance itself; notes and case references have **no** gate anywhere today, so their ceilings are two new checks; and a member's allowance is the chamber's, so the same site must read `firms.tier` rather than the member's own absent plan. This supersedes Phase 5's gating as far as chambers are concerned, and the rule is recorded in full in `docs/implementation_plan.md` (Resolved Design Clarifications, "A Lapsed Account May Still Write, Up To The Allowance Of The Tier It Last Held").
- **A member keeps neither action (ruled).** No **Back Up** and no **Restore**, in Settings > Backup & Restore or on the way out, and the export goes for the same reason the restore does: a member who can export holds the chamber's whole ledger — its clients, its cases, its history — in a file they can keep, which is the firm's asset rather than theirs. Only the owner keeps both, because an export is still how a chamber gets a copy off the phone; it is the restore that is barred.
