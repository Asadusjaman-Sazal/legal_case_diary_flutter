# Task 23 — Admin Panel (Payment Administration)

> **Plan references:** Sync Plan §7 "Manual MFS Payment Flow" (the approval step that previously had no UI), §6 "Subscription Enforcement", Database Schema (`app_admins`, `payment_submissions`, `payment_approval_events`, `approve_payment` contract), "Resolved Design Clarifications" (Payment Method, Subscription Model) in `docs/implementation_plan.md`.
> **Goal:** the first administrator-facing screen in the app. A registered admin sees every user's payment request, can approve or reject one from the phone, and can place the panel in the bottom bar or the drawer through Settings → View Settings.
> **Rules:** Follow the Universal Working Rules in `00_INDEX.md`. Ask, don't guess. The app **never** grants admin rights to anyone: `app_admins` stays server-managed, has no client policy of any kind, and is changed only by the owner through an audited migration or a service-role operation.

---

## Why this task exists

Task 21 built the payer's half of the MFS flow — a submission, its TrxID, and a visible status. The other half had no home at all. `approve_payment` existed and was admin-gated, but the only way to reach it was for the owner to open the Supabase SQL editor by hand, read the `payment_submissions` table, and run the function for each one. That is workable for the first paying lawyer and untenable for a hundred.

## Phase 1 — Server: who may administer, and what the panel may ask for

Migration `20261002110000_admin_panel.sql`, applied to `lsthasywrdrhuuxnykau` and recorded in `supabase/AllSupabaseSql.md`.

1. **`app_admins` gains `full_name` and `email`**, filled in by hand by the owner for each later admin, so a revoked admin can still be identified afterwards. Existing rows are backfilled once from `auth.users.email`.
2. **The grant stays immutable, the description does not.** `reject_admin_update()` refused *every* UPDATE, which would have made the two new columns unwritable. It is replaced by `reject_admin_grant_change()`, which refuses any UPDATE touching `user_id`, `granted_at` or `granted_by` and permits the descriptive columns. Revocation stays a DELETE.
3. **`payment_submissions` gains `rejected_by` and `rejected_at`.** `approved_by`/`approved_at` are the approval record and are untouched; these are the same idea for the other outcome, so a refused payment records who turned it down.
4. **`is_app_admin()`** — SECURITY DEFINER, returns whether the *caller* is an admin. The only way a client learns its own status; the registry row behind the answer stays unreadable.
5. **`admin_list_payment_submissions()`** — every submission joined to the payer profile, returning `full_name`, `email`, `bar_association`, `membership_no` and `mobile_no` alongside the TrxID, amount, status and dates, plus `approved_new_expiry` from the immutable event (what *this* approval set, not the account's current expiry).
6. **`admin_reject_payment(id, note)`** — sets the status, stores the optional note, records the rejecting admin. `already_resolved` for an approved or already-rejected submission, so a rejection can never undo an approval.
7. **Approval needs nothing new**: `approve_payment` is reused unchanged, admin-gated and already writing its own immutable audit event.
8. **No RLS is widened.** `payment_submissions` stays `user_id = auth.uid()` and `profiles` stays self-or-firm; the panel reads through the RPC, which is gated in the function body. `anon` cannot execute any of the three functions.

## Phase 2 — Client data layer

`lib/features/admin/data/admin_repository.dart` and `presentation/admin_viewmodel.dart`, matching `payment_viewmodel.dart`.

- `AdminRepository`: `isAdmin()`, `listPaymentRequests()`, `approve()`, `reject()` — all through the RPCs. `UnavailableAdminRepository` reports "not an admin" so a build with no backend shows nothing.
- `AdminActionFailure` maps the server's own `status` strings to the four things the screen can word, and recognises the `admin_required` exception the gate raises.
- `adminStatusProvider` is separate from the list, because **navigation** needs the answer before the panel does: a screen that discovered it was not an admin after opening would flash its contents to everyone.
- An action never mutates the local list — it re-reads from the server, so what the admin sees is always what the server holds.

## Phase 3 — The Admin Panel screen

`lib/features/admin/presentation/admin_panel_screen.dart`.

- **Design reference:** `legal_case_diary_flutter\mockup_html_screens\admin_panel\code.html` (with `screen.png` beside it), written from the shipped screen after the fact — see the recorded departure below.
- Payment Requests, with two collapsible sections: **Pending open** and **Resolved closed** by default, because a resolved submission cannot be acted on and the admin opening the screen has work to do.
- Resolved is sorted by decision time, newest first (the server's own order is by submission time).
- Each row: payer name, status chip, plan and amount worded by the same helpers the paywall uses, the sender's number, the TrxID, the five personal fields, and the submitted **date & time** (0.0.511). A resolved row also shows **when it was decided** — labelled with the outcome's own word, **Approved** or **Rejected** (0.0.511) — plus the resulting expiry and any note.
- **Approve** and **Reject** while pending. Reject opens a confirmation carrying an optional note for the payer, because a rejection is a decision the payer may query.
- One outcome banner for the last action, and a load-failure state with a retry.

## Phase 4 — Navigation

- `AppRoutes.adminPanel` as a **shell route** built with `NoTransitionPage` (the no-motion rule that guards the bottom nav is about how it feels to switch, and the panel is selectable from that bar).
- One entry in `bottomNavTabDefs` carrying `adminOnly: true`, last in the canonical order, and one `_NavItem` in the drawer after Settings. **A single entry is deliberate**: View Settings drives both areas from the same list, so one entry is what makes "appears wherever the admin selected" work with one admin gate.
- `BottomNavTabDef.adminOnly` and `_NavItem.adminOnly` are distinct from `removable`: a non-admin cannot *hide* the panel, they never *see* it, and a `sideNavOptions` entry left over from an earlier admin session cannot reveal it. The bar drops a gated key rather than rendering a dead route.
- Admin status is `false` while it is still loading, so nothing appears before the server has said yes.

## Recorded mockup departure (resolved)

**The screen shipped before its mockup, by the user's decision, and the mockup was then written from the shipped screen.** CLAUDE.md rule 9 binds a screen body to a referenced file under `mockup_html_screens/`, and no such file existed when Task 23 was built. The user reviewed that gap and chose to **build the mockup later, as the screen needs some touch** — so the panel shipped on the Justice Ledger patterns it copied (the paywall's collapsible cards and typography), and the mockup was a follow-up from the screen rather than before it, the same shape as the paywall's own recorded departure.

**The follow-up is now done.** `mockup_html_screens/admin_panel/code.html` draws the panel as it ships: the case screens' header without the back arrow, search or view toggle, the *Payment Requests* heading one step above the shared Settings label, and the two sections as the shared Settings sub-menu button — Pending open with its request and the two decisions, Resolved closed — each with its own leading icon and a count where a chevron would sit. The header's sync button is drawn in its **ordinary enabled state** — the shared success cloud (`cloud_done`) in primary ink with the "Sync" tooltip — not the grey free-plan variant with a "Sync Requires a Premium Subscription" label that the case screens' mockups carry, because the panel is reached only by a signed-in admin with sync available. That glyph follows the header's narrowed icon set: the shared `SyncButton` now shows the success cloud for idle or a completed sync, the network-off cloud for offline or paused (count stays on top), and keeps its own mark for a real error. `screen.png` sits beside it at 390 px wide, like every other mockup.

**Drawing the mockup surfaced two values the screen got wrong, and the user chose the mockup as the target.** Recorded here because rule 9 made them a conflict the moment the HTML existed: (1) the sender's number was being wrapped in the amount formatter, so a phone number rendered as `৳01712345678`; (2) the method printed the stored `bkash` rather than the brand the payer chose, even though the checkout already maps the three providers to branded labels. **Both are now fixed on the screen** — the number renders plainly (and falls back to the shared em-dash when absent, like the fields around it), and the method goes through a local `_methodLabel` mapping. The checkout keeps its own copy of that mapping; a third screen needing it is the point at which the two should become one.

**The panel comes back after a logout (0.0.505 — reported).** The 0.0.394 fix below drops the panel's live reads when an admin logs out. It had a hole at the **arriving** end of a session, and it hid the panel for good: `signOut()` ends the session **before** it invalidates them, so a screen still watching `adminStatusProvider` re-asked at that instant with no JWT — and `SupabaseAdminRepository.isAdmin()` answers **false** on any failure by design (it must never let the panel flash), which is indistinguishable from a genuine non-admin. That `false` then outlived the sign-out, because signing back in as the **same** account is not an account switch: the logout has just forgotten the remembered id (`_local.clear()`), so `_completeSignIn`'s switch branch (`previousUserId != null && previousUserId != userId`) ran nothing and no read was re-asked. The admin's drawer row, bottom tab and View Settings entry stayed gone until the app was restarted. **The fix re-asks the four account-scoped server reads on every completed sign-in.** They are now one private helper, `_reaskAccountScopedReads()`, called from both `_forgetAccount()` (leaving) and `_completeSignIn()` (arriving); it drops **only** the live reads — `myPaymentSubmissionsProvider`, `adminStatusProvider`, `firmMembersListProvider`, `firmInvitesListProvider` — never local rows, so the account-switch wipe and the per-user cache clearing stay gated on a real switch and a cold start or token refresh still drops nothing of the account's own. **Pinned** by *the same administrator signing back in gets the panel again* in `test/features/account_switch_leak_test.dart`: sign in as the admin, log out, let the signed-out read cache `false`, sign back in as the same admin, and the status must be asked **again** under the new session and answer `true`. It failed before the fix with `Expected: true, Actual: false` — the reported symptom — and passes after it (the injection was verified to have landed before the result was trusted, and the file was restored byte-identically, md5 match).

**The panel is an account's, not a device's (0.0.394 — reported).** `adminStatusProvider` and `adminPaymentRequestsProvider` are **live reads** held in memory by providers, not rows in the database, so neither the branched logout's wipe nor `signOut` could reach them: after user A logged out and user B signed in on the same device, **B was shown the Admin Panel even when not an admin**, with A's queue in it. They are now dropped by `AuthViewModel._forgetAccount()` whenever the account changes — on the Logout button, and on a sign-in that arrives as a different account id, which is what a revoked or expired session leads to (that path clears nothing on its own, which is why the panel also survived a session the server had ended). A non-admin therefore has no panel entry and no queue on any path. Pinned by `test/features/account_switch_leak_test.dart`; recorded in `docs/implementation_plan.md` and Task 21.

### Phase 3 follow-up — the rejection notice goes, the note gets the app's own wording (0.0.502, user request)

> **The action notice is gone from this screen (user request — the whole notice, refusals included).** Approving or rejecting a submission used to raise a one-line banner at the top of the page: *Payment approved. The payer is now premium.*, *Payment rejected.*, or one of four refusal sentences. The admin asked for it to be removed **entirely**, on the reasoning that they already know what they just did — and, asked separately, for the refusal half to go with it rather than stay as the only notice. So `_ActionBanner` is deleted, its sliver with it, and the two now-unused keys `adminPanel_approved` / `adminPanel_rejected` are gone from both ARBs. **The behaviour that replaces the success half is the server's own re-read:** the row leaves Pending and appears in Resolved, which is where the admin goes to check what happened. **The refusal half has no replacement, and that is the user's decision, recorded here because it is a real trade-off:** a refused approve/reject (already decided, no longer exists, not an administrator, an unexpected failure) now changes nothing on screen at all. The row keeps its Approve and Reject, so a second tap is still possible and the outcome is still visible in the list — but nothing says *why* the first one did nothing. The `AdminActionState` machinery, its `AdminActionFailure` mapping, the row's in-flight spinner and the **Non-verified Accounts** page's own notice are all untouched, because that page's notice is a different screen's and this change was scoped to this one.
>
> **The rejection window now carries the app's own wording (user request).** Above the note field sits **Pre-Fill Message**, a 48 px `SettingsPickerRow` that opens an inline list under it (the window is `AlertDialog`, so a picker in a *second* window would hide the note being filled — the row and the check-marked rows are the Settings pickers' own convention, applied inline). It holds the seven sentences the user listed — mobile number & TrxID mismatch, wrong mobile number, wrong TrxID, enter the correct info, two tries left, one try left, be careful next time — written Title Case in the ARB as labels but sentence case as prose, in both languages (`adminPanel_rejectTemplate*`), and **tapping one toggles it without closing the list**, so several can be picked.
>
> **The rules the note obeys, in one place.** `reject_message_templates.dart` holds the localized list and the pure string work: picking a message **appends** it after the text the admin already typed, separated by **one space**, and the first one picked stays first (that is just the order they are appended in). Picking a message the note already carries does nothing, so a double tap cannot duplicate it. A **tick is derived from the note itself** (`adminRejectNoteHas`), so the row's check mark *is* the question "is this sentence in the box" rather than a second piece of state that could disagree with it — unticking removes that sentence and the single space that joined it, and an edit by hand tidies its own ticks. The note stays an ordinary `TextField`, so the admin can rewrite, reorder or delete anything the picker put there.
>
> **Add Your Own, and where the admin's own wording lives.** The list's last row types a message of the admin's own; it goes into the note like a pick **and is kept as an option for later** (the user chose that over a one-off insert, and chose the account over the device). The window reports the change to the screen, which does a **read-modify-write through the repository** (never through the settings view model, which applies a change to whatever settings it happens to hold and would otherwise save defaults over the lawyer's own row) and then makes the same detached premium push the Settings screens make after a preference write; a failed write is recorded as `admin.saveRejectMessages` rather than swallowed. Deleting an entry does **not** rewrite a note already carrying that wording.

### Phase 3 follow-up — the rejection window survives the keyboard (0.0.503, user report)

> **Reported.** With the Reject the Payment window open, opening **Your Own Message** from its list made the rejection window behind it report *Bottom overflowed by 77 pixel*.
>
> **The cause.** `Dialog` lays its child out inside what `MediaQuery.viewInsets` leaves, and the own-message field autofocuses — so the keyboard came up over **both** windows at once and the rejection window, whose middle is its tallest part (title, note, and the opened pre-fill list), was laid out with no room left. Nothing about the new list was wrong on a keyboard-less screen; it was the combination of the tallest window in the app with the shortest viewport.
>
> **The fix is one property: `scrollable: true` on the rejection `AlertDialog`.** Flutter's scrollable path puts the title and content into a `Flexible(SingleChildScrollView(...))` with the actions **outside** it, so the window's middle scrolls in whatever height is left and its two decisions stay pinned and reachable — a rejection is still possible with the keyboard up, which is the point of the window. The 208 px ceiling on the pre-fill list is unchanged: bounding the list was never the defect, laying the window out in zero room was.
>
> **Verified by reproducing it first.** The new case *the window lays out under the keyboard Your Own Message opens* sets a 336 px bottom inset with both windows genuinely open on a **360×640** phone (the smallest common size, the hardest case), and asserts no exception, the picker still present and the Reject Payment button inside the screen. **It failed before the fix — `A RenderFlex overflowed by 160 pixels on the bottom`, the same defect the report describes — and passes after it.** **Teeth:** removing `scrollable: true` in a scratch copy (the injection verified to have landed, `grep` count 0) failed with exactly that overflow; the file was restored byte-identically (md5 match). Writing the test also caught a bad test of its own: the first version tapped *Add Your Own* while the row sat below the fold, so the second window never opened and the case proved less than it claimed — hence the explicit `ensureVisible`, the `findsNWidgets(2)` precondition that both windows really are up, and the (also corrected) screen-height bound on the button's rect.
>
> **Verified.** `flutter analyze` clean; `flutter test` green, including the admin suite's **23** cases.

### Phase 3 follow-up — Non-verified Accounts waits 72 hours (0.0.495, user request)

> **Only sign-ups older than 72 hours are the page's business.** An unconfirmed account was listed the moment it was created, so the page counted a user who was still on the way to their mailbox — and the side-menu badge (which counts this list) ticked up by one on every registration. A sign-up younger than the window is still expected to confirm; only one that has sat unconfirmed for longer is *abandoned*.
>
> **Server — `20261012100000_unconfirmed_accounts_72h_window.sql`.** `admin_list_unconfirmed_accounts()` gains `and u.created_at < now() - c_min_age` (`c_min_age` = `interval '72 hours'`, one constant in the function), and `admin_delete_unconfirmed_account(uuid)` re-runs that same window and returns `{"status":"refused","reason":"too_recent"}` for a younger account — **before** the `is_provisional_account()` test, and with its own reason, so a fresh sign-up is never called an account that has done something when it has done nothing. Without that refusal the window would be cosmetic: a client holding an id could still remove a sign-up the page refuses to show. `is_provisional_account()` is untouched (age and activity are different questions), the two entry points stay `authenticated`-callable and gated in the body, and the internal guard stays closed to every client role, exactly as `20261009130000` left it.
>
> **Client.** `AdminActionFailure.tooRecent` maps the new reason, `adminPanel_deleteTooRecent` words it in both languages, and `adminUnconfirmedMinAgeHours` (72) is the one named number so the copy and the server cannot drift apart unnoticed. ## Admin notifications (push) — a waiting payment reaches the phone

> **Request (the user's).** An admin should get a **live notification** when a payment request is waiting, grouped so ten requests read as one line ("10 payment requests are pending") rather than ten notifications, with an expert opinion on what the plan was missing.
>
> **Five decisions taken with the user before any code (rule 1).** (1) **FCM is added now** — closed-app delivery is the only shape that is a real notification, and it costs nothing (Spark plan; the alternatives all deliver Android *through* FCM). (2) The count is **payments only**: the unverified-accounts half cannot be event-driven, because nothing writes when a sign-up crosses the 72-hour line, and the user chose to drop it rather than add a scheduled re-check. (3) **One notification, count only**, replaced in place. (4) **Sound on the first, silent updates.** (5) Its **own toggle** in Settings → Notifications, and (6) it is shown **only to a confirmed administrator**, like the panel itself. The same notification is posted whether the app is open or closed.
>
> **Server (`supabase/migrations/20261012120000_admin_payment_alerts.sql`, applied and in the ledger).** `device_tokens` (token is the primary key, so a device that changes hands is *reassigned* rather than feeding two accounts; self-only RLS and self-only DELETE; **local operational** class, legitimately hard-deleted) and `user_preferences.payment_alerts_enabled` (per-user, default **on**, writable by its owner through the grants the table already has). Two invoker RPCs — `push_pending_payment_count()` and `push_alert_targets()` — are reachable by the server's own API role only, every client role revoked **by name**; a *missing* preference row reads as the column's own `true`, which is how "never touched it" stays an administrator who wants the alerts. `pg_net` (installed in `extensions`, not `public`) plus two triggers on `payment_submissions` — insert, and update *only when the status moved* — post `{type, table, schema, record, old_record}` to the sender with the Vault-held shared secret, **after commit**, so a slow sender can never delay the payment the user is waiting on.
>
> **Sender (not SQL, so deliberately not in the ledger): `supabase/functions/send-admin-payment-alerts/`.** Deployed with `verify_jwt` off and its own constant-time `x-webhook-secret` gate. It re-reads the count and the fan-set from the database instead of trusting the payload, mints an FCM access token from the service-account key (RS256 over WebCrypto, module-level cache), sends one **data-only** message per device — high priority for the `0 → n` arrival, normal for later corrections — and drops a token the moment FCM calls it unregistered. A missing `FCM_WEBHOOK_SECRET` answers 500 and a wrong header 401, so a misconfiguration cannot look like a delivered notification.
>
> **Client (Phase 3).** `lib/core/push/` holds four files and no more: `push_gateway.dart` (the **only** file importing `firebase_core`/`firebase_messaging`, with the `@pragma('vm:entry-point')` background handler), `payment_alert_message.dart` (parse the payload; build the sentence; post, replace or cancel — no network, no database), `device_token_repository.dart` (`device_tokens` upsert/delete under the caller's own RLS, the row's `user_id` never taken from a caller) and `admin_push_scope.dart` (register for a confirmed admin; follow a token change; mounted once at the app root). `android_notification_gateway.dart` gains the payment-alert channel and the one notification id the whole feature uses (2900, above every alarm/alert/backup id) so a re-post replaces rather than stacks, and `cancelPaymentAlert()` is the zero case. The count is written with `AppDateUtils.formatDigits`, so বাংলা reads ৫ where English reads 5. `AuthViewModel.signOut()` deletes the device's row before the session ends (best-effort, failure recorded as `auth.unregisterDeviceToken`), and the Settings pair — **Payment Request Alerts**, admin-only — also asks for the OS notification permission when it is switched on and missing, because Android 13+ drops what an app may not post.
>
> **A tap opens Payment Requests (0.0.500, user request).** The line carries the app's own payload marker (`paymentAlertPayload` — a hyphenated word, never a UUID, so it cannot be mistaken for a case id), and one pure resolver, `notificationPayloadRoute`, turns a payload into a screen: Payment Requests for the count, that case's detail view for a hearing alert. Both readers use it — the tap listener while the app runs, and the router itself when the tap is what launched the app — so one notification cannot open two different screens. The resolver is also why the scheduler contract was renamed (`onNotificationSelected` / `launchPayload`): its payload stopped being only a case id, and the name had to stop saying it was. The sub-page's back arrow uses `Navigator.maybePop()`, so arriving as a launch's only route is safe rather than a dead end.
>
> **Deliberately not built.** No iOS block in the sender — this app ships Android only.
>
> **Verified.** `flutter analyze` clean; full `flutter test` **1732 passed**, including the new `payment_alert_message_test` (payload parsing, and the words in both languages with Bengali digits), `push_local_only_test` (the Firebase boundary, the local-only message path, the annotated handler, the single id) and `admin_push_registration_test` (an admin registers, a non-admin and a tokenless device do not, a rotated token replaces the row, sign-out removes it, and a broken gateway never blocks the sign-out). `preference_sync_test`'s payload assertions gained the new column, and `notification_settings_test` gained the three admin-visibility cases. **Phase 4 — the device half (0.0.504, verified by the user on two phones).** The user ran the check with two phones: one submitted a payment request, the other — the administrator's — **received the notification**. Read back through the connector on `lsthasywrdrhuuxnykau` in the same change (read-only, nothing written): `device_tokens` holds **1** row, so the admin's device registered itself; both triggers on `payment_submissions` exist exactly as designed (`trg_payment_submissions_admin_alerts_insert` on every insert, `trg_payment_submissions_admin_alerts_update` with `WHEN (new.status IS DISTINCT FROM old.status)`); the `send-admin-payment-alerts` function is **ACTIVE** (version 2, `verify_jwt` off); and the one webhook call ever made answered **200** — `{"ok":true,"pending":3,"alert":false,"targets":1,"sent":1,"failed":0,"pruned":0}` — one target, one message sent, nothing failed, nothing pruned.
>
> **What that run did *not* exercise, named rather than assumed.** (1) **The arrival.** The sender grants sound, vibration and a high-priority wake only to a genuine `0 → n` arrival (`wasArrival(body) && pending === 1`); this run left **3** pending, so the phone posted the line **quietly** as a correction — correct behaviour, but the *sound* path is still unproven on a device. To exercise it the pending count has to reach **zero** first (decide the outstanding requests) and then a new submission arrive. (2) **The zero case** — the line being *cancelled* rather than announcing a count of zero once the last pending request is decided. (3) **Signing out**, which should take `device_tokens` back to **0** rows (it still holds the one). (4) **The tap** on a device, warm and cold, and the back arrow from there to the panel (code-pinned by `notification_tap_test`, not yet device-pinned). (5) **The switch off** — `payment_alerts_enabled = false` should leave the sender a fan-set of `targets: 0`. (6) **Bengali digits** on a device set to বাংলা (`৫` where English shows `5`) — composed on the device, so code-tested only. All six are one-off checks on the admin's phone, not work owed in code.

## Not in this version

- **Rejecting after an approval** — the server refuses it (`already_resolved`) and the panel does not offer a refund path.
- **Any page other than the two the panel now holds** (Payment Requests, Non-verified Accounts). The menu takes more; each is new server surface and new policy, so they are added when they are needed rather than scaffolded empty. *(0.0.459 added the second; the earlier wording — "any section other than Payment Requests" — is superseded.)*
- **Sweeping unconfirmed accounts without being asked.** Non-verified Accounts lists them and can delete one at a time; nothing runs on a schedule. A cron sweep would be a decision about deleting people's accounts unattended, which is not this page's to make. *(0.0.495 added the 72-hour age window — that is a display and delete horizon, not a sweep: nothing is ever deleted by a timer.)*
- **Adding or removing admins from the app.** That stays a service-role operation, deliberately: the one thing that must not be reachable from a phone is the decision about who is allowed to decide.
