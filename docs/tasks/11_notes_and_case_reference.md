## Phase 1 — Notes Screen

### Phases 1 & 2 — refinement

- **0.0.261** — Two corrections to the to-do editor, both superseding the 0.0.260 bullet below. **The Add Item label and its `+` icon are white** (`AppColors.onPrimary`): the app's global `textButtonTheme` fills a TextButton black with white text, and the label had been overriding that foreground with `onSurfaceVariant`, leaving grey-on-black. **Unticking an item now returns it to its original position** rather than leaving it at the bottom of the list. Each row carries a fixed `order` (its place among the unticked rows, assigned when the row is created or loaded); ticking still sends a row to the very bottom, but unticking reinserts it before the first unticked row that outranks it, so it lands exactly where it started. A row added later takes the next `order`, so it stays at the end of the unticked block.

- **0.0.260** — The FAB now asks which kind of note to create: **Text Note** (the Phase 1 flow, unchanged) or **To-Do**, whose body is Google Keep's checklist — a tick, an editable item and a remove button per row, plus an **Add Item** row, with Enter on a row opening the next. Ticking an item drops it below the unticked ones (Keep's own rule, applied as a stable partition) and strikes it through; unticking lifts it back into the unticked block. A new to-do opens with one empty row ready to type into, and blank rows are dropped on save. This is a deliberate extension of the plan's `notes` schema (§ `notes`, which defines `title` + `body` only): `notes.items` holds the checklist as a JSON `[{text, done}]` array, and `null` there means a text note — so a note's kind is the presence of that column rather than a second flag to keep in step. `body` mirrors the item texts, one per line, which is what keeps the plan §12.1 title+body search able to find a to-do by its contents with **no query change**. A to-do card shows its first three rows with their ticks and `+N More`, so the two kinds read differently at a glance. **Part B must carry `items` on the server `notes` table**; the local sync payload already does. Files: `notes_table.dart`, `note_items.dart` (new), `note_detail_screen.dart`, `notes_screen.dart`, `notes_repository.dart`; schema v9 + `from < 9` migration. Tests: `test/features/notes_todo_test.dart` (13).

- **0.0.202** — Both libraries' search box now behaves exactly like the case-list one, because it is the same box in the same place: `ScopedSearchBar` is mounted by `CasesScreenModal` (under the header, above the scrolling list) instead of being the first row of the notes/reference `ListView`. It used to scroll away with the cards, sit inside the list's 16 px padding, and vanish entirely when the library had no rows — an empty library could not be searched at all. The screens pass `isSearching` / `searchController` / `onSearchChanged` to the modal and `_NotesList` / `_ReferenceList` lost the controller, the search callback and the `onCloseSearch` they no longer need. Note/reference filtering, the header search icon, the always-on (x) and tap-outside-to-hide-the-keyboard are unchanged. (`notes_screen.dart`, `case_reference_screen.dart`; tests: `test/features/library_search_test.dart`, 3.)
- **0.0.739** — The Add/Edit Case Reference form's title band is the app's **black** (`AppColors.secondary`, `#000000`) instead of the ink navy the other headers use, matching the Quick Update window's band; the white title and close icon are unchanged. - **0.0.700** — An existing note or to-do opens **read-only**, and **Edit** sits to the right of **Delete** (user request). The detail page starts in a view state: the title and body `TextField`s are `readOnly` with no cursor and no input hint, a to-do's ticks are wrapped in `IgnorePointer` (so they keep their normal colours but do not change), and its **Add Item** and per-row remove buttons are not built. Tapping **Edit** — which now runs the *Recorded for Deletion* warning that used to run when the page opened, since reading is harmless and editing is what needs the question — turns the fields editable; the existing tick then replaces Edit in the same slot and saves and closes as before, and the back arrow saves only while editing (read-only back just closes). A **new** note still opens editable and keeps the tick, because it has to be typed. Proof: `notes_todo_test.dart` gained *an existing note opens read-only, and Edit stands where the tick will* (read-only fields, Edit→tick swap, the edit saving) and *a read-only to-do offers no add or remove, and ticks nothing*; the two tick-order cases now tap Edit first. `flutter analyze` clean; the notes suites pass; full `flutter test` **2,180 passed**. The Notes mockup draws the new-note state and carries a note about the read-only one (rule 9).
- **0.0.744 — Law names become a synced list (Phase 1 of the law-list plan, user request).** The Statute box will offer a dropdown instead of free text, so the names it offers are now data: `laws` is a push/pull domain table, firm-shared like `courts`, with the five sync columns and the court list's three write rules (an add is `is_custom` and appends, a rename sets `is_user_modified`, a delete refuses a built-in). Each row carries a `category` — one of seven stable IDs seeded as code and labelled through `lawCategory_*` ARB keys in both languages, because the headings translate while the law names do not (the source list mixes English and বাংলা). `seed_v3` seeds the **57 names** of `docs/seed_data_test/LawsOfBangladesh.md`, in its order and under its seven headings, so an upgraded install and a fresh one hold the same stable IDs the Phase 2 server seed will generate. Local schema v17. No screen changed in this phase: the dropdown, the grouped Case Reference screen and Edit Law Names follow, and the statute column stays text so no existing reference is rewritten.
