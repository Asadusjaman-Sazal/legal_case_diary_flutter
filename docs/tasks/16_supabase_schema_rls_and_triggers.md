## Phase 2 — Server-Internal Tables (No Client Access)

1. **`invite_attempts`** — rate-limit ledger for `join_firm`: `id UUID PK`, `user_id FK → auth.users`, `attempted_at TIMESTAMPTZ` (server `now()` only). RLS denies ALL direct client access. Create `invite_attempts_user_attempted_at_idx ON (user_id, attempted_at DESC)`.
2. **`mutation_receipts`** — idempotency ledger for `push_changes`: `mutation_id UUID PK`, `actor_id UUID NOT NULL`, `entity_type TEXT NOT NULL`, `entity_id UUID NOT NULL`, `request_hash TEXT NOT NULL`, `terminal_status TEXT NOT NULL`, `result_payload JSONB NOT NULL`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`. No client RLS policies; only the RPC owner reads/writes. Retention: ≥ 400 days, and never purge a receipt still referenced by history/conflict/audit records.
3. **`app_admins`** — immutable admin registry: `user_id UUID PRIMARY KEY REFERENCES auth.users`, `granted_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `granted_by UUID REFERENCES auth.users`. No authenticated INSERT/UPDATE/DELETE policies; membership changes only via audited migrations/service-role operations.
4. **`payment_approval_events`** — immutable audit ledger per the schema table: one event max per submission (`payment_submission_id UUID UNIQUE`), recording actor, plan, amount, previous/new expiry, server time. RLS: owners read own events, admins read all; no client writes, no update/delete path at all.

**Phase 2 completion:** Migrations apply cleanly. `flutter analyze` clean. Update `docs/version_history.md`.

## Phase 3 — Triggers & Server Functions

1. **`server_updated_at` maintenance:** `BEFORE INSERT OR UPDATE` trigger on every synced table setting `server_updated_at = now()`. This is the only column delta pulls filter on.
2. **Delete-transition enforcement (trigger, not RLS):** `BEFORE UPDATE` trigger on each soft-deletable table detecting `OLD.is_deleted = false AND NEW.is_deleted = true` and verifying the editor has `can_delete` in `firm_members` (owner/individual creator always allowed), raising an exception otherwise.
3. **Resurrection guard:** narrow `BEFORE UPDATE` trigger rejecting `OLD.is_deleted = true AND NEW.is_deleted = false` unless a separately audited administrator recovery RPC sets a transaction-local authorization flag. Never compares client timestamps/versions/UUIDs.
4. **Free-tier case-limit guard (defense in depth):** trigger on `cases` INSERT that, when the owner's **derived** entitlement is free (`subscription_expiry + 48h grace > now()` is false) and their non-deleted case count is ≥ 50, rejects the insert. Take `pg_advisory_xact_lock(hashtext(NEW.user_id::text))` before counting to serialize count-and-insert.
5. **Payment rate limit:** `BEFORE INSERT` trigger on `payment_submissions` that overwrites/rejects client `submitted_at`, counts the caller's rows in the last 24h by `submitted_at`, and raises if already 3.
6. **`mirror_owner_subscription_to_firm`:** `AFTER UPDATE OF subscription_expiry ON profiles` trigger (owner rows only) copying expiry + display-only status to the owner's firm — the **only** write path for `firms.subscription_expiry`. Deploy in the same migration as `approve_payment`.
7. **`approve_payment(payment_submission_id UUID)` RPC:** implement exactly per the schema-section contract — `SECURITY DEFINER`, `SET search_path = pg_catalog, public`, `REVOKE ALL FROM PUBLIC`, `GRANT EXECUTE TO authenticated`, internal `app_admins` check, `SELECT ... FOR UPDATE` lock, pending/plan/amount validation, idempotent retries (`already_resolved`), expiry = `GREATEST(COALESCE(subscription_expiry, now()), now()) + 1 month/year`, submission update, firm mirror, and one immutable `payment_approval_events` insert — all in one transaction.
8. **`join_firm(code)` RPC:** `SECURITY DEFINER`; rate-limit check against `invite_attempts` (≥ 5 failures in 15 min → "Too many attempts"), hash the input, match an unused & unrevoked `firm_invites` row, create `firm_members`, update the associate's `profiles.firm_id`/`role`, mark the invite used — one transaction. Failed matches record an attempt via a **non-exception return path** (e.g., `{status: 'invalid_code'}`) so the insert commits; success deletes the caller's attempt rows; each call lazily deletes attempts older than 1 day.
9. **Realtime broadcast triggers:** `AFTER INSERT/UPDATE` trigger on each synced table calling `realtime.send()` with a tiny `{table, id}` payload to the private topic `firm:{firm_id}` (firm rows) or `user:{user_id}` (individual rows). Protect topic access with Realtime authorization (RLS on `realtime.messages`).
10. Revoke ordinary client UPDATE access to `payment_submissions.status/approved_at/approved_by`, `profiles.subscription_expiry`, and `firms.subscription_expiry`.

**Phase 3 completion:** Migrations apply cleanly; RPC smoke tests via SQL pass. `flutter analyze` clean. Update `docs/version_history.md`.

## Phase 4 — Row-Level Security Policies

1. Enable RLS on **all** tables.
2. Implement the full policy matrix from the "Row-Level Security (RLS) Strategy" table verbatim, including:
   - `cases`/`case_history`: SELECT own or same-firm; INSERT own; UPDATE own or firm `can_edit` (coarse — delete transition handled by trigger); DELETE = soft delete only (no hard-delete policy).
   - Config tables (`court_categories`, `courts`, `steps`, `case_types`, `on_behalfs`): all-authenticated SELECT for pre-seeded rows; own/firm SELECT for custom rows; creator-or-same-firm-`can_edit` UPDATE; guarded soft delete. Custom and modified reference rows are firm-shared in firm mode and user-scoped in individual mode.
   - `profiles`: readable by self **and same-firm members** (needed for Manage Associates and "edited by [Name]" rendering); UPDATE self only; no DELETE.
   - `firm_invites`: owner-only everything; redemption exclusively via `join_firm`.
   - `delete_requests`: firm-member SELECT/INSERT; UPDATE by requester (own pending) or `can_delete` reviewer; never DELETE (audit trail).
   - `conflict_log`: own-rows only; no DELETE.
   - `payment_submissions`: own SELECT/INSERT (+ trigger limit); no ordinary UPDATE; no DELETE.
   - Server-internal tables (`invite_attempts`, `mutation_receipts`, `app_admins`): no client policies at all.
3. Wherever a policy/trigger checks premium entitlement, derive it as `subscription_expiry + 48h grace > now()` — never read `subscription_status`.

**Phase 4 completion:** Policy tests (e.g., `supabase test`/pgTAP or scripted anon/authenticated queries) prove the matrix. `flutter analyze` clean. Update `docs/version_history.md`.

## Firm mode server rulings (user-ruled, plan record — not yet written as SQL)

> **Where this comes from.** The user's firm-mode rulings, recorded in `docs/implementation_plan.md` → *Resolved Design Clarifications* (its RLS strategy table has been corrected for both items below) and written out in full in `docs/firm_mode_blueprint.md` §4.4 and §10.

- **The read policies must scope a firm row to a current member, and an unscoped row gains a scope owner — owed as a migration.** The Phase 4 read policies were left as `user_id = auth.uid() or firm_id = current_firm_id()` (and `is_custom = false or user_id = auth.uid() or firm_id = current_firm_id()` on the six reference tables, with `conflict_log` own-rows-only) when `20260930210000_sync_can_write_firm_membership.sql` and `20260930220000_rls_firm_membership.sql` fixed the **write** half. Authorship is immutable, so the `user_id = auth.uid()` disjunct alone still selects every row a removed member authored in the chamber they left, and the pull carries no firm filter of its own — a fresh device pulling after a removal wipe brings that chamber's rows back into a diary that no longer belongs to it. The target, with the audit's second half, is `(user_id = auth.uid() and firm_id is null and scope_owner_id is null) or firm_id = current_firm_id() or scope_owner_id = auth.uid()` on the **eleven ledger tables** — `cases`, `case_history`, `notes`, `case_references`, the six reference tables and `delete_requests` — keeping `is_custom = false` for seeded reference rows and copying the condition with `requested_by` in place of `user_id` in `delete_requests`. Two tables stay narrower: `conflict_log` is **not** a ledger table, so its select needs only the membership condition (`user_id = auth.uid() and (firm_id is null or firm_id is not distinct from current_firm_id())`) and it takes **no** scope owner; and plain equality is equivalent to `is not distinct from` on the read side, because a null on either side is already not true.
- **A dissolve writes the rows a scope owner, not a bare null (user ruling).** A chamber's rows are readable only while that chamber is the caller's, so dissolving must null the rows' `firm_id` **and** write the owner as their **`scope_owner_id`**. With `firm_id` merely nulled, the first read condition — `user_id = auth.uid()` on a firm-less row — hands every member-authored row back to its author and hides it from the owner, which is the opposite of what a dissolve is for. `scope_owner_id` is a scope key, not attribution: `user_id`, `created_by` and `last_modified_by` are not rewritten. Without the same clause on `delete_requests`, a dissolved chamber's request history becomes unreadable to everyone, the member who raised it included.
- **The permission boundary is ruled, and it is a server boundary (user ruling).** The flags are no longer interface rules: **INSERT is gated on `can_add` and UPDATE on `can_edit`**, read from `firm_members` for the caller and the row's firm, by one `BEFORE` trigger per table — the delete-transition trigger's own shape — on `cases`, `case_history`, `notes`, `case_references` and the six reference tables. **Both halves are new work** (audit correction: an earlier draft called the INSERT half already enforced): there is no `can_add_firm` helper beside `can_edit_firm` / `can_delete_firm`, and `sync_can_write`'s INSERT branch reads no permission flag at all, so a member with `can_add = false` can insert a firm row through the RPC *and* straight through PostgREST today. With the shared config now **member-editable** (Task 20's entry), no owner-only guard over the reference tables is needed, and per-member toggles are the only control — there is no firm-wide read-only switch. The **scope columns are server-owned and must be named in `push_changes`**: `firm_id` is written from the caller's own firm at creation and never read from a payload, no client may change it on an existing row, and a caller who holds a firm may not create a firm-less row; `scope_owner_id` is written by the dissolve alone. That has to be stated because the RPC is `SECURITY DEFINER` and strips only `server_updated_at`, `version` and `last_modified_by`, so **any column added later is client-writable through it unless it is named there**.
- **This task's matrix is the place to hold all of it**, and it now also owes the **stored tier**: `profiles.tier` / `firms.tier` (with `tier_pending` / `tier_pending_from` for a mid-term downgrade), written by `approve_payment`, mirrored to the firm by `mirror_owner_subscription_to_firm()` — whose `of` list and `when` must be widened to cover the tier, or a chamber's tier never moves and its seat cap keeps reading the tier before it — read by `join_firm` for the seat cap (Free n/a, Pro 0, Firm 5, Firm Plus 20) and by the lapse allowance. It also owes the **in-use guard** that stops a tombstoned reference row a live case still names from making `purge_tombstones()` fail as a whole, and the **reference-table write scope in `push_changes`** (Task 18), which must accept a member's insert/update under `can_edit` and refuse only the immutable baseline. Task 20's removal workflow depends on the read scoping being done first.

## Firm mode Phase 6 — the in-use guard — as built (0.0.530)

> **The blueprint's Phase 6** (`docs/firm_mode_blueprint.md`), not this file's own Phase 6. Its server half is the guard this matrix already owed. Its client half went **past** the blueprint's own *verify, do not rebuild* wording at the user's instruction, so that change is recorded here and in `docs/implementation_plan.md` (rule 14).

- **Server.** `supabase/migrations/20261016110000_firm_mode_reference_in_use_guard.sql`. `enforce_reference_not_in_use()` — SECURITY DEFINER with `search_path` pinned and unkeyed on role or caller — returns early unless the row goes `is_deleted false → true`, walks the nine `child.table.column` pairs and raises `reference_in_use` as **23503** with a hint naming the dependent. Four `trg_<table>_in_use_guard` triggers (`BEFORE UPDATE … FOR EACH ROW`) are attached by one loop to `court_categories`, `case_categories`, `courts` and `on_behalfs`. **`steps` and `case_types` stay unguardable**, and the migration's header says why: `cases.case_type` is free text, so nothing references either by id. `purge_tombstones` keeps its signature, its `p_retention_days integer default 180`, its cutoff, its children-first order and its returned count, but deletes one candidate at a time inside `exception when foreign_key_violation` and reports the kept rows in a notice — so one blocked tombstone no longer fails the whole nightly run.
- **Device.** `lib/features/settings/data/reference_in_use_checker.dart` is the rule's single home: one SQL union over the live (`is_deleted = 0`) rows of `cases`, `courts`, `steps`, `case_types`, `on_behalfs` and `case_categories`, exposed as `readReferenceInUse()` and as `referenceInUseProvider` (a Drift `watch()`), yielding the in-use ids for `courts`, `on_behalfs` and `court_categories`. `data_deletion_service.dart` now reads that rule instead of its own private blocks, so the Manage Account tick list and the three screens cannot disagree about what is in use, and Edit Court/Steps withholds Delete for a row the rule names. No ARB string, no mockup body and no other screen changed.
- **Measured on the first cut, and fixed.** Reading the rule once at the top of the deletion run was wrong: the category step must read it **after** this run's own court and on-behalf tombstones, or a category whose only holders have just gone is kept and the run deletes less than it used to. `test/features/data_deletion_test.dart` caught it (2 failures) and passes on the re-read.
- **Proof.** `supabase/tests/firm_mode_reference_in_use_guard_test.sql`, rolled back and run wrapped, prints `INUSE OK` on `lsthasywrdrhuuxnykau` — including that a **member's** queued tombstone is refused by the guard rather than by `push_changes`' own authorship rule, which is why the queued case names a court the member authored. `test/features/reference_in_use_test.dart` covers each parent, a tombstoned dependent that does not hold a row, the reactive watch, and a firm member still seeing Add, Edit and Reorder on all three screens.
