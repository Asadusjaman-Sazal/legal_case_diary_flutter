# Legal Case Diary — Flutter App Implementation Plan

> **App Name:** Legal Case Diary (লিগ্যাল কেস ডায়েরি)
> **Target Users:** Individual lawyers & Law Firms in Bangladesh
> **Core Purpose & Target Audience:** The app serves as a digital clerk and ledger for individual lawyers and multi-user law firms (Chambers) in Bangladesh. Its primary goal is to digitize the traditional "cause list" diary, ensuring lawyers never miss a hearing date while maintaining all case details, notes, and precedents securely in their pockets.
> **Platform:** Flutter (Mobile-first, Android & iOS)
> **Backend:** Supabase (PostgreSQL + Auth + Realtime)
> **Offline DB:** Drift (SQLite wrapper for Flutter)
> **Last Updated:** July 17, 2026 (Revision 2.3 — lossless pull cursors, idempotency receipts, timestamp boundaries, admin authorization, encrypted local storage/backups, and deletion-review hardening applied)

> **Build status (read before using this plan as a work queue).** **Tasks 01–21 and Task 23 (the admin panel, added after the original 22) are complete; Task 22 (`docs/tasks/22_verification_plan.md`) is the only task still open.** The app is built and live, and the current work is **bug-fixing and polishing**, within which **firm mode** and the **plans/pricing ladder** are being **revamped** — both are current work, not future task numbers. **"Part A" and "Part B" are finished historical labels, not current constraints:** the offline requirement was a build-order rule that Task 16 fulfilled, and the app has talked to the Supabase backend ever since, so no change should be deferred, refused or labelled on the basis of being "Part A" or "Part B" work. The remaining open items are the *"What Firm Mode Still Owes"* list below and Task 22.

## Revision 2.3 Change Summary (Correctness, Security & Implementation Clarity)

- Replaced timestamp-only pull checkpoints with per-table composite `(server_updated_at, id)` cursors committed after each local page, preventing equal-timestamp and crash-boundary data loss.
- Defined deterministic per-mutation savepoint behavior and the server-internal `mutation_receipts` ledger, including request-hash validation and retention.
- Clarified local epoch-ms versus PostgreSQL `TIMESTAMPTZ` boundaries and Bangladesh civil-date handling; aligned subscription expiry and payment arithmetic.
- Added a concrete immutable `app_admins` registry and safe `SECURITY DEFINER` authorization contract for payment approval.
- Required SQLCipher-compatible local database encryption, OS-backed key storage, encrypted authenticated backups/diagnostics, and failure-safe key-loss behavior.
- Hardened delete-request approvals against stale target snapshots, clarified server-side cascade tombstones, increased invite-code entropy, and made failed-attempt recording transactionally durable.

## Revision 2.2 Change Summary (Concurrency & Operational Hardening)

- Replaced client-authoritative LWW versions with server-assigned optimistic concurrency (`base_version`/`expected_version`, structured conflicts, server increments only).
- Added queue conflict reconciliation and three-way merge metadata (`mutation_id`, `base_payload`, changed fields); later edits are preserved/rebased or marked `conflict_pending`, never silently discarded.
- Made extended-offline recovery a persistent mutation lock before export; added stale-permission rollback, idempotent already-deleted request handling, and a user-facing Sync Status/Diagnostics recovery screen.
- Clarified that accepted case mutations create immutable `case_history` atomically in `push_changes`; rejected attempts go only to `conflict_log`.
- Added server-controlled payment timestamps and an admin-only atomic `approve_payment` RPC; added the invite-attempt lookup index.
- Required delta pulls after uncertain Realtime continuity, versioned/idempotent pre-seed migrations, bounded page-by-page PDF raster fallback, and stable court-category IDs. Appellate Division and High Court Division are themselves court categories for scoping courts, steps, case types, and representation roles.

## Revision 2.1 (of the Implementation Plan) Change Summary (Follow-up Hardening Fixes)

- **`join_firm` rate-limit storage specified:** a new server-internal `invite_attempts` table (no direct client access) is checked and maintained inside the `join_firm` RPC — 5 failed attempts per 15 minutes per user, with lazy cleanup in the RPC itself.
- **`firms.subscription_expiry` mirroring mechanism named:** a dedicated `mirror_owner_subscription_to_firm` trigger (`AFTER UPDATE OF subscription_expiry ON profiles`, owner rows only) is now the only write path for the column, created in the same migration as the payment-approval trigger.
- **Payment rate limit enforcement moved to a `BEFORE INSERT` trigger** on `payment_submissions` (RLS can't count rows per 24h window); the client-side check is retained as UX only.
- **Pull cursors are per-table and composite:** each synced table keeps a crash-safe `(server_updated_at, id)` cursor in the local database; timestamp-only/shared cursors can skip equal-timestamp or inter-table commits.

## Revision 2 (of the Implementation Plan) Change Summary (Historical; concurrency wording superseded by Revision 2.2)

> **Audit note:** Revision 2.2 supersedes the LWW comparator and winner/loser language formerly used in this historical summary. The current and only implementable contract is server-authoritative optimistic concurrency with exact `base_version` checks, structured conflict responses, and explicit three-way reconciliation. No client timestamp, submitted version, or editor UUID may decide write acceptance.

- **Delta-pull correctness:** pulls filter on server-assigned `server_updated_at` (trigger-maintained), never client `updated_at`; pull cursors set from server timestamps (and maintained **per-table** as of Revision 2.1).
- **Clock-skew-proof conflicts (superseded implementation):** per-row monotonic `version` remains the revision identifier, but the server alone assigns it. Updates require an exact `base_version` match; `updated_at` and editor UUID are audit/display metadata only.
- **Atomic push pipeline:** all sync writes go through a single `push_changes` Postgres RPC (optimistic-concurrency enforcement, structured conflict responses, FK-safe ordering, premium gate, idempotent mutations, serialized FIFO worker, retry policy, compaction matrix).
- **Per-device offline reset (firm mode only):** extended-offline check is device-local, threshold raised to 335 days (buffer under 365-day tombstone retention), with an automatic authenticated encrypted safety archive containing the versioned JSON backup before any wipe. An **individual** account is never locked or asked to rebuild — see Resolved Design Clarifications, "Extended-Offline Recovery Lock Applies to Firm Mode Only".
- **Firm-shared config:** `court_categories`, `case_categories`, `courts`, `steps`, `case_types`, `on_behalfs` gain `firm_id` + firm-wide SELECT; `case_history` gains denormalized `user_id`/`firm_id`; `case_types` additionally link to `case_categories` when a court category defines them.
- **Realtime:** "Broadcast from Database" (tiny `{table, id}` pings on private firm/user topics) replaces `postgres_changes` subscriptions.
- **Logout flow branches** for premium-online / premium-offline / free users (no sync deadlock); the safety copy is **offered, never mandatory**, in the Backup to Local Storage format.
- **Invite system hardened:** `firms.secret_key` and locally stored password hashes removed; new `firm_invites` table with hashed single-use revocable codes redeemed via a rate-limited `join_firm` RPC.
- **Subscription authority:** premium entitlement is always *derived* from `subscription_expiry` (+ 48h grace) — never a stored status flag; expiry always enters the 48h grace window first; lapsed-premium users keep all their cases.
- **Free tier clarified:** individual-only, never syncs; the old "Pre-Push Subscription Count Validation" section removed (its race is impossible); upgrade triggers an initial backlog push.
- **Removed `cases.status`:** disposal is derived from `last_step` against the disposed-step set (single source of truth).
- **`delete_requests`** added to `sync_queue` entity types (offline-capable) with "Deletion request sent to Admin/Owner" toast; firm administration declared online-only.
- **RLS realism:** delete-transition (`can_delete`) enforced via trigger/RPC (RLS cannot compare OLD vs NEW); firm members can read each other's profiles; unsynced local tombstones never purged.
- **Battery:** 2–3 s micro-batch write-through (radio tail energy), `connectivity_plus` stream instead of polling, 60 s resume-pull throttle, exact-alarm permission handling (Android 14) + `BOOT_COMPLETED` rescheduling, platform abstraction for the Windows port.

## Resolved Design Clarifications (User Approved)

The following design decisions have been resolved based on user feedback:
- **The Lawyer's Own Details Live on the Account (`profiles`).** The five fields edited at Settings > Accounts & Profile > Profile — full name, bar association, membership number, office address and mobile number — are the account holder's own record, not device state, so a re-install or a second phone must not ask for them again. `profiles` stays a **pull-only cache** for everything else, and the shape of the one exception is deliberate: the client writes the holder's **own row only** (`profiles_update_self`, Phase 4) and **only those columns** (column-wise grants, Phase 3 + `20260929130000_profiles_personal_details.sql`), through a plain PostgREST PATCH — no queue, no RPC, no generic sync behavior. `email` is a **server-owned mirror** of `auth.users.email` (sign-up and e-mail-change triggers) and is never client-writable. Two rules govern the two copies: the account's values **fill the device's blanks only** — a detail the user typed on this device is never overwritten by a pull — and a save that could not reach the server is **retried** on the next launch, resume or reconnect rather than silently left behind. Saving shows the truth about which copy it reached: the toast says *Profile saved* only when the account accepted the PATCH, and the offline variant only when it did not (nobody signed in, no backend, or no connection) — the fields themselves are always saved on the device first, with no country-code prefix box beyond the editor's fixed `+88`, so the user types the local number with its leading `0` (`01XXXXXXXXX`).
- **App Name:** Official names are **Legal Case Diary** in English and **লিগ্যাল কেস ডায়েরি** in Bengali.
- **Justice Ledger:** This is the main theme and instruction file from the Google Stitch front-end design, not a financial ledger. All theming and styles must align with it. Reference: legal_case_diary_flutter\mockup_html_screens\justiceLedger\DESIGN.md
- **English Typography:** **Manrope** for headlines, **Inter** for body text, and **IBM Plex Sans** for labels and data (like case numbers).
- **Bengali Typography:** **Tiro Bangla** must be used for Bengali text throughout the app.
- **Localization (l10n):** The app UI supports both **Bengali** and **English**. The user can switch language in Settings. Implemented using Flutter's `flutter_localizations` package + `intl` package with `.arb` files. Bengali is the default locale for Bangladeshi users.
- **Case Numbering:** `case_number` is a single text entity (e.g., "110/2021"). It will not be split into separate number and year fields.
- **Date Format:** Dates display as `DD/MM/YYYY` (customary in Bangladesh). Drift stores local values as Unix epoch milliseconds; Supabase uses the explicit `TIMESTAMPTZ`/`BIGINT` boundary defined in the Database Schema. Hearing/next dates are Bangladesh civil dates and must not shift with UTC conversion. **Next Date Format Rule:** Show "Today" or "Tomorrow" when the configured local civil date matches; otherwise show `DD/MM/YYYY`.
- **Login Flow:** A unified, world-class single login screen (Email + Password) for everyone. No confusing "Owner vs Associate" separate screens. The app determines the user's role and firm membership dynamically upon login by reading their `profiles` record.
- **Sign Up & Team Onboarding:** 
  - **Individuals & Firm Owners:** Use the standard Sign Up screen to create a new account (starts as an Individual, converts to Firm automatically when an associate is added).
  - **Associates (Joining a Firm):** The Firm Owner generates a short, **single-use Invite Code** from the app (OTP-style: usable exactly once, no expiry, revocable by the owner before use). The Associate downloads the app, goes to Sign Up, selects "Join Existing Firm", and enters the Invite Code along with their details. Redemption happens through a rate-limited, `SECURITY DEFINER` `join_firm(code)` RPC against the hashed code in the `firm_invites` table (see Database Schema) — single-use + server-side rate limiting makes brute-force guessing infeasible while keeping the code short and typeable. This securely links them to the firm.

- **Backdrop Blur (No BackdropFilter):** Flutter's `BackdropFilter` is a GPU-heavy operation that causes severe frame drops (jank) and device heating on 2GB RAM Android devices, which are common in the target Bangladeshi market. **Do not use real-time `BackdropFilter` anywhere in the app.** Instead, simulate blur effects using performance-safe alternatives: use a semi-transparent dark overlay (`Colors.black54`), a frosted-glass appearance via a blurred pre-rendered static asset, or a `Container` with `BoxDecoration` using colors/gradients. The visual result should be indistinguishable to the user while being completely jank-free.
- **Subscription Model**: Freemium model. Free tier supports up to 50 **non-deleted** cases (`is_deleted = false` only). Soft-deleted cases do **not** count against this limit. Premium tier unlocks unlimited cases, secure cloud sync/backup to Supabase, and multi-device synchronization. **The free tier is strictly individual and strictly local:** cloud sync is never active on the free plan, free accounts are single-device, and Firm mode (adding any associate) requires an active premium subscription. The app is nonetheless architected so that the moment a user goes premium, it is 100% ready to sync (see Sync Plan §2 and §6).

- **How A Subscription Is Sold — Direct Distribution, For Now (user ruling).** The app is distributed **directly, not through Google Play, for now**: the project’s own APK, delivered by the in-app updater that already reads its own GitHub releases, is the only channel until the product has been tested and feedback gathered, and Play is a **later decision rather than a rejected one**. Three facts make this more than a distribution preference. Play **requires Play Billing for an in-app digital subscription** and forbids steering an in-app user to another payment method through buttons, links or messaging, and Bangladesh is in **no** alternative-billing or user-choice-billing programme, so there is no local exemption to enrol in. A Play-distributed app **may not update itself by any method other than Google Play’s update mechanism** (`Device and Network Abuse` policy), and "the user tapped Android’s installer" creates no exception. Therefore the two mechanisms this app is built around — the manual MFS flow (bKash/Nagad/Rocket → TrxID → `payment_submissions` → Admin Panel approval) and the GitHub-APK self-updater — are **compliant only while the app is not on Play**, and direct distribution keeps 100 % of the revenue instead of 85 %. What that makes load-bearing: the in-app updater is the **only** way an update reaches a user, so its release naming, size verification, `FileProvider` grant, per-resolver URI permission and **release authenticity** (a signed release or a checksum pinned in the app — with no store review in the path, the release feed is otherwise a direct route into every installed diary) are critical infrastructure **— built 0.0.541: the downloaded APK's signing certificate is compared with the installed app's own inside the install handoff, before any content URI or intent, so a tampered or unverifiable APK is refused with a sentence of its own in both languages and never reaches the installer**; installs become the marketing problem, so the folder, `README.md` and the website are part of the product **(the readme now carries the download page, the owner behind the releases and the install steps in English and Bengali; the GitHub releases page stands in as the download page until a site exists — user ruling)**; the manual MFS flow stays exactly as built, and its zero-commission economics belong in the pitch; and if Play is adopted later the Play build must switch to Play Billing **and** drop the self-updater, which makes it a **build flavour** rather than a code change, with the 15 % coming off margin rather than added to the customer’s price.

- **A Chamber Holds One Ledger, And The Owner's Own Diary Becomes It (user ruling).** A chamber account holds chamber rows and nothing else: there is no per-row "mine" marker, no ownership chip, no scope filter, and no such thing as a private case inside a firm account. Creating a chamber therefore **asks nothing** about the diary already on the phone — a lawyer creates a chamber in order to collaborate — so the moment the firm is created, the cases, notes, case references and customised seed data the owner already has **become the chamber's**, stamped with the new `firm_id` like every row written afterwards. **What creation stamps, exactly (user ruling, 0.0.520):** every ledger row the owner authored while firm-less — cases, case histories, notes, case references, the customised reference rows and any pending delete request — **tombstoned rows included**, so a member never meets a case the chamber had already deleted, each stamped row taking a `version` bump and a fresh `server_updated_at` so every device converges by pulling rather than by re-uploading. (An earlier draft had creation ask one explicit question — *"Share your N existing cases with this chamber? Everything you share becomes visible to every member you invite."* — and it is **withdrawn**: sharing at creation is the default, not a choice.) **(-0.0.522) Built:** `ensure_firm` performs this stamping itself in the transaction that creates the firm — the four case-data tables, the six reference tables’ **custom** rows and the owner’s pending delete requests, **tombstones included**, each taking a `version` bump and a refreshed `updated_at` beside the trigger’s own `server_updated_at` — and an idempotent re-call (a rename, a repair) stamps nothing again. **The write path carries the same scope (0.0.522):** `push_changes` now derives a new row’s `firm_id` from `current_firm_id()`, so a member’s insert can no longer land as a personal row inside a chamber, and an existing row keeps the firm it has because the update never names the column. Deliberate as-built detail: the scope columns are **stripped and derived rather than refused**, because the shipped client sends the **whole local row** as its payload — its `firm_id` is null on every individual write and can be stale between a write and the pull that would correct it — so refusing a payload that merely names the column would refuse legitimate writes while buying nothing, since a column the UPDATE never names cannot change. This is also what keeps the app's existing reads correct as they stand: every case and note query filters on `is_deleted` and screen scope only, so a single ledger cannot show one member's row to the wrong person, whereas a mixed personal-and-chamber account would need every list, count, badge, export, PDF, search and reminder to become scope-aware, and one forgotten path would leak silently. Who wrote what is answered by attribution instead — `user_id`, `created_by` and `last_modified_by`, which "edited by [Name]" and the conflict banner already read.
- **A Chamber Seat Starts Empty, And An Account With Its Own Diary Cannot Take One (user ruling).** Joining an existing chamber is refused when the account already holds its own diary, where *its own diary* means non-deleted rows this account authored while it had no chamber — `firm_id IS NULL` **and no scope owner**, which is what stops a dissolved chamber’s rows ever counting as anybody’s own diary — cases, notes, case references, or a court category, case category, court, step, case type or on-behalf it added or edited. The refusal is worded: **"This account already has its own diary (N cases). An associate's diary must be empty — sign up again using a different account with Join Existing Firm, or export your diary and delete this account."** (English source string; localized in both ARBs like every other refusal.) Two consequences are deliberate. First, rows an account authored **inside** a chamber are the chamber's, not its own diary, so they never block it — an account removed from one chamber (below) is left with an empty diary and may join another chamber with the same account. Second, an invitation never merges: an existing individual with a diary either stays personal or becomes the chamber it owns, and the refusal is the whole of the rule. A refused join changes nothing and says why; it is never silent.
- **A Lapsed Chamber Can Still Be Joined, On Purpose (user ruling).** If the owner's subscription has lapsed past the 48-hour grace window when a new associate redeems a code, the join still succeeds, and nothing bad follows from it. There is nothing to merge — the seat is empty by the rule above, so the newcomer brings no second diary and the chamber's ledger is not touched — and the only effect is that the new member works **local-only** with everybody else until the owner renews. The app then behaves exactly as it always does without a connection: every write is still saved locally and still queued in `sync_queue` with its sync columns, the member sees the plan's existing *"Your firm's premium subscription has ended. Contact your firm owner to renew."* banner, and the moment the owner renews, the false→true entitlement transition re-issues the delta pull and all of it catches up by itself. Refusing the join would strand the owner's new colleague for no benefit to anyone, so it is deliberately allowed. Lapsing does not weaken the other gate either: a chamber that does not exist yet still cannot be **created** without **the Firm tier or above** (user ruling): Pro’s seat cap is 0, so the creation gate belongs with the cap rather than with a bare premium check, `ensure_firm`’s gate reads the stored tier instead of the derived premium answer it reads today (`is_premium()` in `20260930180000_ensure_firm_premium_gate.sql`, so the replacement is owed), and a Pro caller is refused with the reason rather than allowed to build a chamber nobody can join.
- **Every Member May Add And Edit, And The Shared Config Is Member-Editable (user ruling — reversed).** A newly joined associate starts with `can_add = true` and `can_edit = true`, so the chamber's cases, notes and case references are theirs to work on from the first day, with no per-member setup step for the owner to remember. **`can_delete` stays false**, because deletion inside a chamber runs through the delete-request flow, which this ruling keeps: any member may raise a request for a case, note or reference, and the owner approves or rejects it (Task 20 Phases 3–4, unchanged). The owner may still narrow add or edit per member — the toggles remain his — and **the shared config is member-editable**: the reference data (court categories, case categories, courts, steps, case types, on-behalfs) stays firm-shared under rule 10, and **every member may add, edit and reorder it** — Edit Court/Steps, case types and on-behalfs offer Add, Edit and Reorder to a member exactly as they do to the owner. The owner-only reading is **withdrawn**, on the user’s own reason: most owners do not touch cases themselves, their associates do, so a chamber in which one person alone may add a new court name or a new step queues its work behind its busiest person. Three limits hold it. **The built-in baseline is immutable for everyone:** a row with `is_custom = false` is the seeded, globally shared list, so no member and no owner may edit, reorder or delete it, and a chamber that wants different wording adds its own row. **A reference row a live case still names cannot be deleted:** refused on the device already, and the server guard is owed (see "A Reference Row A Live Case Still Names Cannot Be Deleted" below) — a tombstoned row a live case still points at would make the nightly purge fail as a whole. And **a member’s own permission still governs it:** `can_edit = false` switches their reference edits off with everything else, so the owner’s control is not lost by this reversal, only no longer the only control. Member edits are attributed (`last_modified_by`), sync like any other domain row and are visible to the whole chamber; two members changing the same court at once is an ordinary conflict on the same banner and rebase flow, because reference rows get no private path. This supersedes the shipped `join_firm` default of `can_edit = false` (`20260929102300_phase3_join_firm.sql`).
- **The Join Gate's Three As-Built Rulings (0.0.523).** §2.1's empty-seat rule and §5.3/§5.4's seat cap are the *why*; these three facts are what the implementation settled and are absent from the rest of this document. (1) **A refusal consumes nothing and changes nothing:** `join_firm` decides `has_own_diary` and `seats_full` **before its first write**, so a refused join writes no membership, relinks no profile and does not burn the code — the code is the caller's to retry, and the earlier shape that restored rows in place was withdrawn because it made the refusal non-atomic. (2) **The refusals carry their own numbers:** both answers include the count the sentence quotes — `cases` from `individual_diary_cases` (individual rows only: a row with a `firm_id`, or one a dissolve gave a `scope_owner_id`, is the chamber's business and never counts, so a removed member may rejoin with the same account) and `seats` from `firm_seat_cap` — because **the client cannot compute either**: an associate cannot read another account's diary count, and the tier's cap is not in any table the app may read. They travel as **statuses, not errors**, since nothing went wrong and the account is untouched. (3) **An already-member redemption retires the code as `revoked`, not `used_by`:** the answer is still `already_member`, the code is still dead to a stranger, but the owner's invite list does not read *used* for someone who was already in the chamber. Both helpers, `holds_own_diary` and `individual_diary_cases`, are granted to **`authenticated` alone** — a signed-out caller must not be able to probe another account's diary count through the gate's own refusal.
- **The Permission Is A Boundary, Not An Intention (user ruling).** The flags are enforced **on the server**, so a modified client — or a direct PostgREST call carrying a member’s own token — cannot name its own permissions. **INSERT is gated on `can_add` and UPDATE on `can_edit`**, read from `firm_members` for the caller and the row’s `firm_id`. **Both halves are new work** (audit correction: an earlier reading in this document called the INSERT half already enforced): there is no `can_add_firm` helper beside `can_edit_firm` / `can_delete_firm`, and `sync_can_write`’s INSERT branch reads no permission flag at all, so a member with `can_add = false` can insert a firm row through the RPC *and* straight through PostgREST today. The shape is the one the delete transition already uses — a **`BEFORE` trigger per table**, not a policy rewrite: `cases`, `case_history`, `notes`, `case_references` and the six reference tables, one trigger each, reading the caller’s `firm_members` row; `can_delete` keeps its existing gate (the delete-transition trigger plus the pending delete-request flow) and is not duplicated. **A member may not change their own flags:** the `firm_members` write path is owner-only already (`20260930210000_sync_can_write_firm_membership.sql`) and the read guard is the scoping fix below. **Per-member toggles are the only control** — one concept, not two: there is no firm-wide read-only switch, the owner who wants a frozen chamber sets every member’s `can_add` and `can_edit` off, and the owner’s own seat is not a special case to design around. With the shared config now member-editable, no owner-only guard over the reference tables is needed. This closes what this document carried as an open decision, and it is why the interface and the server can agree: `can_edit = false` means the same thing in the screen and in the database, and the owner’s decision survives a client that ignores it.
- **Removing A Member Wipes That Member's Device Before Its Access Ends (user ruling).** Removal is one act with two halves. On the owner's side the server revokes membership, ends that member's sessions and Realtime topic access, and broadcasts the revocation on both topics so connected devices enforce it at once; the member's authored rows are **untouched** and stay the firm's, with attribution preserved and never reassigned. On the removed member's device the app runs its **complete wipe scope** — the same one a logout uses, `BackupRepository.wipeToFreshInstall`, which leaves behind a fresh install's database including the baseline seed — discards every queued mutation instead of pushing it, cancels that device's scheduled case notifications, and force-signs out — **by itself, with no confirmation step and no waiting for a tap** (user ruling): a copy that waits for a tap is a copy the person holding the phone can keep, so the earlier design’s notice carrying an *Erase & sign out* button is **withdrawn**, and what the member sees instead is an informational *your access ended* screen that reports what has already been removed and why. The order is the point: **the device erases before it can reach the firm again**, so nothing of the chamber is left on it — no case, no note, no reference, no roster, no invite, no pending request. The account keeps no link to the firm whatsoever afterwards, and because its diary is then empty it may join another chamber with the same account (the rule above). **The honest limit** is a device that never comes back online: the server side is immediate and the chamber's rows are unreachable from it, but the local copy can only be erased the first time that device is opened, because nothing can reach a phone that is off. **The removal confirmation says so in plain words and tells the owner what to do about it** (user ruling): that the associate’s phone keeps a copy of the chamber until that phone next opens the app, and that the copy is erased then on its own; that the associate should be asked to **open the app once, while the two of them are still together and connected**, so the wipe runs while someone can see it; that for a phone which will never be opened again the only way to clear it is the device’s own means — a factory reset, or the platform’s remote-wipe/locate feature — because no app can erase a device that is off; and that the chamber’s rows on the server are untouched and attributed, so nothing of the firm is lost or hidden either way. The same limit is shown to the removed member on the screen that tells them their access ended. One more rule is stated rather than implied (audit): **a removal takes that device’s push registration with it** as soon as the device is reachable again — and that happens at the removal itself rather than later (user ruling, 0.0.520): `remove_firm_member` deletes the member's `device_tokens` rows in the same transaction as the revocation, so no firm notification can be routed to a removed device even before its own erase runs. Offline work still pending there is discarded rather than synced, deliberately: it belongs to a chamber the member has already left. **The wipe is only half of it, though, because the server still hands those rows back.** `cases`, `case_history`, `notes` and `case_references` still read `user_id = auth.uid() or firm_id = current_firm_id()` (`cases_select_scoped` and its three twins, Phase 4), the six reference tables read `is_custom = false or user_id = auth.uid() or firm_id = current_firm_id()`, and `conflict_log`'s read policy is own-rows-only with no membership condition at all. A removed member's authored rows keep their `user_id`, because attribution is immutable — so `user_id = auth.uid()` alone selects every row that member ever wrote in the chamber they left, and the app's own pull adds no firm filter of its own. `20260930210000_sync_can_write_firm_membership.sql` and `20260930220000_rls_firm_membership.sql` closed exactly this hole for **writes** and left **reads** alone, on the stated belief that "a caller with no firm already reads nothing from a firm row" — which is true of the `firm_id = current_firm_id()` half and **false of the `user_id = auth.uid()` half standing beside it under `or`**. The read policies must therefore be scoped the way the write path already is, and an unscoped row gains a **scope owner** while they are: `(user_id = auth.uid() and firm_id is null and scope_owner_id is null) or firm_id = current_firm_id() or scope_owner_id = auth.uid()`, on the **eleven ledger tables** — `cases`, `case_history`, `notes`, `case_references`, the six reference tables and `delete_requests` — keeping `is_custom = false` for the reference tables’ seeded rows, and copying the condition with `requested_by` in place of `user_id` in `delete_requests` (whose select is firm-only with no author clause at all, which is precisely why it needs the scope clause: without it a dissolved chamber’s request history would be unreadable to everyone, the member who raised it included). Two tables stay narrower, and the first pass got this wrong: `conflict_log` is **not** a ledger table — its rows are a device’s own merge diagnostics — so its select needs only the membership condition (`user_id = auth.uid() and (firm_id is null or firm_id is not distinct from current_firm_id())`) and it takes **no** scope owner; and plain equality is equivalent to `is not distinct from` on the read side, because a null on either side is already not true. This is what the RLS strategy table below now shows. Without that change the removal wipe is undone at that account's next full pull, because a fresh local database starts at the initial cursor sentinel and pages in every table; and under the `firm_id IS NULL` definition of *its own diary* those resurrected chamber rows would not even block a later join, so one chamber's ledger could reappear inside the next. Two consequences follow. A chamber’s rows are readable only while that chamber is still the caller’s, so **dissolving** a chamber must null its rows’ `firm_id` **and write the owner as their scope owner** rather than only clearing `profiles.firm_id`. A bare null would do the opposite of what a dissolve is for: the read policy’s first condition — `user_id = auth.uid()` on a firm-less row — would hand every member-authored row back to its author and hide it from the owner, and under the member-editable-config ruling above the associates write most of a chamber’s cases. `scope_owner_id` is a **scope** key, not an attribution one, so `user_id`, `created_by` and `last_modified_by` are **not** rewritten and the *edited by [Name]* rendering is unaffected. It also settles the seat-empty rule above — a dissolved chamber’s rows never count as their authors’ own diary — so a former member may still join another chamber with the same account. And the timing matters, because that pull runs only once the account is premium again — on a plan of its own or on another chamber's — which is precisely the moment the old chamber’s rows would arrive. **It ships no earlier than the seat-empty refusal:** a self-erasing device is only safe once a new seat is guaranteed empty, because a member whose diary had been kept would have it erased with no backup (a member is offered none) and no confirmation step left to warn the person holding the phone. 
- **Firm Mode Is Premium, So Nothing Needs Exempting From The 50 Cases (user ruling).** A free account has no online sync at all — sync is a premium feature from the first day — so it can never be in a chamber: creating one is refused server-side, and joining one is the only other way in. The 50-case limit is therefore the **free individual's** wall and nothing else, and there is no "chamber exemption" to write, because a chamber account is premium-derived by definition (the owner's or the firm's `subscription_expiry + 48h`). When a chamber’s subscription lapses it falls back to local-only and **keeps every row**; the 50-case limit is not re-imposed on a lapsed chamber, exactly as it is not re-imposed on a lapsed individual — instead the **lapse allowance of the tier it last held** applies (Starter 100, Pro 250, Firm 500, Firm Plus 1,000 and Enterprise 2,000 cases, notes and case references, with the most recently updated rows writable and the rest read-only until renewal; see "A Lapsed Account May Still Write, Up To The Allowance Of The Tier It Last Held"). This supersedes the earlier "chamber accounts are exempt from the 50-case limit" default, which described an exemption that cannot arise.
- **Backup And Restore Inside A Chamber (user ruling).** Restoring a local backup file is **barred whenever firm mode is on, the owner included**, for one reason: a backup file is a photograph of the ledger taken at one moment, and putting it back over a chamber re-introduces rows other members may have changed or deleted since, silently undoing their work. The single exception is a **completely empty device** — a fresh install, or the state a wipe leaves — where there is nothing to overwrite; even there it is not a merge, because the full pull a fresh install performs brings the chamber's rows, and every tombstone the server still holds, over the restored ones, so a deletion from within the last 365 days corrects a stale restored row (a server row already purged past that window cannot, which is the accepted ceiling of the exception). A member who is being removed, and a member signing out or switching account, is **not offered a backup at all** — no *Backup Data to Local Storage* window and no passphrase prompt — and instead gets a plain warning naming what is being discarded and, when there is a connection, that the sync should be allowed to finish first. This supersedes the safety-copy offer in Sync Plan §5 **for firm accounts only**: an individual account's logout flow keeps the offer it has. **A member keeps neither action (ruled):** no **Back Up** and no **Restore**, in Settings > Backup & Restore or on the way out, and the reason the export goes too is the one that decides it — a member who can export holds the chamber’s whole ledger, its clients, its cases and its history, in a file they keep, which is the firm’s asset rather than theirs; only the owner keeps both. **What the empty-device exception may write (ruled):** `profiles`, `firms` and `firm_members` are **never restored** — they are pull-only caches, they belong to the server, and a stale `firm_id` named beside a restored membership row is the removal check’s own condition, so a restore could erase the diary it had just written; each restored **row** is stamped with the current chamber’s `firm_id` and has its `scope_owner_id` cleared, so it belongs to the chamber like every other row of it; a file whose rows name **another firm** is refused outright, because such a row can neither be pushed (`sync_can_write` refuses a firm that is not the caller’s) nor read back from the server; and `user_id`, `created_by` and `last_modified_by` are **not** stamped, because attribution is not the restorer’s to rewrite — the restoring account is written in only where an owner column names nobody at all, which is a hand-filled workbook. **Built (0.0.538):** the bar is firm mode's own fence with no way through — the premium guard's *Delete Local & Cloud Data* route is not offered inside a chamber — and it sits above that guard; the caches are never restored, every restored row is stamped with the current chamber's `firm_id` (`settleRestoredScope`, one writer for the column), a file naming another chamber is refused with its own sentence, and a member keeps neither action at both sites (the Settings list hides Backup & Restore, the screen shows the notice, and the logout flow replaces the copy offer with the warning). `scope_owner_id` is cleared by construction: it is a server column absent from the local schema and stripped from every push payload by `20261015110000`.
- **What A Chamber Shares, And What Stays A Member's Own (user ruling).** Shared with every member of the chamber: **cases and their case histories, notes, case references, and the customised seed data** — court categories, case categories, court names, steps, case types and on-behalfs. Never shared, always personal to the account that set it: the Settings entries for **notifications, language and view** (notification time and day offset, the master notification toggles, the app language, the bottom-navigation tabs, the side-menu rows, the default landing page and the case-list display mode), together with every other per-user setting such as the backup nudge and the app lock. This is rule 10 said plainly, with the shared half named, and it is held by the table classes rather than by discipline: the first group are push/pull domain tables, the second are per-user preference rows that are never written to a firm topic.
- **The Order Of Work For Firm Mode (addendum).** 1. **Chamber creation** shares the owner’s existing diary and stamps it with the new `firm_id`, and the write path carries that scope — without it firm mode is inert, because a chamber account’s rows would not carry the scope the reads and the Realtime topic need. 2. **The join refusal**, with the empty-seat definition as its companion (*its own diary* means `firm_id IS NULL` and no scope owner), and the **invite fix** beside it — an already-member redemption returns `already_member` and retires the code as **revoked** rather than consuming it as used, and the client never offers the Join Existing Firm field to an account that already has a firm. 3. **The removal wipe, its no-backup rule and the owner warning** — and a self-erasing device ships **no earlier than step 2**, because a member whose diary had been kept would have it erased with no backup and no confirmation step left to warn them. 4. **The read-side scoping**, which is what makes step 3 stick. 5. **The permission boundary** (`can_add` on INSERT, `can_edit` on UPDATE, one trigger per table; both halves new work). 6. **The server-side in-use guard** for reference rows. 7. **The lapse allowance and the read-only-over-the-allowance rule**, which read the settled ladder — so the **stored tier column comes first**, because the allowance is derived from it and from nothing else. 8. **Dissolution**, with the roster-empty precondition and the unscoping step **and its scope owner**. 9. **Attribution in the UI** — who added a row, who last changed it — and the owner’s roster, which are readability rather than correctness. A per-row "only me" scope is **not** on this list and is not planned: under the single-ledger model above it would have nothing to mark, and building it is exactly what would turn every read path into a leak surface. The detail behind all of it (the reasoning, the edge cases and the owed work) is recorded in `docs/firm_mode_blueprint.md`. **The build order now lives as a per-phase execution spec in that file's `## Phases to Implement:` section** — fifteen phases with status, migration, objects, proof, acceptance and hazards, and it is the **status of record**; the nine steps above are the design dependency order, which the phase list follows except that it **hoisted the read-side scoping to Phase 1** because the hole was live, and **Phases 1–6 of it are built**.
- **The Tier Ladder Is Settled, And The Tier Is Stored (user ruling).** *Which tier* an account holds and *how many seats* it bought are stored rather than implied, because two rules need a source: the lapse allowance has to be derivable after a lapse, and the join-time seat cap has to read something. Both become columns — **`profiles.tier`** for an individual and **`firms.tier`** for a chamber — written by `approve_payment` at approval and **never cleared by expiry**, because the column is the record of the last tier held; the seat cap is read from the same value (Free n/a, Starter 0, Pro 0, Firm 5, Firm Plus 12, Enterprise unlimited). **The write path is two steps and the second is easy to miss** (audit): `approve_payment` writes the **profile**, and the firm’s copy moves only because `mirror_owner_subscription_to_firm()` copies it — a trigger that fires *on `subscription_expiry` changes only* and copies two columns — so `tier` needs the same mirror, with the trigger’s `of` list and its `when` widened to cover it, or a chamber’s tier would never move and its seat cap would keep reading the tier before it. **`join_firm` reads the cap and refuses a join that would exceed it**, which is new: the shipped `join_firm` inserts a membership with no seat check of any kind, and a refusal names the cap and how many seats are in use. **Client writes are closed on both tables by construction rather than by luck** — the column privileges deny by default any column a later migration adds (`20260929102500_phase3_column_privileges.sql` grants `update (full_name)` on `profiles` and `update (name)` on `firms`), so `tier` is unwritable until someone deliberately grants it, which nobody will. **A downgrade adds two more values beside it:** the tier in force cannot be overwritten mid-term, so a lower-tier purchase writes **`tier_pending`** and **`tier_pending_from`**, and every reader — the seat cap in `join_firm`, the lapse allowance, the Subscription screen — takes the **effective** tier (`pending` once its instant has passed, else the tier in force) rather than the column as stored. A **seat cap binds new joins only**: nobody is ever auto-removed by a billing change, the owner is told to trim the roster, and the extra members keep working read-write until he acts.
- **A Lapsed Account May Still Write, Up To The Allowance Of The Tier It Last Held (user ruling).** Lapsing never deletes, hides or re-reads a row, but it does **cap what can be written**, and this is new. A **free account that has never been premium** keeps the wall it has today: 50 live cases, and no ceiling on notes, references or seed customisation. A **lapsed account — individual or chamber — may keep writing locally** while it holds fewer than the allowance of the tier it last held: **Starter 100, Pro 250, Firm 500, Firm Plus 1,000 and Enterprise 2,000** cases, and the same number of notes and case references, read from the account’s **stored tier** (`profiles.tier`, or a chamber’s `firms.tier`) and from nothing else — approaching it from the plan the account bought would misread a chamber that was downgraded before it lapsed. **Beyond the allowance the excess is read-only:** nothing is lost or hidden, every row can be opened, searched, printed and exported, and the writable set is the **most recently updated** rows of that kind (`updated_at` descending, `id` as the tie-break), so the cases the lawyer is actually on stay editable and the archive is what waits for renewal; **deleting a writable row frees a slot**. **Children follow their parent:** a note or a case reference attached to a read-only case is read-only too, no new note may be added to a case over the allowance, and the allowance’s own note and reference ceilings then apply in their own right to everything else. **Seed customisation is unlimited**, because a court name, step or case type is not the product and a chamber that cannot add a new court cannot work. Renewal returns the whole ledger at once on the false→true entitlement transition, which is also when the delta pull and the queued backlog run. Scaling the allowance with the tier is deliberate: a flat 100 would reduce a 20-lawyer chamber holding 6,000 cases to 100 editable cases overnight, which buys churn rather than renewal. **It is a local rule and it says so:** while lapsed the engine cannot push anything anyway, so the cap is enforced on the device, and the server’s own gate on `push_changes` remains the security boundary — which is now exactly true, because a member’s own expiry is ignored while they hold a firm and a member cannot buy one. **Where it has to be enforced, so it is not a rule without a site (audit):** the shipped gate is `freeTierCaseLimit` (50) in the Add Case save path, applied whenever the account is not premium, so a lapsed Pro or Firm account would be stopped at **50** until that check is replaced by the allowance itself; notes and case references have **no** gate anywhere today, so their ceilings are two new checks rather than a tightened existing one; and a member’s allowance is the chamber’s, so the same site must read `firms.tier` rather than the member’s own absent plan. The allowance is a ceiling on **writing**, never on reading: a lapsed chamber can still hand a client a printed cause list of all 2,500 of its cases.
- **A Member May Not Buy A Personal Plan, And Their Own Expiry Does Not Count While They Hold A Firm (user ruling).** A member needs no plan of their own, and while the owner’s subscription is live the member syncs on the same mirrored `firms.subscription_expiry` every gate already reads. **A member cannot buy a personal plan:** the app does not offer Subscription Plans to a member — an account inside a chamber it does not own — and **the server refuses the submission itself**, because a screen was never the boundary. **The owner is exempt** (user ruling 2026-10-17): his purchase is the chamber’s renewal, and the two entries the rule removes from a member are his only routes to it. **(0.0.534) Built** in `20261017100000_firm_mode_member_no_plan.sql`: the insert policy refuses a member while the owner may still submit, and `has_sync_entitlement` counts the chamber’s expiry alone once `profiles.firm_id` is set; the app drops the entry on the Subscription screen and the side-menu row, the paywall shows a chamber notice, and Current Plan reads *Premium* rather than a member’s old plan. Proven by `supabase/tests/firm_mode_member_no_plan_test.sql`. Both halves are work with a named site (audit): the side menu’s **Current Plan** row expands into Subscription Plans, so that row — not only the Subscription screen — has to drop the entry for a member, and `payment_submissions_insert_own` is `with check (user_id = auth.uid())` today, so refusing the submission is a **policy change** and not a client check. This matters because the state is reachable today: `profiles.subscription_expiry` is not cleared when someone joins, so an account that bought Pro and then joined with an empty diary keeps a live expiry, and the server’s gate was *my own expiry **or** the firm’s* — while the owner was lapsed, that member kept pushing and the lapse allowance had no server gate behind it for that one account. That is now closed (0.0.534). **While the account holds a firm, only the firm’s expiry counts.** Paid time is preserved rather than destroyed: it is ignored in a chamber and applies again the day they are individual, and when the firm lapses the member lapses with it.
- **The Scope Columns Belong To The Server (audit).** `firm_id` is written **from the caller’s own firm when the row is created** and never read from a payload; **no client may change it on an existing row**; and a caller who holds a firm may not create a firm-less row at all, because a chamber holds chamber rows and nothing else. `scope_owner_id` is written by the dissolve and by nothing else. This has to be stated because `push_changes` is `SECURITY DEFINER` and so bypasses the column privileges that guard direct PostgREST writes — it strips only `server_updated_at`, `version` and `last_modified_by` from a payload, which means **any column added later is client-writable through the RPC unless it is named there**. Without the rule, one accepted update lets an author null their own row’s `firm_id` (and set `scope_owner_id` to themselves), which takes the case out of the chamber’s ledger and carries it into their next chamber as their own. **(0.0.522) Built, both halves, in `20261015110000_firm_mode_creation_and_scope.sql`:** a new row’s `firm_id` is the caller’s own firm (null for an individual, the chamber for a member — which is what made firm mode work at all, because the client’s whole-row payload carried `firm_id` null and every member’s case was landing as a personal row inside the chamber), an existing row keeps the firm it has because the update never names the column, and `scope_owner_id` is subtracted from every payload before any branch reads it, so the dissolve remains its only writer. The scope columns are **stripped and derived rather than refused** — the payload’s `firm_id` is not an error, it is simply not read — because the shipped client sends the whole local row and a stale value would otherwise fail a legitimate write.
- **A Reference Row A Live Case Still Names Cannot Be Deleted (user ruling — the server guard is owed).** A tombstoned reference row that a non-deleted case still points at cannot be removed at all, because the foreign key refuses it, and the nightly `purge_tombstones()` would then fail **as a whole** rather than skip one row. The device already refuses it, and the Manage Account tick list relies on the same rule; the server guard is new work and belongs with the rest of the owed SQL.

## Database Schema

> **Naming Convention Mapping:** To ensure seamless DB-to-Dart translation without custom mapping boilerplates, the industry standard is used:
> - **Database Columns (SQLite & PostgreSQL):** `snake_case` (e.g., `court_id`, `case_number`, `is_deleted`).
> - **Dart Model Fields / JSON:** `camelCase` (e.g., `courtId`, `caseNumber`, `isDeleted`).
> - **Drift Auto-mapping:** Drift maps these automatically so that database files use native `snake_case` columns and generated Dart classes use native `camelCase` fields, preventing naming mismatches.

> **Timestamp Convention (explicit storage boundary):** Drift stores timestamps as `INTEGER` Unix epoch milliseconds because SQLite has no native timestamp type. Supabase/PostgreSQL stores server-authoritative instants (`server_updated_at`, submission/approval times, subscription expiry, audit times, invite attempts) as `TIMESTAMPTZ`; client-origin display metadata such as local `updated_at` may remain `BIGINT` epoch milliseconds because it is untrusted and never used for authorization, ordering cursors, or conflict acceptance. Repository serializers convert `TIMESTAMPTZ` ISO-8601 UTC values to/from local epoch milliseconds at the boundary. Calendar-only legal dates such as `next_date` and `hearing_date` are normalized to a local civil date (start-of-day in the configured Bangladesh timezone) and compared by calendar date, never as an arbitrary UTC instant. The display layer (`date_utils.dart`) renders the configured locale and timezone consistently.

> **Sync Columns:** Every synced data table (`cases`, `case_history`, `notes`, `case_references`, `court_categories`, `case_categories`, `courts`, `steps`, `case_types`, `on_behalfs`, `delete_requests`) includes:
> - `updated_at` (INTEGER) — Epoch ms of the last local modification, retained for display/audit only. It never decides write acceptance because device clocks are untrusted.
> - `version` (INTEGER) — Monotonic per-row revision assigned **only by the server**. Inserts receive version 1; accepted updates receive `current_server_version + 1`. Clients never choose or increment the authoritative value.
> - `server_updated_at` (TIMESTAMPTZ, **Supabase only**) — Maintained by a Postgres `BEFORE INSERT OR UPDATE` trigger (`server_updated_at = now()`). This is the only column delta pulls filter on. It does not exist in the local Drift schema.
> - `synced_at` (INTEGER) — Epoch ms of last successful Supabase push. `null` means unsynced.
> - `is_deleted` (BOOLEAN) — Soft delete flag. Never hard-delete rows.
> - `last_modified_by` (TEXT/UUID) — User ID of the last accepted editor, assigned/validated by the server from `auth.uid()`.
>
> **Optimistic concurrency contract (server-authoritative):** Every queued update/delete carries the row's last known `base_version` (also called `expected_version`). `push_changes` accepts it only when `base_version = current server version`, applies the mutation, and assigns the next version. A mismatch never falls back to timestamps or UUID ordering; it returns a structured `conflict` result containing the current server row/version and the submitted mutation metadata. This prevents two offline clients that both edited version 1 from independently claiming version 2, and prevents a tampered client from winning with an artificially large version. Inserts are idempotent by stable row ID + `mutation_id`. (The `version` and `server_updated_at` columns are not repeated in each table definition below — they apply globally per this note.)

### `firm_invites` (Single-use onboarding codes — replaces the former `firms.secret_key`)
| Column | Type | Notes |
|---|---|---|
| `id` | UUID PK | |
| `firm_id` | UUID FK → `firms` | |
| `code_hash` | TEXT UNIQUE | SHA-256 hash of a cryptographically random, normalized invite code with at least 50 bits of entropy (for example 10 Crockford Base32 characters). Plaintext is shown once, never stored or logged. |
| `created_by` | UUID FK → `auth.users` | The owner who generated the code |
| `used_by` | UUID FK → `auth.users` | null until redeemed. **Single-use:** once set, the code can never be used again. |
| `used_at` | INTEGER | Epoch ms — null until redeemed |
| `revoked` | BOOLEAN | The owner can revoke an **unused** code at any time. Default `false`. |
| `created_at` | INTEGER | Epoch ms |

> **Redemption flow (online-only):** Codes have **no expiry** but are strictly **single-use** (OTP-style) and revocable before use. Joining goes through a `SECURITY DEFINER` RPC `join_firm(code)` — required anyway, since an associate cannot SELECT the firm pre-membership under RLS. The RPC: hashes the input, matches an unused & unrevoked row, creates the `firm_members` row, updates the associate's `profiles.firm_id`/`role`, and marks the invite used — all in one transaction. **Rate limiting (concrete mechanism):** max 5 failed attempts per 15 minutes per user, tracked server-side in a small **`invite_attempts`** table (see below). At the start of `join_firm`, the RPC counts rows in `invite_attempts` where `user_id = auth.uid() AND attempted_at > now() - interval '15 minutes'`; if the count is ≥ 5, it raises a "Too many attempts — try again later" exception before touching `firm_invites`. Every **failed** match records an attempt through a non-exception return path (for example `{status: 'invalid_code'}`), so the insert commits; do not insert and then `RAISE`, because PostgreSQL would roll the attempt back with the statement/transaction. A successful redemption deletes the caller's attempt rows. Rows older than 15 minutes are ignored by the check and lazily cleaned up by the RPC itself (a `DELETE ... WHERE attempted_at < now() - interval '1 day'` on each call) — no cron job needed. Single-use + rate limiting makes brute-force guessing infeasible even with a short, typeable code.

> **Retry Policy and recovery:** Each queue entry retries with **exponential backoff** (e.g., 30s → 1m → 2m → 4m … capped at 30m). Network/HTTP 5xx errors are retryable; RLS denial, validation failure, optimistic-concurrency mismatch, and permanent server rejection stop automatic retries immediately and set `state` to `blocked` or `conflict_pending`. After 10 transient failures, mark the entry `blocked` for manual review instead of looping. The push worker is a **single serialized FIFO**—never parallel fire-and-forget pushes.
>
> **Sync Status / Diagnostics screen:** Every user (not just firm admins) can open a Sync Status screen showing entity, operation, state, retry count, last error, and last attempt. Actions: **Retry**, **Discard** (with confirmation and authoritative-row rollback/pull), **Review Conflict**, and **Export Diagnostic Bundle** (redacted metadata + queue payloads suitable for support). A blocked/conflicted badge in the app header links here; no queue row may become permanently invisible. **(0.0.471 — user request) A row names the record it is about, and a blocked row names its reason.** The queue carries only an `entity_type` and an `entity_id`, so a card built from the row alone names nothing a user can place. `resolveSyncEntrySubjects` (in `sync_status_providers.dart`, the screen's own Task 19 Phase 4 layer) now resolves each open entry against **one query per table**: a **case** entry — and a **case-history** entry, through the case its row belongs to — yields the case's stored type, number and court, and the widget renders it exactly as every case screen does (`caseTypeLabel` + case number, with the court's name through `seedLabel(court.id, fallbackEn: courtName)`); **every other entity** yields its own local name (a note's title, a reference's page/title, or the name a `courts`/`case_types`/`steps`/`on_behalfs`/`case_categories` row stores, with a `court_category` resolved through `courtCategoryName` because it stores a localization key). A **delete request** and a **conflict log** carry no name of their own — naming them means following the record they point at, which this screen does not do — and a row whose local record is **gone** resolves to nothing: the card shows no identity rather than a guessed one. A **blocked** card additionally carries a labelled **Why It Is Blocked** block above the server's message: `syncBlockCause(row)` reads the one distinguishable case out of the row's own facts — `gaveUp` when `retryCount >= syncBlockRetryLimit`, the worker's own limit, which is now a **shared constant** in `push_worker.dart` so the screen's wording and the engine's rule cannot drift — and `serverRefused` otherwise, which is what a permanent rejection and an unreadable result both are. Nothing is inferred from the error text.
>
> **FK-Safe Ordering:** Queue entries are ordered by **entity dependency first** (config tables `courts`/`steps`/`case_types`/`on_behalfs` → `cases` → `case_history`/`delete_requests`/`conflict_log`), then by `created_at` within each group. Combined with the atomic `push_changes` RPC (which applies a whole batch in one transaction with correct internal ordering), this makes FK violations from queue reordering impossible.
>
> **Offline Compaction Matrix (per `entity_id`):**
> | Offline operations on the same record | Compacted to |
> |---|---|
> | `insert` + one or more `update`s | single `insert` with the latest snapshot |
> | `insert` + `delete` | **both dropped** — never pushed (the server never needs to know) |
> | `update`(s) + `delete` | single soft-`delete` update with the latest snapshot |
> | multiple `update`s | single `update` with the latest snapshot |
>
> Compaction must preserve the earliest `base_version`/`base_payload`, union the intentional `changed_fields`, retain the latest intended payload, and keep the stable logical `mutation_id` rules required for idempotency. **Never compact across an entity in `conflict_pending`:** freeze that entity's compaction, preserve all later queue entries in order, apply the returned server row as the new authoritative base, and three-way rebase later mutations when their changed fields do not overlap remote changes. If overlap or semantic ambiguity exists, leave the entity `conflict_pending` for user review; banner dismissal or a timeout never determines data correctness.

> **Delete-transition enforcement (trigger, not RLS):** Postgres RLS `WITH CHECK` sees only the *new* row — it **cannot compare OLD vs NEW**, so a policy like "`can_edit` for standard fields but `can_delete` when setting `is_deleted = true`" is unimplementable in pure RLS. Instead, a `BEFORE UPDATE` trigger on each soft-deletable table detects the delete transition (`OLD.is_deleted = false AND NEW.is_deleted = true`) and verifies the editor has `can_delete` in `firm_members`, raising an exception otherwise. RLS keeps the coarse row-access rules; triggers (and the `push_changes` RPC) handle field-level transitions.
>
> **Premium gate in RLS/RPC:** Wherever a policy or trigger needs to check premium entitlement, it derives it as `subscription_expiry (+ 48h grace) > now()` — never by reading `subscription_status` (see `profiles` schema note).
>
> **Firm-mode permission and scope (user ruling, owed as a migration):** INSERT is gated on `can_add` and UPDATE on `can_edit` by one `BEFORE` trigger per table (`cases`, `case_history`, `notes`, `case_references` and the six reference tables), reading the caller’s `firm_members` row — **both halves are new work**, since no `can_add_firm` helper exists and no INSERT path reads the flag today. The scope columns are server-owned: `firm_id` is written from the caller’s own firm when the row is created and never read from a payload, no client may change it on an existing row, and a caller who holds a firm may not create a firm-less row at all; `scope_owner_id` is written by the dissolve and by nothing else. That has to be stated because `push_changes` is `SECURITY DEFINER` and therefore bypasses the column privileges that guard direct PostgREST writes — it strips only `server_updated_at`, `version` and `last_modified_by` from a payload, so **any column added later is client-writable through the RPC unless it is named there**, and one accepted update would let an author null their own row’s `firm_id` and take the case out of the chamber’s ledger. The tier columns share the entitlement pair’s server-only status.
>
> **Firm-mode read scoping (owed as a migration):** the SELECT cells above carry the scoped form — the membership disjunct alone is not enough, because attribution is immutable and `user_id = auth.uid()` standing beside it under `or` still selects every row an author wrote in the chamber they left. The scope clause applies to `court_categories` and `case_categories` as well, which this table does not row out, and on `delete_requests` it is what keeps a dissolved chamber’s request history readable to the member who raised it. The reasoning and the leak chain are in Resolved Design Clarifications, "Removing A Member Wipes That Member’s Device Before Its Access Ends".

## Detailed Sync Plan & Multi-User Workflow

The synchronization architecture dynamically adapts depending on whether the user is operating individually or within a law firm (Chamber).

### 1. Multi-User/Firm Setup (Offline-First with Realtime Sync)
In multi-user chamber setups, multiple users interact with the same dataset. While real-time updates are preferred when online, the app is fully offline-capable.
- **Account Mode Detection (Individual vs Firm):** Every account starts as an **Individual Account** (`firm_id = null`, `role = 'individual'` in the user profile). The moment the main user adds any associate via `Settings > Accounts & Profile > Manage Associates`, the system creates a `firms` record, sets the main user's `role` to `'owner'`, links both profiles to the new `firm_id`, and transitions the account to a **Firm Account**.
- **Associate Deletion Policy (Delete Request Workflow):** Associates without `can_delete` permission **cannot directly delete records** from the app. Instead, when they attempt to delete a case, note, or reference, the action creates a **Delete Request** entry stored in the `delete_requests` table. This request appears as a notification/badge in the `Settings` dashboard (and optionally `Manage Associates` screen) of all firm members who have `can_delete = true`. A reviewer can tap the notification, view a snapshot of the item to be deleted, and choose to **Approve** (which triggers the soft-delete and sync) or **Reject** (which keeps the record and notifies the requester). Deletion permissions themselves can be granted or revoked at any time by the firm owner via `Settings > Accounts & Profile > Manage Associates`.
- **Offline Continuity:** If the internet connection is lost in Firm mode, the app continues to work as usual. All additions, edits, and deletions (if authorized) are saved to the local Drift database and queued in `sync_queue`.
- **Hybrid Lifecycle-Aware Foreground Sync:** The sync strategy is a battery-efficient hybrid that combines a smart delta pull on resume with Supabase Realtime WebSocket notifications while active, and micro-batched write-through (2–3 s coalescing window) on every local change. This gives near-real-time collaboration with zero background resource consumption:
  - **Smart Delta Pull on App Launch/Resume:** When the user opens or foregrounds the app:
    1. First check the local `sync_queue` for any pending unsynced items. If found, push them to Supabase immediately via the `push_changes` RPC (see §1.1).
    2. Then perform a targeted **delta pull** per synced table using a stable composite cursor **`(server_updated_at, id)`**, ordered ascending by both columns. Query rows satisfying `server_updated_at > cursor.time OR (server_updated_at = cursor.time AND id > cursor.id)` and page with a fixed limit until the page is short. `server_updated_at` is trigger-assigned—never client `updated_at`. The UUID tie-breaker prevents rows sharing the same timestamp from being skipped at page/cursor boundaries.
    3. **Cursor update (per-table, crash-safe):** Maintain an independent composite cursor for every table. After each page is fully committed to Drift in one transaction, persist that page's final `(server_updated_at, id)` in the same durable checkpoint flow; a crash may replay rows but cannot skip them. Do not advance before local commit. An empty page completes that table without inventing a device-clock cursor. For initial/full pulls, start at the minimum sentinel. Store the cursor map per device in the local database (preferred, transactionally adjacent to imported rows), not only in `SharedPreferences`; schema migration/reset must preserve or intentionally reset it. A single shared cursor is forbidden because pulls occur at different times.
    4. **Continuity-aware resume throttle:** Skip a resume pull within 60 seconds **only if the client can prove the same Realtime connection generation remained continuously subscribed since the last successful pull**. Any disconnect, channel error, authentication refresh/reconnect, process suspension with unknown continuity, connectivity restoration, or WebSocket reconnection forces an immediate per-table delta pull before the throttle may apply again. Broadcast is an ephemeral notification—not a durable event log—so uncertain continuity is always repaired through REST delta pull.
    5. **Clock-Skew Detection:** On each successful sync, compare device time against server time. If skew exceeds ~2 minutes, record the offset locally and show a non-intrusive warning: *"Your device clock appears incorrect. Please fix it to ensure reliable syncing."*
  - **Supabase Realtime — "Broadcast from Database" (Foreground Only, Notification Only):**
    The app does **not** use `postgres_changes` subscriptions. `postgres_changes` delivers the **full changed record** (not lightweight pings) and Supabase evaluates RLS *for every subscriber on every change* — this scales poorly and is why Supabase recommends **Broadcast** for production. Instead:
    
    - A Postgres `AFTER INSERT/UPDATE` trigger on each synced table calls **`realtime.send()`** with a tiny payload — just `{table, id}` — to a **private topic**: `firm:{firm_id}` for firm members, or `user:{user_id}` for individuals. Topic access is protected by Realtime authorization (RLS on `realtime.messages`).
    - The client keeps exactly **one** channel open, subscribed to its private topic. On receiving a `{table, id}` ping, the app performs a **micro delta pull** via REST for just the changed row(s).
    - This gives exactly the notification-only behavior the design calls for, at a fraction of the server cost: tiny frames over the socket, no per-subscriber RLS churn, and effectively unlimited firm-member scalability.
    
  - **WebSocket Reconnection Strategy (Exponential Backoff):**
    1. **Immediate attempt** on foreground resume (`didChangeAppLifecycleState == resumed`).
    2. **On failure:** Retry with exponential backoff: 1s → 2s → 4s → 8s → 16s → 32s (max interval).
    3. **After 6 failed retries** (~63 seconds), stop active retrying and rely on the **`connectivity_plus` stream**: the OS broadcasts connectivity changes, so the app reacts instantly when a network appears — **no periodic polling** (the old 30-second connectivity poll is removed; it wasted battery and reacted slower). The built-in `supabase_flutter` auto-reconnect handles transient socket drops; this backoff applies when foreground reconnect fails.
    4. **User-visible indicator:** After 3 consecutive failures, a subtle "Sync paused" status icon appears in the app header. Tapping it forces an immediate retry and resets the backoff counter.
    5. **Graceful degradation and gap repair:** During WebSocket absence, sync continues via REST push/pull on user actions and resume. Track a monotonically increasing local connection generation; after every reconnection or connectivity restoration, push pending changes and then force a per-table delta pull before declaring sync healthy. WebSocket loss therefore causes delayed notification, never an unexamined gap.
    
  - **Micro-Batched Write-Through on Local Action (2–3 s coalescing window):** When the active user performs any action (add/edit/delete a case, note, or reference), the change is saved to the local Drift DB first (for instant UI feedback) and enqueued. A **2–3 second micro-batch window** then coalesces all writes made in that window into **one** `push_changes` RPC call. Rationale: each HTTP request keeps the cellular radio in a high-power state for ~10–20 s afterward (tail energy) — a lawyer updating 25 cases after a court day would otherwise cause 25 radio wake-ups. The window is imperceptible to users, cuts radio usage by an order of magnitude, and *shrinks* the data-loss window because the batch is queued atomically in `sync_queue` on failure. If the push fails (no internet), the batch remains in `sync_queue` for retry on reconnection.
  - **Lifecycle Bounds:** The Realtime WebSocket channel is opened when the app enters the foreground (`WidgetsBindingObserver.didChangeAppLifecycleState == resumed`) and **immediately closed** when the app is backgrounded or the screen is locked. This ensures zero radio usage when the app is idle.
- **Automatic Re-sync:** Once a connection is re-established, the background `SyncService` pushes queued operations to Supabase in dependency-then-`created_at` order (see `sync_queue` FK-Safe Ordering note), then pulls remote changes.
- **Firm Mode Conflict Resolution (Optimistic Concurrency + Three-Way Reconciliation):** Each mutation submits `base_version`, `base_payload`, `changed_fields`, and `mutation_id`. `push_changes` accepts only an exact version match and assigns the next version. On mismatch it returns `conflict` with the authoritative row/version; device timestamps and editor UUIDs never choose a winner.
  - **On push conflict:** Mark the entity `conflict_pending`, freeze compaction for it, preserve every later queue entry, and log the rejected attempted payload in `conflict_log`. Apply the server row as the authoritative base, then three-way compare base/server/local changes. Disjoint field changes may be rebased into a new mutation against the latest server version; overlapping or semantically coupled fields require review.
  - **On pull conflict:** If a pulled row intersects pending local mutations, run the same three-way path rather than deleting pending edits. A pull never silently overwrites a queued mutation.
  - The conflict log is queued to its Supabase mirror for portability. A non-dismissible banner links to **Review Conflict**, showing server values, attempted values, and later preserved edits. The initial release may require manual field selection/copying for ambiguous conflicts, but the wire protocol and queue metadata must support `mergeable_conflict` from day one.
  - Banner dismissal or elapsed time never resolves data. Resolution occurs only through successful rebase/push, explicit user choice, or confirmed discard with authoritative rollback.
- **Online-Only Firm Administration (explicit rule):** Creating a `firms` record, generating/revoking invite codes, adding or removing associates, and changing associate permissions are **online-only operations**. These involve RLS-privileged multi-row server mutations (and the `join_firm` RPC), and supporting them offline invites nasty edge cases for near-zero benefit. The relevant screens (`Manage Associates`, invite generation) show a "Connect to the internet to manage your firm" state when offline. All *case data* operations remain fully offline-capable.

### 1.1 The `push_changes` RPC (Single Atomic Push Pipeline)
All sync writes go through **one Postgres RPC**—`push_changes(rows jsonb)`—instead of direct table upserts. For each logical mutation, the RPC:
1. **Optimistic concurrency:** Locks the target row and accepts an update/delete only when incoming `base_version` equals the current server `version`; inserts require no existing row. On acceptance the server assigns `version = current + 1` (or 1 for insert), `last_modified_by = auth.uid()`, and server time. Clients cannot submit the authoritative resulting version.
2. **Structured conflict response:** A mismatch returns `status = conflict`, the authoritative row/version, `mutation_id`, and enough metadata for three-way reconciliation. It never uses client timestamps or UUID ordering as a fallback.
3. **Atomic history:** When an accepted case mutation changes `next_date`, `last_step`, or `notes_results`, create the immutable `case_history` event in this same transaction using `source_mutation_id`, `base_case_version`, and `result_case_version`. Rejected mutations create no normal history.
4. **Deterministic per-mutation results:** Use one outer transaction and one savepoint per logical mutation, processed in dependency order. A permanent conflict/validation/permission failure rolls back only that mutation to its savepoint and returns a stable result; independent valid mutations may commit. A database/infrastructure error or violated batch invariant aborts the entire RPC. The response contains exactly one result for every submitted `mutation_id`, in input order, so the client never faces a partially unknown batch. Mutations explicitly linked as one domain operation (for example case update + generated history) remain atomic inside one savepoint.
5. **Permission and premium gates:** Re-check current `firm_members` permissions and derived premium entitlement before every applicable mutation. Return stable machine-readable rejection codes so clients can roll back provisional actions correctly.
6. **Idempotency:** Persist a receipt for every terminal mutation result. Retrying a known `mutation_id` with the same canonical request hash returns the original result and cannot increment version or duplicate history; reuse with a different hash returns `mutation_id_reused` and applies nothing.
7. **Tombstone and delete-request semantics:** Writes against soft-deleted rows return the tombstone. Delete requests targeting an existing tombstone return `already_resolved`, not a generic error.

One RPC round trip per micro-batch also delivers the D1 battery win (single radio wake-up per batch).

> **`mutation_receipts` (server-internal idempotency ledger):** Define `mutation_id UUID PRIMARY KEY`, `actor_id UUID NOT NULL`, `entity_type TEXT NOT NULL`, `entity_id UUID NOT NULL`, `request_hash TEXT NOT NULL`, `terminal_status TEXT NOT NULL`, `result_payload JSONB NOT NULL`, and `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`. `push_changes` inserts/reads this table in the same savepoint as the domain mutation. RLS exposes no direct client policies; only the RPC owner can read/write it. Retain receipts for at least the maximum supported offline window plus retry buffer (minimum 400 days), and never purge a receipt still referenced by history/conflict/audit records.

### 2. Upgrade Readiness & Initial Backlog Push (Free → Premium Transition)
> The former "Pre-Push Subscription Count Validation" section has been **removed**. Its premise was a multi-device race (two offline devices at count 49 each adding a case → 51). That race is **impossible**: free accounts never sync and are strictly single-device, and Firm mode requires premium. The only moments case counts and sync interact are the ones below.
- **Always Sync-Ready Architecture:** Even though the free tier never syncs, every local write on a free account still populates `sync_queue` and maintains all sync columns (`version`, `updated_at`, `is_deleted`, `last_modified_by`). The moment the user upgrades, the app is 100% ready to sync with zero migration.
- **Initial Backlog Push on Upgrade:** When a subscription becomes active, the `SyncService` reviews the accumulated `sync_queue`, compacts only eligible `pending` rows, preserves `conflict_pending` rows for review, and exposes `blocked` rows in Sync Status rather than silently clearing them. After user-confirmed retry/repair, it pushes FK-ordered micro-batches through `push_changes`, then performs a full pull. Permanent validation/permission failures remain visible and are never force-retried as ordinary backlog.
- **Free-Tier Case Limit (local enforcement):** The 50 non-deleted case limit is enforced **locally** at the "Add Case" flow with a paywall screen (see §6). Since free accounts never push, no pre-push validation is needed.
- **Server-Side Trigger Guard (defense in depth):** A Postgres trigger on `cases` still rejects INSERTs when the owner's derived entitlement is free and their non-deleted case count is ≥ 50 — catching stale or tampered clients. Because two concurrent inserts under READ COMMITTED could both read 49 and land at 51, the trigger takes `pg_advisory_xact_lock(hashtext(NEW.user_id::text))` before counting, serializing the count-and-insert. (This scenario is nearly impossible given single-device free accounts, but the lock is one line and makes the guard airtight.)
- **Downgrade Behavior:** After premium expiry (past the 48h grace window, §6/§7), sync stops but **no data is deleted**, the 50-case limit is **not** re-imposed on existing cases, and the account may still write up to the **allowance of the tier it last held** — Starter 100, Pro 250, Firm 500, Firm Plus 1,000 and Enterprise 2,000 cases, notes and case references, with the most recently updated rows writable and the rest read-only until renewal. A **downgrade** is timed differently from a lapse and takes effect at the **next renewal**, never mid-term: because the tier in force cannot be overwritten, a lower-tier purchase writes **`tier_pending`** and **`tier_pending_from`** beside it, and every gate derives the effective tier (see Resolved Design Clarifications, "The Tier Ladder Is Settled, And The Tier Is Stored").

### 3. Preventing Deleted Data Resurrection (Zombie Data Mitigation)
To prevent older, offline/inactive devices from restoring cases that have been deleted by other users:
- **Soft Deletes (Tombstones):** Hard deletes are avoided. Deletion marks `is_deleted = true` and updates the `updated_at` timestamp. Soft-deleted rows persist on Supabase for **365 days** as tombstones, then are purged by a scheduled DB function.
- **Server-authoritative resurrection guard:** Normal clients cannot write synced tables directly; `push_changes` is the sole mutation path and locks the current row. If the authoritative row is already soft-deleted, the RPC returns `status = 'tombstone'`, the current row/version, and the submitted `mutation_id` without applying or incrementing anything. A narrow `BEFORE UPDATE` defense-in-depth trigger rejects `OLD.is_deleted = true AND NEW.is_deleted = false` unless a separately audited administrator recovery RPC sets a transaction-local authorization flag. The trigger never compares client timestamps, client versions, or editor UUIDs.
- **Client Pull Phase:** If pulled data contains `is_deleted = true`, the client applies the authoritative tombstone locally and hides the record from normal UI queries. If no local mutation is pending, related completed queue entries may be resolved. If pending/later edits exist, preserve them, mark the entity `conflict_pending`, attach the tombstone as `server_payload`, and require explicit rebase/copy-to-new-record or confirmed discard; never silently delete queued work.
- **Client Push Phase:** If a client pushes a modification to a row the server has marked deleted, the server returns the tombstone. The client applies it locally and follows the same reconciliation path: resolve only the rejected mutation after recording the conflict, while preserving later queue entries until explicit resolution.
- **Cascade Soft-Deletes:** An accepted case delete soft-deletes related server `case_history` rows inside the same `push_changes` transaction, assigning each changed child a new server version and `server_updated_at`; server code never writes a device-local `sync_queue`. The originating device applies the returned parent/child rows locally, while other devices receive them through delta pull/Realtime pings. If the local delete was created offline, the client may stage child tombstones for immediate UI consistency, but they are marked derived and reconciled to the server-returned versions rather than pushed as independent mutations. This prevents orphaned history and double version increments.
- **UI & Cleanup:** All UI queries add `WHERE is_deleted = 0` filter. Local soft-deleted records are purged from the device's Drift DB after **90 days** — but **only if their deletion has actually reached the server**: purge requires `synced_at IS NOT NULL AND synced_at >= updated_at`. Without this guard, a tombstone created during a long offline stretch could be purged before it ever synced, losing the deletion — the record would then resurrect from the server on the next pull.
- **Extended Offline Period Reset (per-device, 335 days, firm mode only):** The offline-gap check is **per-device**, not per-user. Comparing against `profiles.last_successful_sync_at` would be defeated by any *other* device keeping the column fresh — e.g., the owner's phone syncs daily while their old tablet sits offline 200 days; the tablet's gap would never be detected, and it is exactly the device the check exists for. Instead, each device keeps its own `last_successful_sync_at`, written by the delta pull into the durable local `sync_metadata` table (the Revision 2.4 Addendum's placement, superseding the earlier `SharedPreferences` note), and checks it on reconnect. The threshold is **335 days** — safely under the 365-day server tombstone retention (a device offline less than that can still sync correctly, since all tombstones it needs are still on the server), with a 30-day buffer before purge. **The lock applies in firm mode only** — an individual account is never locked, because a solo diary has no other writer whose deletions could be resurrected (see Resolved Design Clarifications, "Extended-Offline Recovery Lock Applies to Firm Mode Only"). When a device in **Firm mode** reconnects after ≥ 335 days offline:
  1. In one durable local transaction, set persistent `extended_offline_recovery_required = true` **before** export or network work, pause push/pull workers, and wait for any already-started local write transaction to finish. While this flag is set, repositories reject every mutation and the UI disables editing/FAB actions with a recovery-required message. The lock survives process termination.
  2. **Automatic safety export under the lock:** Export the complete local Drift DB plus all pending/blocked/conflicted `sync_queue` rows and metadata to the versioned Backup & Restore JSON format. Record archive path, checksum, and completion state. No post-export mutation is possible.
  3. Show a blocking warning: *"You have been offline for [X] days. Your local changes have been saved to [path]. Fresh data must be loaded from the server before editing can continue."*
  4. If the user selects:
    (a) **Proceed:** verify the export checksum, clear firm-shared local tables and queue, perform a full authenticated pull, commit the fresh database, then clear `extended_offline_recovery_required` and re-enable mutations. If any step fails, keep the lock and retry safely.
    (b) **Close:** terminate/leave the app locked without cloud writes. On every next launch, restore the blocking recovery flow; do not permit read-write use until recovery succeeds.

### 4. Individual Setup (Offline-First, Queue-Based Sync)
For solo practitioners, the application operates fully offline.
- **Drift First:** All inserts, updates, and soft deletes occur in the local Drift SQLite database.
- **Sync Queue:** Each action generates a row in `sync_queue`.
- **Background Worker:** When an internet connection is established, the `SyncService` processes the queue (compacted, FK-ordered, serialized FIFO) and pushes micro-batches through the `push_changes` RPC.
- **Conflict Resolution (Optimistic Concurrency):** If a premium individual logs in on multiple devices, conflicts use the same exact `base_version` validation, structured server-row response, queue preservation, and three-way reconciliation as Firm mode. Client timestamps and editor UUIDs never decide acceptance.
### 5. Local Database Security & Account Switching
To ensure data security and prevent cross-contamination when users switch accounts on the same device, the local Drift SQLite database and `sync_queue` are completely wiped whenever a user actively logs out. **The logout flow branches by plan and connectivity — a single "mandatory sync before wipe" rule would deadlock free users (who have no sync at all) and offline premium users (who cannot sync), leaving them permanently unable to log out:**
- **(a) Premium + online:** If `sync_queue` has pending rows, a mandatory sync with Supabase is performed. Only after the sync completes successfully does the app wipe the local data and complete the logout.
- **(b) Premium + offline:** Logout is blocked with *"Connect to the internet to sync your changes first."*, alongside an explicit **"Log out anyway"** option. Tapping it shows a warning: *"Some data haven't finished syncing to cloud yet. Logging out now will result in those unsynced data being discarded."* with **Proceed** and **Close** buttons. **Proceed** → the app then **offers** the safety copy (below), and on **Yes** writes it before the wipe — in exactly the same manner and format as `Settings > Backup & Restore > Backup to Local Storage` — with clear messaging: *"Your data has been backed up to [path]. You can restore it after logging back in."* **Close** → the logout flow is cancelled.
- **(c) Free users:** The app **offers** the safety copy (below), and on **Yes** backs the data up in the same manner and format as `Settings > Backup & Restore > Backup to Local Storage`, with the same *"Your data has been backed up to [path]. You can restore it after logging back in."* message. Then the wipe proceeds.
- **The safety copy is offered, never mandatory (0.0.398 — user request).** Every branch that would otherwise auto-export first opens one window — titled **Backup Data to Local Storage**, with **Yes** and **No** centred and sized like the Exit App? window (112x48 at 16 pt). **Yes** writes the copy (asking for the passphrase only when Encryption On Backup is enabled; a dismissed passphrase window still cancels the logout and deletes nothing), and **No** wipes with no copy. A dismissed window (barrier or system back) cancels the logout, as the app's other confirmations do. The window is **not shown at all** when the wipe trades away nothing: a **premium account whose work is already on the server** (its queue empty, or its mandatory sync completed), or a **free account holding nothing the user authored** — no case, note or case reference, and no added/edited court category, case category, court, on-behalf, step or case type (`is_custom` or `is_user_modified`). A row the user added or edited in those six reference tables counts as their work even with no case on the device.
- **A completed logout lands on the Login screen (follow-up).** Whichever branch runs, once the session has actually ended the user is shown the app's single sign-in screen. It is an **explicit** navigation, not the router's sign-in gate: that gate is decided once per launch, so a device already signed in is never re-gated mid-session, and without this a signed-out user would be left on the now-empty Settings surface. A cancelled branch (a declined offline block, a closed warning, a dismissed passphrase) changes nothing and navigates nowhere.

This guarantees that local data is tightly bound to the current Supabase `auth.uid()`. When a new user logs in, they start with a fresh database and perform an initial pull from Supabase (premium) or a fresh local database (free).
- **A wipe leaves a fresh install's database, and an account switch wipes too (0.0.400 — two reported device defects).** (a) The complete wipe takes the seeded reference data and its `seed_migrations` ledger with everything else, and `SeedMigrationRunner` runs only when the database is **opened**, so a logout in the middle of an app run left the next account on that device with no court categories at all — an Add Case form whose Court Category, court names, case categories, case types, steps and on-behalfs were empty while the static Higher/Lower Court, Division and District dropdowns still showed. The wipe is therefore one named operation, `BackupRepository.wipeToFreshInstall` (the complete scope, then the baseline seed migrations), so no caller can wipe without restoring what an install starts from; extended-offline recovery keeps its own order because it re-seeds between its wipe and its authoritative pull. (b) The wipe was reachable **only** through the Logout button. A session the server revoked, one that expired, or one that could not be parsed back at all runs no logout flow and clears nothing — which is deliberate for a rejected session, but a later sign-in **as a different account** then opened the diary onto the previous holder's cases, notes, reference rows **and** their `sync_queue`, so the header counted work with no owner on that device while `IdentityAdoptionService` refused to hand the rows over. The account switch — plan §5's own rule above — now runs that same wipe before the arriving account is adopted, from the moment `AuthViewModel._completeSignIn` sees a different account id arrive. **(0.0.401)** The wipe's deletes go through Drift's table API (`db.delete(table).go()`), never `customStatement`: raw SQL removes the rows from the file but tells no query stream, so a device whose database was already clean still showed the previous account's pending count on its header and its queued mutation on Sync Status for the rest of the app run. Each table's streams are invalidated as every other writer in the app does; only `restoreSnapshot` keeps raw deletes, and it has its own reload lever (the restore screen re-opens the database).
- **Offline Session Expiry (never gates local data):** Supabase access tokens expire in ~1 hour and refreshing requires network. The app **never blocks local DB access on JWT validity** — an offline lawyer must always reach their diary. If a token refresh ultimately fails while online (e.g., revoked session or changed password), the app requires re-login, but **never wipes local data while `sync_queue` has pending rows** — the re-login path routes through the branched logout flow above so unsynced work is synced, exported, or explicitly discarded by the user, never silently lost. **A third way a session ends needs the same treatment.** A persisted session that cannot be parsed back into one at all (`SignOutReason.sessionMissing` — corruption rather than rejection, and raised before any request is made) requires a sign-in exactly as a rejected refresh token does. Reading only the rejection left such a device falling through to *offline, token stale*, which by design shows nothing: the diary opened as usual, the sync was dead for good, and the user had no prompt and no reason to ever sign in again. Both reasons are now decided in one place, `authSessionNeedsSignIn`, and a deliberate sign-out is deliberately not one of them.
### 6. Subscription Enforcement (Free vs Premium Sync)
- **Free Plan:** 50-case limit applies to `is_deleted = false` records only. Soft-deleted cases are excluded from the count. If a user hits 50 live cases, the "Add Case" flow is blocked with a paywall screen. Online Sync is only available in the premium plan; it is disabled from the very beginning for the free plan, meaning all data remains strictly local. The free plan is strictly individual and single-device (Firm mode requires premium).
- **Premium Entitlement Is Derived, Never Stored:** There is no trigger that can fire *at the expiry instant* — expiry is a moment in time, and triggers need a write. A stored `subscription_status` flag therefore inevitably goes stale. Instead, premium entitlement is **always computed** — on the client, in RLS policies, and in the `push_changes` RPC / server triggers — as: `subscription_expiry + 48h grace > now()`. No cron job, no stale-status bugs. The `subscription_status` columns on `profiles` and `firms` are retained for display/analytics only and are never consulted for authorization.
- **Premium Plan:** On app init or reconnection, the app computes entitlement from `profiles.subscription_expiry` (or the firm's, below). If valid, sync is authorized.
- **Entitlement Is Settled Before The Gates Read It.** Entitlement is derived from the **cached** `profiles` row, so any gate that reads it before that row exists answers *free* — which is how a premium account was shown `Subscription: Free` beside `Plan: 1 Month` (the plan comes straight from `payment_submissions`), refused in Online Sync with *"Premium is required to sync across devices"*, and left saying *Last Sync: Never* because the engine's own `_isEntitled` check made `syncNow` return **silently** with no retry scheduled. Three consequences to hold to. **(a)** The account refresh also runs **as soon as a session appears**, not only on launch/resume/reconnect: `AccountRefreshScope` mounts once above the router, so a sign-in on a running app is its own moment and is triggered by a change of account id. **(b)** A gate must distinguish *unknown* from *free*: `entitlementKnownProvider` is false until the cached row lands, and both the Subscription row and Online Sync say nothing (a dash / *Checking Your Subscription…*) rather than claiming Free. **(c)** The engine never re-tries a run it refused, so the **false → true entitlement transition** is what re-issues the delta pull (`SyncTriggerScope`), which is the only automatic repair that does not wait for a resume, a reconnect or a local write.

### 10. Bullet-proof Notification System (Upcoming Case Alerts)
- **Core Mechanism:** Combines `flutter_local_notifications` (for high-importance UI banners) and `android_alarm_manager_plus` (using `setExactAndAllowWhileIdle`) for precise background alarm firing. No persistent Foreground Service notification is used, as it disturbs users.
- **Settings Configuration:** Alerts are configured via `Settings > Notifications` with two key parameters stored in `SharedPreferences`:
  - `notification_time` (String/TimeOfDay, e.g., "08:00"): The daily time the notification is triggered.
  - `notification_day_offset` (Integer, e.g., 0 = same day of hearing, 1 = 1 day before hearing, 2 = 2 days before hearing).
- **Scheduling Logic & Interactivity:** A daily background job queries the local Drift SQLite database for any case having `next_date` that matches the configured offset. If found, it schedules a high-priority system notification containing the case number, parties, and court name. **When the user taps the notification, the app navigates directly to the Detail View of that case.**
- **OEM Battery Killer Mitigation (Critical for Bangladesh Market):** The Bangladeshi smartphone market is dominated by Xiaomi (MIUI), Oppo (ColorOS), Vivo (Funtouch OS), and Realme (Realme UI). These OEMs have aggressive battery management systems that completely ignore standard `AlarmManager` calls and kill background isolates — meaning standard notifications will silently fail on the majority of target devices. To counter this:
  - **OEM Detection on First Launch:** On the first launch (and accessible via `Settings > Notifications`), the app reads `Platform.localeName` and `device_info_plus` to detect the device manufacturer.
  - **Localized Setup Guide UI:** A localized, step-by-step "Battery Optimization & Auto-Start Guide" screen is shown to the user, instructing them to manually:
    1. Enable **"Auto-start"** for the app (required on Xiaomi/MIUI, Oppo/ColorOS, Vivo).
    2. Set Battery Optimization to **"Unrestricted"** / **"No restrictions"** for the app.
  - **Deep Links to OEM Settings:** Where possible (using platform `Intent` calls via `android_intent_plus`), the guide includes a "Take Me There" button that uses deep link Intent URLs to jump the user directly to the specific OEM battery or auto-start settings page, eliminating guesswork.
  - **Reminder:** If the user skips the guide, a persistent non-intrusive banner is shown in `Settings > Notifications`: *"Notifications may not work reliably on your device. Tap to complete setup."*
- **Exact Alarm Permission (Android 12–14+):** `setExactAndAllowWhileIdle` requires the `SCHEDULE_EXACT_ALARM` permission, and **Android 14 denies it by default for new installs**. The app must:
  1. Detect at runtime whether exact alarms are permitted (`canScheduleExactAlarms`).
  2. If denied, deep-link the user to the system "Alarms & reminders" grant screen — this integrates naturally into the existing OEM Setup Guide UI above.
  3. If the user refuses, **fall back to inexact windowed alarms** (`setWindow`/`setAndAllowWhileIdle`) so notifications still fire, just with minute-level rather than second-level precision.
- **Boot-Time Rescheduling:** `AlarmManager` schedules **do not survive a device reboot**. The app registers a `BOOT_COMPLETED` broadcast receiver that re-schedules the daily notification alarm after every reboot (and after app updates via `MY_PACKAGE_REPLACED`).
- **Platform Abstraction (Windows Port Prep):** All notification scheduling, alarm management, and OEM battery-guide logic is accessed through a **platform-abstraction interface** (e.g., `NotificationScheduler` with `AndroidNotificationScheduler` / future `WindowsNotificationScheduler` implementations). `android_alarm_manager_plus`, `android_intent_plus`, and the OEM guide are Android-only — isolating them behind an interface now means the Windows port swaps implementations instead of rewriting call sites.

### 10.2 Admin Payment Alerts (Push — Administrator Only)
- **Why a second notification path exists:** §10 is the *hearing* reminder — a local alarm over the local database, no server involved. An administrator also has to learn that a payment request is **waiting for approval**, and the only shape that is a real notification is one that arrives while the app is closed. That needs a push sender, so this is the one place in the app where the message comes from outside it.
- **Firebase Cloud Messaging, and nothing else.** Google lists FCM as **No-cost** on the free Spark plan (no credit card, no Blaze), and every hosted alternative (OneSignal, Courier, Pusher Beams, Novu) delivers Android *through* FCM — so each would add a vendor, an SDK and a dashboard without removing the Firebase project. The app reuses the **existing** Cloud project `38386857573` (setup walkthrough: `docs/firebase_fcm_setup.md`), and `android/settings.gradle.kts` declares the `com.google.gms.google-services` plugin. The transport lives behind **one boundary file** (`lib/core/push/push_gateway.dart`) — the same rule the alarm and notification packages follow behind `android_notification_gateway.dart` — so the Windows port replaces one file.
- **What a tap does (0.0.500).** The line carries the app's own payload marker, and **one** pure resolver (`notificationPayloadRoute`) turns a notification payload into a screen — the panel's Payment Requests page for the count, a case's detail view for a hearing alert — read by the tap listener while the app runs and by the router when the tap is what launched it, so the two can never disagree. A legal-looking payload stays a case id, so no earlier alert changed destination.
- **The message is numbers, never words.** The sender posts a **data-only** message `{pending, alert}`; the client composes the sentence from the ARB files and writes the count in the active language's own digits, so one message reads correctly in English and in বাংলা. The device's only other read on that path is the language already stored in `SharedPreferences`.
- **One line, replaced in place.** Ten pending requests read as **one** notification that is rewritten as the total moves, not as ten notifications; a total of **zero cancels** it rather than announcing zero. The arrival (0 → n) is the only one that earns sound, vibration and high importance; later corrections are quiet (`onlyAlertOnce`), and the sender gives an arrival a high-priority wake. The same line is posted whether the app is open, backgrounded or closed (user's decision), so there is no second behaviour to explain.
- **It is local work.** The foreground listener and FCM's background isolate both call the one function `applyPaymentAlert`, which posts through `AndroidNotificationGateway` and does nothing else — no network call, no database open, no Supabase init. That is what keeps a push handler's cost at one notification, and `test/core/push_local_only_test.dart` guards it at source level the way `notification_local_only_test.dart` guards the daily job.
- **Whose phone is registered.** Only a **confirmed administrator's** device. `AdminPushScope` asks `is_app_admin()` through the existing admin repository and writes the FCM token into `device_tokens` only when the answer is yes: on launch, on a session that arrives while the app runs (keyed on the account id, which also covers a switch), and again whenever FCM hands the device a new token. `AuthViewModel.signOut()` deletes the row **before** the session ends — best-effort, and remembered in the error log — because the row is the device's own to delete only while it is still signed in; the row's primary key is the token, so a device that changes hands is reassigned rather than feeding two accounts.
- **The user's switch.** `Settings > Notifications` gains **Admin Panel Notification** (renamed from *Payment Request Alerts* — 0.0.512, user request) (ON/OFF), shown only to a confirmed administrator, stored as `user_preferences.payment_alerts_enabled` (per-user, never firm-shared, default **on**) and **synced**, because the sender reads that column itself and skips an account that switched it off — which is what makes the switch work while the app is closed. Turning it on asks for the OS notification permission when the app does not already have it, the same question `Send Test Notification` asks.
- **The device half, confirmed (0.0.504, the user's two-phone test).** One phone submitted a payment request and the administrator's phone received the line, which is the only shape of proof this feature can have — the sender is outside the app and delivery is outside both test suites. ### 12.3 Power & Sync Efficiency (Battery Conservation)
- **Foreground WebSocket Sync (Broadcast Ping Channel):** The Supabase Realtime WebSocket connection is active only when the app is in the foreground, carrying **only tiny "Broadcast from Database" `{table, id}` pings** on the private firm/user topic (see Sync Plan §1) — smaller frames over the socket and zero per-subscriber RLS churn, which itself is a battery win. When the app is backgrounded or the screen is locked, the channel is immediately disconnected. On returning to the foreground, the connection is re-established.
- **Micro-Batched Write-Through (2–3 s Coalescing Window):** Every local write (add/edit/delete) is saved to the local Drift DB first for instant UI feedback, then coalesced with any other writes made within a **2–3 second micro-batch window** into **one** `push_changes` RPC call (see Sync Plan §1). Rationale: each HTTP request keeps the cellular radio in a high-power state for ~10–20 s afterward (tail energy), which dwarfs the payload cost — a lawyer updating 25 cases after a court day would otherwise cause 25 radio wake-ups. The window is imperceptible to users, cuts radio usage by an order of magnitude, and *shrinks* the data-loss window because the whole batch is queued atomically in `sync_queue` on failure. This is the single biggest battery win in the design.
- **Sync Queue Compaction:** If multiple unsynced local edits occur on the same database record offline, the sync queue processor collapses them per the **Offline Compaction Matrix** (see `sync_queue` schema note), pushing only the latest snapshot state and reducing network requests.
- **Event-Driven Connectivity (No Polling):** The app never polls for connectivity. It subscribes to the **`connectivity_plus` stream** — the OS already broadcasts connectivity changes, so the app reacts instantly when a network appears, at zero polling cost (see Sync Plan §1 WebSocket Reconnection Strategy).
- **Continuity-Aware Resume-Pull Throttle (60 s):** Rapid app switching may skip a delta pull within 60 seconds only when the client proves the same Realtime connection generation remained continuously subscribed since the last successful pull. Any disconnect, reconnect, auth refresh, connectivity restoration, process suspension, or unknown continuity forces an immediate per-table delta pull before sync is declared healthy (see Sync Plan §1).
- **A User-Controlled Sync Switch, Cleared By A Restart (0.0.469, user request):** the Online Sync screen carries its own **Disable Sync / Enable Sync** card — at the foot of the screen, below the *Pending Sync* entry, so it cannot be read as a second way to sync. Both directions are the same **filled dark button with a white label** (0.0.470, user request: white ink needs the fill, the card behind the button being white too), so turning sync off is offered as plainly as turning it back on. Off is a **pause**, not a setting: the flag (`syncEnabledProvider`) lives in memory for this app run only and is deliberately never persisted, so a restart is the second way back besides the button. While it is off the app makes no request at all — `SyncService.syncNow` (which every trigger funnels into: launch, resume, reconnect, a local write, and the screen's own Sync Now), `_drainRealtimePings` and `runBacklogPush` each refuse *before* a transport is built and arm no retry, and `SyncTriggerScope` closes the Realtime channel at once, holds it closed and skips the recovery check, so a paused device neither sends, receives nor holds a socket. Turning the switch back on rejoins the channel, re-runs the recovery check and asks for the delta pull it missed. The screen states it as a choice rather than a fault: its own **Sync Off** pill and body, Sync Now disabled with the reason beneath it, and entity rows marked *Not synced* in muted ink instead of the error red.
- **Purely Local Background Operations (Enforced Rule):** All background services — including alarm manager triggers for notifications and any scheduled tasks — must run **completely locally** against the Drift SQLite database. **No background network calls, no GPS operations, and no Supabase requests are permitted from background isolates or background tasks.**
- **Rendering Optimization:** Using Riverpod's `.select()` modifier to listen only to the specific properties needed, avoiding unnecessary rebuilds. Listings use pagination (`limit` and `offset`) to avoid loading large datasets into RAM.

### 12.3.1 Security, Local Database Encryption & Sensitive Exports
- **Database-at-rest encryption required:** Legal case data must not ship in plaintext SQLite. Use a maintained SQLCipher-compatible Drift backend for full-database encryption so ordinary `LIKE`/FTS queries continue to work after the database is opened; do not implement deterministic per-field encryption for searchable legal text. Validate Android and planned Windows support with an integration test before locking the package choice.
- **Key management:** Generate a random per-installation database key, store it only in Android Keystore-backed secure storage (and the OS credential vault on future desktop platforms), never in SharedPreferences, source code, logs, analytics, or synced tables. Redact keys and sensitive payloads from crash reports. Define explicit behavior for secure-storage/key loss: never silently create a new empty database over an unreadable encrypted file; offer authenticated cloud restore or user-selected encrypted backup recovery.
- **Lifecycle hardening:** Clear sensitive in-memory state on logout/account switch, require the account-switch wipe described in §5, disable Android auto-backup for raw database/secure-key files unless an encrypted restore design is verified, and prevent sensitive screen contents from appearing in app-switcher snapshots where platform support allows. **The in-memory state is not only what a wipe can reach (0.0.394):** an account-scoped **live read** — this account's payment history, the admin panel's status and its queue, and a firm owner's roster and invite codes — is a server read held by a Riverpod provider, so it outlived both the branched logout's database wipe and `signOut`, and the next account on the device read the previous holder's rows: a non-admin was shown the Admin Panel, and *Payment History* was somebody else's ledger. **(0.0.505 — reported) The same dropping had a hole at the *arriving* end, and it hid the panel from its owner.** `signOut()` ends the session **before** it invalidates those reads, so a screen still watching `adminStatusProvider` re-asked at that instant with no JWT — and `isAdmin()` answers **false** on any failure by design (the panel must never flash), which is indistinguishable from a genuine non-admin. That `false` outlived the sign-out, because signing back in as the **same** account is not an account switch: the logout has forgotten the remembered id, so `_completeSignIn`'s switch branch runs nothing and no read is re-asked — the admin's drawer row, bottom tab and View Settings entry stayed gone until the app was restarted. The four account-scoped reads are now re-asked on **every completed sign-in** as well as on the way out, through one private helper (`_reaskAccountScopedReads()`) that drops only the live reads and never local rows, so the switch wipe and the per-user cache clearing remain gated on a real switch and a cold start or token refresh still drops nothing of the account's own. `AuthViewModel._forgetAccount()` now drops all four, together with the SharedPreferences profile record, as one *the account is leaving* operation, and it runs on the Logout button **and** whenever a sign-in arrives as a different account id — the path a revoked or expired session takes, which clears nothing on its own. A cold start, or the same account arriving again, drops nothing.
- **Backups and diagnostics — encryption is opt-in, off by default (revised):** Safety exports and user backups containing case data **can** be sealed with an authenticated format (versioned header, KDF parameters, nonce, ciphertext, authentication tag, checksum) using a user recovery secret. **Encryption is off until the user turns it on** in Settings > Backup & Restore > Encryption On Backup, so a fresh install writes the readable versioned JSON envelope, asks no passphrase, and restores it back without one; the restore path opens either kind and prompts for a passphrase only for an encrypted container. A sealed export is still never placed in shared storage without that explicit choice. Diagnostic bundles default to metadata only, and including queue/case payloads still requires explicit consent; the bundle follows the same preference (sealed when encryption is on, readable JSON when off) with a visible expiry/deletion reminder.
- **Dialogue-free backups into a diary folder (0.0.446, user request):** "Backup to Local Storage", "Backup as Excel File" and "Backup to Google Drive" no longer open a "Save to…" dialog — they all write automatically into the diary's backup folder, named **`Backup_dd-mm-yy_hh-mm-ssam/pm.<ext>`** (local civil date/time; `.lcbak` container or `.xlsx` workbook). The Drive action then offers the share sheet (Google Drive is a target), attaching the real public-folder file directly — the `ShareableBackupSink` that once copied a `content://` result into the cache is gone, because every backup is now a real path. The private automatic safety exports (`LocalArchiveSink` → `<documents>/backups`) are unchanged.
- **The diary folder is the public Downloads directory (0.0.446 correction, user request):** the first attempt used the app's private documents directory, which resolved to `/data/user/0/com.legalcasediary.app/app_flutter/LegalCaseDiary` — invisible and unnavigable, exactly what the user did not want. path_provider's Android paths are all app-scoped (`Android/data/<pkg>`), so the true public folder is answered by a small host channel (`com.legalcasediary.app/public_downloads` → `Environment.getExternalStoragePublicDirectory(DIRECTORY_DOWNLOADS)`), yielding **`/storage/emulated/0/Download/LegalCaseDiary`** — visible in a file manager and over USB, writable directly by the app (its own files) under scoped storage with no permission. Where the channel is absent the resolver falls back to the private documents directory. The automatic safety exports stay private.
- **Automatic Backup runs its own local scheduler (0.0.448, user request):** the Backup & Restore screen's Automatic Backup section (Off / Everyday / Every 3 days / Every 7 days / Every month) previously only *stored* `backup_schedule_days` and executed nothing. A new scheduler mirrors the notification one: `lib/core/backup/` holds pure rules (`BackupSchedule.isDue`, `decideBackupJob` → `disabled | encryptionOnSkips | run`), the `@pragma('vm:entry-point')` job (`backup_alarm_callback.dart`), and `AndroidBackupScheduler` arming a **daily, self-re-arming** alarm through the notification gateway's helpers (own id base clear of the alert range, `rescheduleOnReboot: true`). Armed on launch (`BackupSchedulerScope`), re-armed on a schedule change, cancelled on logout/account switch. The write happens **before** the sweep, so a failed write leaves yesterday's file in place rather than none. The sweep keys on the automatic stem, so a manual backup — which a user chose to keep and which shares the folder — is never touched. **`backupFileNamePattern` had to accept the new stem**, because a restore lists the folder through it: a name it rejected would have made the automatic backup invisible to Restore and defeated the feature.
- **A restore belongs to the account that made it (0.0.472, user request):** a backup's envelope names no owner, so any account could restore any file — and the rows it brought named somebody else, so the next sync refused them. `core/backup/backup_ownership.dart` (pure: no Flutter, no Drift, no file system) now classifies a file's rows against the identity restoring it. Every portable table's owner column — `user_id`, or `requested_by` where the schema names it that way — is read from the **live schema**, with `firm_id` where the table has one, so a renamed or added column cannot leave the check looking at something that is not there. A row counts as this device's when its owner is the device's own identity (**the bound account after sign-in, or this device's pre-account placeholder before it** — the same value every local write is stamped with) **or** its firm is a firm this device belongs to; one row naming any other account refuses the whole file with the new `BackupRestoreFailure.anotherAccount`, which Backup & Restore shows in its own sentence. The check runs when the file is opened and again before the transaction — **ahead of the replace question** — so a refused file is never offered the chance to wipe the diary and never touches the database. **The one relaxation is the hand-filled sample workbook:** an owner cell that is blank, or holds text no id can be (`user_id`, `example-court-id`, a name typed by hand), names nobody, so that file restores and `stampRowOwnership` writes this device's identity onto those rows — which is what makes the sample the user typed their own cases into syncable instead of orphaned. A row that already names somebody keeps its owner, its firm scope and its attribution: a firm's rows are shared, so an associate's own backup is accepted and its authors are not rewritten. Refusing is deliberately stricter than accepting, and one case is recorded rather than accidental: another device's **pre-account** backup is refused too, because its placeholder is a different person as far as the server is concerned.

Support moved from this page to the **Settings main page's App Info group** — it is the entry a blocked user reaches for.)** The check reads the **public GitHub releases API** (`Asadusjaman-Sazal/legal_case_diary_flutter`, tag `v<version>`, asset `Legal.Case.Diary.v<version>-ARM64.apk` — the workflow sets a name with spaces and GitHub turns them into dots as it stores the file, so the published asset a user downloads reads with dots) through the stdlib `dart:io` `HttpClient` — no auth token, no new dependency — and compares the tag against `appVersion` (`data/update_release.dart`, pure). **Battery discipline is the point of the section's placement here:** `UpdateCheckScope` runs the check **once per process, after the first frame**, only when `isUpdateCheckDue` (frequency elapsed) says so, and never schedules, polls, or re-runs — no background isolate, no alarm, no network from a background task, which keeps §12.3's purely-local-background rule intact. Offline is not an error: the day is counted toward a **consecutive-offline streak**, the first seven are silent, and the **eighth** shows one *connect and check* toast (**once per streak**; a successful online check resets the streak). The install is a deliberate platform handoff — `MainActivity.kt` resolves the cached APK through a `FileProvider` (`${applicationId}.apkprovider`, `res/xml/apk_paths.xml`) and fires `ACTION_VIEW` with `application/vnd.android.package-archive`, needing `REQUEST_INSTALL_PACKAGES`; Android shows its own installer confirmation. **(0.0.508, user-reported bug)** The cache copy is **not** deleted at the handoff: `startActivity` only *dispatches* an intent and Android's installer opens the content URI afterwards, so deleting the file in that gap was one of the two causes of the reported "selecting *Package Installer* does nothing". It is deleted at the **next launch**, once the app is running the offered version (the install landed) or the offer has gone. The other cause is the URI grant: this intent resolves to several activities, so Android shows a **chooser**, and a chooser does not forward `FLAG_GRANT_READ_URI_PERMISSION` to the app the user picks — the installer was handed a `content://` URI it could not read. The grant is therefore issued **per resolver** (`queryIntentActivities` + `grantUriPermission`), and the manifest's `<queries>` declares the `VIEW` + `application/vnd.android.package-archive` intent, without which Android 11+ package visibility leaves that resolver list empty and the grants never happen. Both halves are pinned by source assertions in `test/features/update_install_test.dart`, since the install runs in Kotlin and no widget test can drive it. The downloaded size is verified against the release's stated asset size before installing, so a truncated download never reaches the installer.

## Revision 2.4 — Alignment Decisions and Complete Data Contracts

The following decisions are authoritative wherever an earlier section is ambiguous. Task files 00–22 must implement these rules without inventing alternatives.

### 1. Table classification and scope

- **Push/pull domain tables:** `cases`, `case_history`, `notes`, `case_references`, `court_categories`, `case_categories`, `courts`, `steps`, `case_types`, `on_behalfs`, `delete_requests`, and `conflict_log`. - **Firm-shared editable reference data:** `court_categories`, `case_categories`, `courts`, `steps`, `case_types`, and `on_behalfs`. Built-ins use deterministic IDs. Firm members share firm-scoped customizations; individuals use user-scoped customizations.
- **Pull-only local caches:** authenticated `profiles`, `firms`, and `firm_members`. They are refreshed from the server and are never uploaded by the generic domain queue.
- **Per-user preferences:** language, theme/view configuration, navigation configuration, notification enabled/time/default offsets, backup-nudge metadata, and related settings. They are never firm-shared. They persist in a local `user_preferences` table keyed by user identity; premium accounts may sync them through a dedicated user-scoped server preference row protected by self-only RLS.
- **Local operational state:** `sync_queue`, per-table pull cursors, `seed_migrations`, and `sync_metadata`. `sync_metadata` stores device `last_successful_sync_at`, clock offset, recovery-required flag, archive path/checksum/completion state, and atomic recovery checkpoints. These are not generic domain-synced tables.
- **Server-managed/account/payment tables:** auth users, `profiles`, `firms`, `firm_members`, `firm_invites`, `payment_submissions`, `payment_approval_events`, `mutation_receipts`, `invite_attempts`, and `app_admins`. Global domain sync columns do not automatically apply to them, and they are never queued. **One documented exception:** a `profiles` row's own display and detail columns are writable by their holder (see Resolved Design Clarifications, "The Lawyer's Own Details Live on the Account") — the server still owns `email`, `role`, `firm_id` and the entitlement pair.

### 4. Backup, identity, recovery, and membership

- A backup is a versioned authenticated-encrypted **full-app restorable snapshot**: all domain rows/history/tombstones, custom and user-modified seed rows, queue entries, per-user preferences and case-notification settings, pull-only caches, cursors, seed ledger, sync/recovery metadata, and required local configuration. Exclude database keys, auth tokens, passwords, recovery secrets, and other nonportable secure credentials; recreate or reauthenticate them after restore.
- Restore validates authentication tag/checksum/schema compatibility before a single transaction. A non-empty target offers Replace or Cancel only. Replace is atomic and rolls back on any failure.
- Before repositories adopt authenticated ownership, atomically rewrite placeholder-owned offline rows, queue payloads/base snapshots, notification settings, and attribution to the authenticated identity/firm. Preserve audit provenance separately and never expose one account's data to another.
- If `join_firm` fails after sign-up, onboarding remains retryable. If abandoned before successful redemption, a protected cleanup operation removes the provisional profile/account so it is treated as never created.
- Extended-offline fresh start explicitly clears all domain tables, queue, pull-only caches, per-user preferences/settings, notification configuration, cursors, custom/seed data, seed ledger, and recovery metadata after the verified archive. Preserve only minimum secure session material required for authenticated pull; require reauthentication if preservation is unsafe.
- Removing an associate immediately revokes server/app access. The server rejects removed-member mutations; the client discards/rolls back their pending mutations, retains immutable server audit attribution, receives a membership-revocation broadcast, then forces logout and securely erases all app data on next connectivity.
